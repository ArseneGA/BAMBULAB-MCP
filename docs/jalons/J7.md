# J7 — Adaptateur imprimante Bambu LAN et simulateur

Livrables : `internal/printer` (interface `Adapter`, implémentation `Bambu`), `internal/printer/sim` + `cmd/printer-sim` (simulateur), tests d'intégration adaptateur ↔ simulateur en processus.
Sources : `docs/research/bambu-lan-protocol.md` (notée « note » ci-dessous), `docs/DOSSIER.md` §10.
Aucune imprimante réelle n'a été contactée ; le simulateur n'écoute que sur 127.0.0.1 (il refuse tout autre hôte).

## 1. Conforme à la note de recherche

| Point | Réalisation |
|---|---|
| MQTT TLS 8883, user `bblp`, mot de passe = code d'accès | paho, `ssl://host:8883`, `SecretProvider` (jamais loggé ; `StaticSecret` masque `%v/%s/%#v`) |
| Topics `device/{SERIAL}/report` (abonnement) et `/request` (publication) | idem, QoS 1 pour les requêtes |
| `pushall` : limité à 1 / ≥ 5 min | envoyé à chaque (re)connexion, puis au plus toutes les 5 min (`PushAllMinInterval`) ; un lancement peut en déclencher un si la limite le permet |
| Rapports partiels P1 | fusion récursive des objets, remplacement des tableaux (`hms`) ; `FullReportSeen` n'est vrai qu'après un rapport ressemblant à un pushall |
| `get_version` | firmware lu dans le module `ota` (repli : premier `sw_ver`) |
| `pause` / `resume` / `stop` avec `param:""` | contrôles gardés par l'état courant, attente de la réponse (`result`) ou de l'état attendu |
| `project_file` | champs de l'exemple de la note, `ams_mapping` tableau d'entiers, `use_ams`, `sequence_id` incrémenté |
| FTPS implicite 990, `bblp` / code d'accès | `github.com/jlaffaye/ftp` `DialWithTLS` |
| États `gcode_state` | IDLE, INIT/PREPARE/SLICING → preparing, RUNNING → printing, PAUSE → paused, FINISH → finished, FAILED → failed ; hors ligne synthétique ; reste → unknown |
| Règles du dossier §10 | preuve de confirmation vérifiée par fonction injectée ; accusé de transport / acceptation / état observé distingués ; perte réseau après start → `StartUnknown` sans renvoi ; réconciliation par lecture d'état ; plateau vide non détectable → attestation humaine obligatoire |

Choix de bibliothèque FTPS : `jlaffaye/ftp` (client) car il gère le TLS implicite, PROT P, SIZE/STOR/DELE, et partage le `*tls.Config` entre contrôle et données (cache de sessions TLS + `ServerName` fixe : prérequis probable de la reprise de session). Côté simulateur : `fclairamb/ftpserverlib` (TLS implicite natif), plutôt qu'une implémentation maison.
Broker du simulateur : `mochi-mqtt/server/v2` (client inline pour écouter `request` et publier `report`).

## 2. Sécurité TLS

Le certificat de l'imprimante est auto-signé. `TLSOptions` exige **exactement une** voie, sinon `ErrTLSPolicy` :
1. `PinnedSHA256` (recommandée) : empreinte du certificat feuille, comparée dans `VerifyPeerCertificate` ;
2. `RootCAPEM` : vérification classique ;
3. `InsecureSkipVerify` + `InsecureReason` obligatoire (consignée au niveau WARN à chaque construction).
`printer.FetchCertFingerprint(ctx, "ip:8883")` affiche l'empreinte présentée pour que l'utilisateur la valide hors bande puis l'épingle ; elle n'est jamais épinglée automatiquement.

## 3. Garde-fous de `Start` (ordre exact)

1. Liaison de la preuve (sans I/O) : vérificateur présent, jeton non vide, non expirée, `printer_id`, `sha256`, `plate`, `ams_mapping` identiques à la requête ; `PlateClear` vrai. Sinon `ErrNoProof`, `ErrProofExpired`, `ErrProofMismatch`, `ErrPlateNotClear`.
2. Réservation : un seul Start à la fois (`ErrBusy`).
3. Imprimante connectée, rapport frais (≤ 30 s, pushall si permis, sinon `ErrStaleStatus`), état `idle` (`ErrNotReady`), sans `print_error` ni HMS (`ErrPrinterError`).
4. Fichier distant présent avec la bonne taille (FTPS `SIZE`).
5. **Seulement alors** appel du vérificateur injecté (qui peut consommer un jeton à usage unique) : un refus d'état ne brûle donc pas la confirmation.
6. Publication QoS 1 ; PUBACK attendu ; puis attente de la réponse `result` et de l'état.
   - réponse `fail` ou imprimante en `FAILED` après acceptation → `ErrStartRejected` (certain : rien ne tourne) ;
   - perte de session, délai dépassé ou PUBACK absent → `*StartUnknownError{Stage}` (`errors.Is(err, ErrStartUnknown)`), étape = `transport_unacknowledged` / `transport_acknowledged` / `accepted` ;
   - `nil` dès que PREPARE ou RUNNING est observé.
7. paho est configuré **sans** reconnexion automatique : un nouveau client est construit à chaque reconnexion (sinon la file QoS 1 pourrait rejouer le `project_file`). Aucun renvoi automatique n'existe nulle part.

`Reconcile(ctx, StartExpectation)` n'envoie jamais de commande de lancement ; après reconnexion et pushall il rend `started` (même `subtask_name`/fichier en preparing/printing/paused), `not_started` (idle, ou FINISH/FAILED d'un autre fichier) ou `unknown` (hors ligne, périmé, autre travail en cours, ou FINISH/FAILED du **même** fichier, indiscernable d'un tirage antérieur).

Upload : nom distant déterministe `<stem>-<sha256[:12]>.gcode.3mf` ; si un fichier de ce nom a déjà la bonne taille, aucun transfert (`Reused`). Sinon STOR avec empreinte et taille calculées au vol ; écart → suppression distante + `ErrUploadMismatch` ; `SIZE` après envoi vérifié.

## 4. Supposé (non confirmé par une source)

- **Valeur exacte de `url`** : défaut `ftp:///{name}` (configurable : `StartURLTemplate`, ex. `file:///mnt/sdcard/{name}`). La note la laisse à valider.
- **Orthographe du booléen de nivellement** : la note écrit `bed_levelling`, le dossier `bed_leveling` ; les deux clés sont envoyées.
- **`ams_mapping`** envoyé comme tableau d'entiers (la note montre `""` dans l'exemple mais décrit un tableau) ; vide si `use_ams` faux. Longueur 5 supposée, non imposée (valeurs −1…253 acceptées).
- `md5` envoyé vide ; `project_id/profile_id/task_id/subtask_id` à `"0"` ; `bed_type` `"auto"` ; `subtask_name` = nom distant sans extension.
- La réponse à `project_file` porte le même `sequence_id` et `result` (la note le dit pour les requêtes en général ; non vérifié pour cette commande). Si l'imprimante ne répond pas, l'état observé suffit à conclure.
- `Start` réussit à PREPARE ou RUNNING, pas seulement RUNNING : sur le vrai matériel PREPARE dure plusieurs minutes (chauffe, nivellement), attendre RUNNING dépasserait tout délai raisonnable. Un échec en cours de PREPARE (fichier introuvable) se voit dans le suivi (`failed` + `fail_reason`), pas dans le retour de `Start`.
- Reprise de session TLS sur le canal de données FTPS : activée côté client (cache de sessions) ; non vérifiée contre le vrai serveur. Le simulateur ne l'impose pas.
- Transfert FTPS non annulable en cours de route (le contexte n'est contrôlé qu'avant la connexion).
- Détection de rapport « complet » (gcode_state + nozzle_temper + hms) : heuristique.
- `Reconcile` considère un état `finished`/`failed` du même fichier comme `unknown` (choix prudent).
- Pause/Resume/Stop ne vérifient pas la fraîcheur (gestes de sécurité) mais l'état connu.
- Simulateur : valeurs `fail_reason`, `print_error`, HMS et `stg_cur` fictives ; `reject_start` simule un refus quelconque (la vraie raison d'un refus sans Developer Mode est inconnue).

## 5. À valider sur la vraie P1S

1. Firmware exact (`get_version`), présence du Developer Mode (P1 ≥ 01.08.02.00), LAN Only activé.
2. L'authentification MQTT fonctionne-t-elle en lecture seule sans Developer Mode ? (la note ne le tranche pas.)
3. Forme réelle de `url` pour `project_file` (`ftp:///`, `file:///mnt/sdcard/`, `file:///sdcard/`) et dossier de dépôt de la carte SD après FTPS (racine ? `cache/` ?).
4. Réponse de l'imprimante à `project_file` (champs, `reason` en cas d'échec) ; comportement avec `ams_mapping` incorrect (« mettra en pause et ne démarrera pas ») : l'adaptateur le verrait comme un `StartUnknown` par délai ou un état `paused`.
5. Format réel de `hms`, `print_error`, `mc_print_error_code`, `fail_reason`, `total_layer_num`.
6. Cadence réelle des rapports en idle (la fraîcheur de 30 s au lancement suppose des rapports réguliers) ; sinon allonger `MaxStartStatusAge` ou autoriser plus de pushall.
7. Reprise de session TLS exigée ou non sur FTPS ; support d'EPSV ; PASV renvoyant la bonne IP.
8. Passage `FINISH` → `IDLE` : un nouveau `project_file` est-il accepté depuis FINISH ? (`AllowStartFromFinish`, faux par défaut.)
9. Comportement du code d'accès après mise à jour du firmware.

## 6. Procédure de premier branchement réel (sans jamais lancer d'impression sans accord)

Principe : une étape n'est tentée que si la précédente est validée par l'utilisateur ; aucune étape ne démarre une impression avant l'étape 9, qui exige un accord explicite et la présence de l'utilisateur devant la machine.

1. **Préparer l'imprimante** (utilisateur) : plateau vide et dégagé, imprimante surveillée. Réglages > WLAN/Réseau : activer *LAN Only*, redémarrer, activer *Developer Mode*, noter l'IP et le code d'accès. Noter le firmware affiché.
2. **Secrets** : placer le code d'accès dans le fichier de configuration local ignoré par Git (jamais dans le dépôt, les journaux ni les réponses MCP).
3. **Empreinte** : exécuter `FetchCertFingerprint` sur `IP:8883` ; faire valider l'empreinte par l'utilisateur (comparer avec l'écran de l'imprimante / le routeur si possible), puis l'enregistrer comme `PinnedSHA256`. Ne pas utiliser `InsecureSkipVerify` hors diagnostic ponctuel consigné.
4. **Lecture seule MQTT** : `Connect` puis `Status` uniquement. Consigner dans ce document le `gcode_state`, la présence de `total_layer_num`, le format `hms`/`print_error`, la cadence des rapports, le firmware (`get_version`). Aucune commande d'écriture.
5. **Observer** pendant ~10 minutes en idle : mesurer l'intervalle entre rapports (point 6 de la section 5).
6. **FTPS** : `Upload` d'un petit fichier de test **inoffensif** (par exemple un `.3mf` déjà tranché mais qui ne sera pas lancé). Vérifier : connexion, login, STOR, `SIZE`, emplacement visible sur l'écran de l'imprimante. En cas d'échec de transfert de données, tester la reprise de session TLS et EPSV (section 5, point 7).
7. **Idempotence** : relancer le même `Upload` ; attendu `Reused=true`.
8. **Dry-run de `Start`** : exécuter `Start` avec une preuve **invalide** (jeton inconnu) et vérifier qu'il est refusé *avant* toute publication. Contrôler les préconditions (`ErrNotReady`, fraîcheur) sans rien envoyer.
9. **Premier lancement réel** : uniquement après accord explicite de l'utilisateur, plateau vérifié visuellement par lui, fichier court et sans risque (ex. petite pièce, matériau déjà chargé), main sur le bouton d'arrêt de l'imprimante. Confirmation produite par le mécanisme de confirmation (jeton lié à l'imprimante, au sha256, au plateau, aux matières). Noter l'URL de `project_file` qui a fonctionné, la réponse de l'imprimante, les états traversés, puis corriger `StartURLTemplate` et les hypothèses de la section 4.
10. **Pause / reprise / arrêt** pendant cette première impression, sous surveillance.
11. **Perte réseau** (optionnel, sous surveillance) : couper le Wi-Fi quelques secondes après un lancement de test pour constater `StartUnknown` puis `Reconcile`.

## 7. Simulateur (`cmd/printer-sim`)

```
printer-sim -mqtt-port 8883 -ftp-port 990 -control-port 8890 -access-code 12345678 \
            -faults hms_error,... -prepare 1s -print-duration 10s
```
Pannes : `offline`, `drop_after_start` (une fois : l'impression démarre, la liaison tombe sans accusé), `ignore_start`, `reject_start`, `hms_error`, `file_missing`, `plate_occupied` (sans effet observable, comme le vrai).
API de contrôle (127.0.0.1) : `GET /state`, `POST /faults/{nom}?on=true|false`, `POST /reset`.
Le simulateur émet des rapports **partiels** (seules les clés changées + `wifi_signal` périodique) et un rapport complet sur `pushall`. Les 8883/990 par défaut exigent éventuellement des droits : utiliser `-mqtt-port 0 -ftp-port 0` pour des ports éphémères (affichés au démarrage, avec l'empreinte du certificat).

Limites : l'imprimante réelle peut exiger la reprise de session TLS sur FTPS, des noms de fichiers particuliers, ou répondre autrement : le simulateur encode **notre lecture** de la note, il ne la prouve pas.
