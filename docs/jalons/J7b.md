# J7b — chaîne d'impression de bout en bout (`internal/printing`)

> **Révision sécurité du 2026-11-06** (modèle de menace : `docs/SECURITY.md`). Ce document décrit la chaîne telle que livrée puis durcie ; en cas de divergence, ce bandeau et `docs/SECURITY.md` priment. Changements : (1) l'outil MCP `confirm_print_from_app` est **supprimé** — aucun outil MCP n'approuve ; (2) l'accord humain exige un **navigateur enregistré** (`bambud enroll`, cookie de session) sur `/confirm/{id}`, `/stop/{id}`, `/setup/printer/{id}`, valable **2 min** après le clic et **invalidé après tout `not_sent`** ; (3) `cancel_print` en PRINTING **ne renvoie plus d'identifiant exécutable** : il crée une demande d'arrêt et renvoie `stop_url` (`/stop/{id}`), l'arrêt n'a lieu qu'après validation humaine ; (4) `add_printer` perd `insecure_reason`, `allow_start_from_finish`, `pinned_sha256` ; hôte limité au réseau local ; l'empreinte du certificat est lue par le serveur, **affichée** avec le numéro de série attendu et épinglée quand l'humain saisit le code ; (5) `printer.Start` : fichier distant → état frais idle → vérification de la preuve → publication ; (6) clés d'idempotence composées `printJobID:kind:clé`, rejeu avec d'autres paramètres refusé ; (7) `Reconcile` prudent, correspondance de fichier exacte ; (8) nouvel état terminal sûr `START_ABORTED_BEFORE_SEND` ; (9) `/api/previews/{sha}` limité aux aperçus enregistrés ; (10) `get_print_status` sans `ReadOnlyHint`, `EnsureModels` sans `sync.Once` figé.

Livrables : `internal/printing` (service), `internal/mcpserver/print_tools.go` (16 outils MCP après la révision sécurité, une ligne dans `New`), `internal/httpapi/printing.go` (routes + pages, une ligne dans `NewHandler`), branchement dans `internal/core` (`Core.Printing`), deux petites exportations (`catalog.RunWorker/EnsureDerived/RegisterGenerated`, `goals.GetProfileRevision`).
Sources : `docs/DOSSIER.md` §1, §6, §10 ; J1 (machine d'états, `ConsumeConfirmation`, kinds physiques), J5 (slicer, archive), J6 (variantes), J7 (adaptateur, simulateur).
**Aucune imprimante réelle n'a été contactée** : tout est validé contre `internal/printer/sim` (127.0.0.1) ; un mock ne vaut pas un essai matériel.

## 1. Séquence imposée (et ce qui la garantit)

`execute_headless_slice` (DRAFT → PREPARED → SLICING → VALIDATED) → `validate_print_artifact` → `upload_print_artifact` (UPLOADING → UPLOADED → AWAITING_PRINT_CONFIRMATION) → question posée à l'utilisateur → `request_print_confirmation` → **l'humain confirme sur une page web locale** → `start_print` (START_REQUESTED → PRINTING observé, ou START_UNKNOWN) → suivi (COMPLETED / FAILED).

| Règle | Mécanisme |
|---|---|
| L'envoi ne chauffe ni ne déplace rien | le dépôt n'émet que FTPS ; test : aucune commande `project_file` reçue par le simulateur après dépôt, état `IDLE` |
| Une autorisation ne vaut pas pour la suivante | la confirmation est liée au `PrintJob` (`ConsumeConfirmation(..., printJobID)`), à l'imprimante, à l'empreinte, au plateau, aux matières ; usage unique en base ; test : 2e impression du même fichier refusée avec l'ancienne confirmation |
| Pas de lancement sans confirmation consommée atomiquement | le `ProofVerifier` de l'adaptateur appelle `store.ConsumeConfirmation` **juste avant la publication MQTT**, après les contrôles d'état de l'imprimante : un refus d'état (`ErrNotReady`…) ne brûle donc pas la confirmation ; test : 5 `start_print` concurrents → 1 seule commande |
| `kind` physique, idempotent, jamais rejoué | `upload_print_artifact` et `start_print` passent par la file (`jobs.physicalKind` : clé d'idempotence obligatoire ; `start_print` est `neverReplay`) ; un travail `start_print` interrompu devient `unknown`, jamais relancé |
| Résultat incertain | START_UNKNOWN : `start_print` refuse, `cancel_print` refuse, seul `reconcile_print` agit (lecture d'état, jamais de commande de lancement) |
| Redémarrage du service pendant un lancement | `Recover` : START_REQUESTED → START_UNKNOWN ; PRINTING → suivi repris |
| Plateau vide | l'imprimante ne peut pas le savoir : attestation humaine obligatoire (case à cocher) ; `get_printer_status` répond toujours `plate_empty: "inconnu"` |

## 2. Mécanisme de confirmation choisi

Dossier §10 : « un simple booléen inventé par un agent n'est pas une preuve suffisante ». Choix :

1. `request_print_confirmation` crée une `PrintConfirmation` (jeton 256 bits, TTL 10 min par défaut, max 24 h). Le **jeton reste dans la mémoire du service** : il n'est ni renvoyé au modèle, ni stocké en clair (la base ne garde que son hachage ; test : absent de tous les fichiers de données et de la réponse). Le modèle reçoit `confirmation_id`, `confirm_url` et les éléments liés (fichier, imprimante, empreinte, plateau, matières, durée estimée).
2. **Seul canal d'approbation : page `/confirm/{id}`** (HTML serveur sans JavaScript), **derrière le cookie d'un navigateur enregistré** (code à usage unique obtenu par `bambud enroll` sur le terminal de l'humain, voir `docs/SECURITY.md` §2). L'humain voit le résumé, coche « le plateau est vide et dégagé », clique « Lancer l'impression ». Le formulaire porte un nonce à usage unique et n'est accepté que si `Sec-Fetch-Site: same-origin` et `Sec-Fetch-Mode: navigate` ; en-têtes `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, `no-store` ; protection cross-origin du garde HTTP. **L'accord vaut 2 minutes** après le clic et est invalidé après tout `not_sent`.
3. **Aucun outil MCP n'approuve.** `confirm_print_from_app` a été supprimé (révision sécurité). `get_print_confirmation_view` reste, marqué `_meta.ui.visibility: ["app"]`, en **lecture seule** (ni jeton ni nonce).
4. `start_print` ne reçoit que `confirmation_id` : il refuse tant que l'humain n'a pas approuvé, puis le service **consomme lui-même** la confirmation avec le jeton gardé en mémoire. Aucune route JSON ne permet d'approuver.

**Limites assumées** (à lire avant de se fier à ce mécanisme) :
- Ce n'est pas une preuve cryptographique de présence humaine : c'est une barrière qui sort la décision du canal que contrôle le modèle. Un agent qui disposerait lui-même d'un client HTTP local (hors MCP) pourrait lire la page puis soumettre le formulaire ; la mise en œuvre de `visibility:["app"]` dépend de l'hôte (Claude Desktop non qualifié ici).
- Le jeton n'existe qu'en mémoire : un redémarrage du service entre la demande et l'approbation oblige à refaire `request_print_confirmation` (comportement voulu).
- Avec `--api-token` (écoute hors loopback) le garde exige `Authorization: Bearer` sur l'**API JSON et `/mcp`** ; les **pages HTML** (`/enroll`, `/confirm`, `/stop`, `/setup`, `/agents/pair`) n'exigent **pas** le Bearer mais le cookie d'un navigateur enregistré. `--public-url` fixe la base des liens (plus de `http://[::]:port`).

## 3. Registre d'imprimantes et secrets

- `list_printer_models` : modèles semés **depuis les profils de Bambu Studio** (`printing.SeedPrinterModels`, remplace le TODO de `contracts.SeedPrinterModels`) : volume d'impression, buses, plateaux, source. Tout le reste (caisson, AMS, températures, caméra) reste **nil = inconnu**.
- `add_printer` : modèle, hôte (réseau local : RFC 1918, lien local, fc00::/7, `.local` ; sinon `--allow-any-printer-host`), série, buse, nombre d'AMS (déclaré), ports. **Aucun paramètre pour le code d'accès, l'empreinte du certificat, `insecure_reason` ni `allow_start_from_finish`** (test : absents du schéma d'entrée et refusés). L'outil renvoie `setup_url` = `/setup/printer/{id}` : page HTML (navigateur enregistré) où le serveur **affiche l'empreinte du certificat lue sur l'imprimante avec le numéro de série attendu** ; l'humain saisit le code d'accès, ce qui épingle exactement l'empreinte affichée. Aucune connexion tant que rien n'est épinglé ; changement d'hôte (`UpdatePrinterHost`) → ré-épinglage obligatoire.
- Coffre : `FileSecretStore`, AES-256-GCM (l'identifiant d'imprimante est la donnée authentifiée : une entrée copiée sous un autre identifiant ne se déchiffre pas), fichier `secrets/printers.secrets` ; clé maître `secrets/master.key` **enveloppée par DPAPI sous Windows** (liée au compte), sinon fichier 0600 + avertissement journalisé. Pas de trousseau OS (pas de dépendance cgo). Le code n'est ni dans la base, ni dans l'audit, ni dans les journaux, ni dans les réponses ; `accessCodeProvider` masque `%v/%s/%#v`.
- `get_printer_status` : état normalisé + **fraîcheur** (`age_seconds`, `stale`, `connected`) ; imprimante sans code ou injoignable → `offline` avec la raison, sans erreur d'outil.
- `AllowStartFromFinish` (par imprimante, faux par défaut, **non réglable par MCP/API** : `Service.SetAllowStartFromFinish`, code de confiance) : J7 §5 point 8 non validé sur matériel. Quand il est vrai, le service **vérifie en plus** qu'une activité de CE fichier a été observée après la commande (sinon START_UNKNOWN) et n'attribue un `FINISH` à l'impression qu'après avoir vu une activité (`seen_active`), car l'adaptateur peut prendre le `FINISH` précédent pour un succès.

## 4. Outils MCP ajoutés (17)

`list_printer_models`, `list_printers`, `add_printer`, `get_printer_status`, `execute_headless_slice`, `validate_print_artifact`, `upload_print_artifact`, `request_print_confirmation`, `start_print`, `get_print_status`, `cancel_print`, `reconcile_print`, `capture_preview`, `create_parametric_model`, `modify_geometry`, et l'outil d'application en lecture seule `get_print_confirmation_view` (`confirm_print_from_app` supprimé). `cancel_job` (existant) aiguille un identifiant `pj_…` vers `cancel_print`.

Routes HTTP équivalentes (`/api/printers`, `/api/print-jobs…`, `/api/confirmations/{id}`, `/api/previews`, `/api/models/parametric`, `/api/models/modify-geometry`) et pages `/setup/printer/{id}`, `/confirm/{id}`.

- **`execute_headless_slice`** : modèle + version + imprimante (+ révision de profil ; sinon la variante appliquée par `apply_variant`, sinon profils par défaut de la machine). Travail `printing.slice` (heavy, rejouable, tolérant à la reprise). Orientation de la variante appliquée au maillage (comme `goals`). Artefact conservé par empreinte.
- **`validate_print_artifact`** : `slicer.ValidateArchive` (blocage sur échec d'un contrôle d'archive) **et** compatibilité avec l'imprimante réelle : modèle d'imprimante, buse, plaque demandée, hauteur/volume, type de plateau (avertissement), matières : emplacements AMS déclarés, doublons, famille de matière du catalogue vs type du fichier découpé, buse minimale ; matière absente du catalogue = avertissement (« non vérifiée »), jamais acceptée silencieusement. Accepte `print_job_id` ou `artifact_id` (par ex. artefact d'une variante : une impression VALIDATED est alors créée, historique « artefact existant »).
- **`upload_print_artifact`** : `idempotency_key` et `assignments` (filament → emplacement `ams1:1..ams4:4`/`ext` → matière) obligatoires ; renvoie `question` = « Le fichier X est envoyé sur la P1S. Veux-tu lancer cette impression ? » (nom court du modèle) avec imprimante, empreinte, plateau, matières, durée/masse estimées et rappel plateau vide. `ams_mapping` dérivé des affectations (position = filament − 1, valeur = unité×4 + bac, 254 = externe ; supposition à valider, cf. J7 §4). La liaison de la confirmation encode `f{n}>{emplacement}` : changer l'affectation invalide la confirmation.
- **`start_print`** : vérifications dans l'ordre : clé (composée `printJobID:start:clé`, rejeu avec une autre confirmation refusé), impression en AWAITING, confirmation = celle de l'impression, non expirée/utilisée, approbation humaine **de moins de 2 min**, réservation de l'imprimante (une seule impression active), état **frais et idle** (ou finished si autorisé) sans erreur ; puis travail `start_print` → adaptateur : fichier distant vérifié, **relecture d'état fraîche + contrôle idle, puis** vérification/consommation de la preuve, puis publication (accusé de transport / acceptation / état observé distingués). Issues : `printing`, `start_unknown`, `rejected` (FAILED), `not_sent` (rien envoyé, jeton intact, **accord humain invalidé**), `aborted_before_send` (`START_ABORTED_BEFORE_SEND`, terminal : confirmation consommée mais lancement non enregistré, rien envoyé), `replayed`.
- **`get_print_status`** / suivi : abonnement de l'adaptateur + relevé périodique ; FINISH → COMPLETED, FAILED → FAILED, avec avancement (couche, %, restant) ; ne conclut que si le rapport désigne bien le fichier.
- **`cancel_print`** : avant lancement = annulation logique (la confirmation en attente cesse de valoir) ; SLICING = annule aussi la découpe ; PRINTING = **crée une demande d'arrêt** (TTL 10 min) et renvoie `stop_url` (`/stop/{id}`) + question : l'imprimante n'est arrêtée que quand l'humain valide cette page (navigateur enregistré + nonce) ; aucun identifiant exécutable n'est renvoyé au modèle ; START_REQUESTED/UNKNOWN et terminal (dont `START_ABORTED_BEFORE_SEND`) = refus.
- **`reconcile_print`** : `started` → PRINTING + suivi ; `not_started` → UPLOADED (nouvelle confirmation requise) ; `unknown` → reste START_UNKNOWN. `not_started` n'est conclu que si l'imprimante est idle (ou finie sur un autre travail) dans un rapport **complet** postérieur à la publication (repère : publication par l'adaptateur, sinon l'instant de `START_REQUESTED`) + délai de stabilisation (10 s), **sans commande acceptée** depuis ; sinon `unknown`. La correspondance de fichier est exacte (nom sans extension ou nom de base du G-code), jamais une sous-chaîne.
- **`capture_preview`** : PNG Go pur (z-buffer logiciel, suréchantillonnage 2×, police bitmap 5×7 intégrée, aucune dépendance). `model_id` : vue isométrique orthographique, Lambert, géométrie seule. `artifact_id`/`print_job_id` + `layer` : tracé 2D des segments extrudés d'une couche du G-code (couleur par `FEATURE`, contour du plateau si l'imprimante est connue). La légende donne les paramètres de rendu et dit **ce qui n'est pas représenté** (matériau, supports, déplacements à vide, rétractions, temps, défauts de maillage). Le PNG est conservé (`png_sha256`, route `GET /api/previews/{sha256}`).
- **`create_parametric_model`** : worker Python (`parametric`), sorties confinées dans un dossier de travail, enregistrées au catalogue (STEP + STL, version v1, provenance « génération paramétrique », hypothèses du worker). Échoue clairement (`cad_backend_missing`) si `uv`/CadQuery manquent ; testé avec un worker injecté.
- **`modify_geometry`** : opérations typées `scale` (facteur ou x,y,z, > 0), `rotate`, `mirror`, `translate`, `center_on_bed` (imprimante ou dimensions), `lay_flat` (plus grande face plane d'appui), `cut_plane` (plan axe = offset, garde au-dessus/dessous, **capuchon** par triangulation si la section est faite de contours simples non imbriqués ; sinon coupe ouverte + avertissement explicite). `base_version_id` périmée = refus. Résultat : **nouvelle version** (STL, parent = base), original intact, matrices appliquées, différences (boîte, volume, étanchéité, triangles). Échelle/rotation/miroir se font autour du centre de la boîte englobante.

## 6. Limites et restes à faire

- **Jamais essayé sur la vraie P1S** : `url` de `project_file`, `ams_mapping`, comportement depuis `FINISH`, cadence des rapports… restent les hypothèses de J7 §4–5. La procédure de J7 §6 s'applique, avec en plus : enregistrer le navigateur (`bambud enroll`), saisir le code via `/setup/printer/{id}` (jamais dans la conversation) après avoir comparé l'empreinte du certificat et le numéro de série affichés, tester les pages `/confirm/{id}` et `/stop/{id}` avant tout lancement.
- Le service ne connaît ni le type de buse (durcie ou non) ni le contenu réel de l'AMS (la télémétrie AMS n'est pas lue) : les affectations sont **déclaratives** et vérifiées contre ce que l'utilisateur déclare, pas contre l'imprimante.
- Suivi : si le service redémarre en PRINTING, le suivi reprend ; un `FINISH` du même fichier vu sans activité préalable n'est pas attribué (l'impression reste PRINTING avec une note) faute de pouvoir distinguer deux tirages du même fichier.
- Une impression par imprimante à la fois (réservation) ; pas de file d'impressions.
- `capture_preview` : rasterisation CPU sans anticrénelage de texte avancé ni éclairage au-delà de Lambert ; les très gros maillages (> 1 M de triangles) sont lents (pas de décimation).
- `modify_geometry` : pas de capuchon pour les sections creuses ; un 3MF d'origine donne un STL (métadonnées Bambu non reprises) ; `lay_flat` ne choisit pas l'orientation de lacet ; les supports/coutures peints ne sont pas transportés (dossier §6, dernier paragraphe).
- `create_parametric_model` n'a été exercé qu'avec un worker injecté (ni `uv` ni CadQuery vérifiés ici).
- La page de confirmation hors loopback : voir §2, dernière puce.
- Un répertoire vide `C:\ARSENE~1` a été créé par erreur à la racine du disque pendant le développement (chemin mal formé) ; il est inoffensif et à supprimer à la main.

## 7. Plateau multi-pièces et aperçu du plateau (chantier B)

Outils MCP (`internal/mcpserver/plate_tools.go`) et routes (`internal/httpapi/plates.go`), logique dans `internal/printing/plates.go`, `plates_pack.go`, `plate_preview.go` ; migration `0150_plate_plans.sql` (table `plate_plans`, plans en JSON).

- **`plan_plate`** (`POST /api/plate-plans`) : `printer_id` + pièces (`model_id`, `quantity`, `label`, `settings` par pièce, `layer_ranges`). Réglages acceptés (liste blanche validée par type, tous relus par Studio : `TestRealPerObjectKeys`) : `sparse_infill_density`, `sparse_infill_pattern`, `wall_loops`, `layer_height`, `top_shell_layers`, `bottom_shell_layers`, `brim_type`, `brim_width`, `enable_support` ; une clé inconnue est refusée avec la liste des clés. Le plateau vient du profil machine (dimensions, hauteur utile, zones interdites) ; sans profils, du volume du modèle d'imprimante. **Rapport « tient / ne tient pas » avant toute découpe** : chaque pièce contre le plateau (empreinte, hauteur, marge), nombre de plaques, occupation par plaque. Disposition : `arrangement=studio` (défaut si Studio est là : `Slicer.Arrange`, `--arrange 1` sans découpe, relue dans le projet exporté) ou `estimate` (rectangles englobants, rotation de 90°, écart `spacing_mm`, zones interdites évitées ; repli automatique et signalé si Studio échoue). `group_by_settings` ne mélange jamais deux jeux de réglages sur une plaque.
- **`execute_plate_slice`** (`POST /api/plate-plans/{id}/slice`) : refuse un plan qui ne tient pas ; crée **un PrintJob par plaque** (DRAFT → PREPARED → SLICING → VALIDATED) ; chaque découpe reconstruit le 3MF depuis le projet figé (`SliceSpec.Plan`, positions comprises) et tranche **la seule plaque k** (`--slice k`) : l'archive de chaque impression ne contient que sa plaque, dont le numéro (`Job.Plate`) et l'empreinte sont ce que `validate_print_artifact`, le dépôt et la confirmation lient, comme pour toute impression. Après la découpe, le service **vérifie que l'archive porte exactement les pièces du plan pour cette plaque** (sinon `plate_mismatch`, impression en échec) et joint au résumé (`summary.objects`) la matière, les couches et l'étendue de **chaque pièce**, lues dans le G-code (`slicer.ObjectReport`). Idempotence : `idempotency_key` par plaque ; un rejeu renvoie les mêmes impressions ; une plaque déjà découpée n'est pas relancée.
- **`get_plate_plan`** (`GET /api/plate-plans[/{id}]`) : relit un plan ou liste les plans.
- **`capture_preview`** gagne `mode` (`mesh` | `layers` | `plate`) et `plan_id`. Mode **`plate`** : vue de dessus du plateau réel (grille 10 mm, repères tous les 50 mm, zones interdites hachurées), pièces rasterisées à leur position et orientation réelles — lues dans le plan (avant découpe) ou dans le 3MF d'une plaque découpée (`print_job_id` / `artifact_id`) —, numérotées, avec légende (nom, dimensions, réglages, et après découpe masse, part et couches par pièce ; temps de la plaque entière). ~900 px de large, 30 à 40 Ko. Mode **`layers`** : la couche de G-code existante (`artifact_id`/`print_job_id` + `layer`). Sans `mode`, le comportement d'avant est inchangé.
- **Sécurité** : aucun de ces outils ne dépose, n'approuve ni ne lance ; chaque plaque suit la séquence habituelle et exige son propre accord humain (docs/SECURITY.md §3).
- Tests : `TestPlanPlateReportAndPreview` (rapport, rejets, aperçu), `TestRealStudioPlatePlan` (4 matrices à 100 % + 2 poussoirs à 15 %, disposition Studio, découpe, validation, aperçu de l'archive, idempotence) ; unitaires `plates_unit_test.go` ; côté `slicer` : `TestRealPerObjectInfill`, `TestRealPerObjectKeys`, `TestRealThreePlates`, `TestRealArrangeThenSlice`, `TestObjectReportSplitsByLabel`, `TestPlateOriginsFollowStudioGrid` ; côté `mesh` : `TestWriteBambuProjectRoundTrip`.
- Limites : la pièce est posée comme dans sa version du catalogue (pas d'orientation automatique) ; une pièce multi-objets est fusionnée en un seul objet ; le rangement estimé est conservateur ; un seul filament par plan (pas d'affectation de couleurs par pièce) ; jupe, bordure et tour d'essuyage ne sont pas dessinés ; le temps n'est pas ventilé par pièce ; un plan fige les positions : modifier une pièce impose de recalculer le plan.

### Retours supplémentaires de l'écran Impression

- **A. Impressions « découpe en cours » pendant des heures.** Cause : une découpe annulée côté file (`cancel_job` sur le travail), échouée ou perdue ne mettait pas à jour le `PrintJob` (le handler ignorait volontairement l'annulation) ; et l'écran étiquetait aussi « découpe en cours » les impressions encore **en file** (PREPARED), alors que la file ne découpe qu'une à la fois. Correction : `CheckConsistency` / `SweepOrphans` (toutes les 15 s, à chaque lecture de l'historique et de `get_print_status`) ferment l'impression avec une raison explicite quand son travail est échoué, annulé, inconnu, introuvable, ou « en cours » sans battement depuis 3 min / depuis plus de 45 min ; l'interface affiche « en file (position n) » ou « découpe en cours · x % ». Tests : `TestOrphan*`, `TestQueuedSliceReportsPositionNotRunning`.
- **B. Historique encombré.** `list_print_history` (vues all/active/finished/failed/archived/trash, regroupement par modèle, compteurs), `manage_print_history` (archive / corbeille / restore, uniquement sur des impressions terminées, **rien n'est supprimé définitivement**), `GET /api/print-jobs?view=&group=model`, `POST /api/print-jobs/history`, onglets, groupes et boutons dans l'interface. Test : `TestHistoryViewsArchiveTrashRestoreAndGrouping`.
- **C. « Joignable · failed » après un arrêt humain.** `get_printer_status` renvoie `display`, `explanation`, `last_job`, `hms_codes` : après un arrêt validé sur `/stop`, l'écran affiche « arrêtée (annulée par vous) » ; sinon « échec ou annulation (failed) » avec l'explication de `gcode_state FAILED` (annulation **ou** erreur, `print_error` / codes HMS). Test : e2e 5 (arrêt humain).
- **D. -50 affiché tel quel.** Remplacé par le message du point 1 (le texte anglais de Studio reste dans l'erreur technique entre crochets).

Limites : la règle de la zone sûre (238 × 228) est déduite des trois mesures terrain et du profil, **pas vérifiée contre Studio 02.09** ; la progression de découpe est une estimation ; les codes HMS sont donnés en hexadécimal, sans traduction (pas de base d'erreurs Bambu embarquée) ; les couleurs d'un filament de profil ne sont plus jamais affichées, donc un AMS non lu et non déclaré donne « inconnue ».
