## 1. Protocole `agentlink` v1 (`/agent/v1`)

HTTP + JSON, versionné (`ProtocolVersion = 1`, refus d'une autre version à l'appairage et au hello).

| Étape | Route | Détail |
|---|---|---|
| Jeton | `POST /api/agents/pairing` (admin, **boucle locale uniquement**) | jeton `pair-…` à usage unique, 15 min, stocké **haché** |
| Appairage | `POST /agent/v1/pair` | échange le jeton contre `agent_id` + secret (256 bits) ; le serveur ne garde que SHA-256(secret) ; jeton consommé atomiquement |
| Auth | `Authorization: Bearer <agent_id>.<secret>` | comparaison en temps constant ; agent révoqué refusé |
| Hello | `POST /hello` | annonce des capacités (Studio présent/version/lancé, slicer local, dossiers autorisés, CAO, types de travaux), liste des travaux détenus → **réconciliation** |
| Heartbeat | `POST /heartbeat` | signe de vie (15 s par défaut), reçoit les annulations demandées |
| Travaux | `GET /tasks/next?wait=N` (long-polling ≤ 30 s), `POST /tasks/{id}/start|progress|result` | remise atomique `queued → assigned` ; rapport idempotent |
| Inventaire | `POST /inventory` | lots de 100 : `rel_path`, taille, mtime, **sha256**, chemin d'origine |
| Envoi | `POST /uploads/begin` puis `PUT /uploads/{sha}?task=ID` + `Content-Range` | **reprise** (offset renvoyé par le serveur, 409 + `Upload-Offset` en cas de décalage) ; sha256 recalculé à réception avant toute publication dans le magasin ; seul un envoi autorisé par un travail est accepté |
| Entrées | `GET /blobs/{sha}` (Range) | uniquement les artefacts listés dans les entrées d'un travail non terminé de CET agent ; le client vérifie le sha256 |

Aucun chemin partagé n'est supposé : tout passe par identifiants d'artefacts + empreintes. Les `rel_path` reçus sont validés (jamais absolu, `..`, lecteur, nom réservé Windows, caractères interdits) ; les étiquettes de dossier sont assainies.

**Disponibilité** : `Online` = signe de vie dans les 45 s (configurable). `GET /api/capabilities` et `get_capabilities` exposent `agents[] {id, name, online, last_seen, agent_version, studio_installed, studio_running, studio_version, local_slicer, shared_folders, cad, tasks}`, la fonction `windows_agent` (et `studio_session`, `windows_slicing`, `windows_import`) et `mode` = `linux_renfort_windows` quand au moins un agent est en ligne (sinon `linux_seul`). Branchement par `Core.CapabilityHooks` (une ligne dans `core.go`, posée par `agentlink.For(core)`).

### Travaux, exécuteur et perte de l'agent
Table `agent_tasks` (`executor = windows-agent`, `kind`, `params`, `inputs` figés avec leur taille, états `queued → assigned → running → succeeded|failed|cancelled|unknown`). Les travaux Linux restent dans la file `jobs` ; `executor: linux` sur ce protocole est refusé avec un message explicite.

- **Agent perdu** (plus de signe de vie > `OfflineAfter`, ou révoqué) : ses travaux `assigned`/`running` passent à **`unknown`** avec une note ; ceux jamais remis (`queued`) restent en file, rien n'a démarré. Rien n'est relancé tout seul.
- **Retour** (hello) : l'agent liste ce qu'il détient. Détenu et en cours → `running` (« réconcilié ») ; terminé côté agent → il rapporte l'issue réelle (acceptée depuis `unknown`) ; non détenu → reste `unknown`. Le journal de l'agent (un fichier par travail, `%LOCALAPPDATA%\BambuAtelier\state`) permet de rapporter après un redémarrage : un travail interrompu est rapporté `failed/agent_restarted`.
- **Reprise explicite** `POST /api/agent/tasks/{id}/requeue` (travail `unknown|failed|cancelled`, **non physique**) : nouveau travail (`replaces`), l'ancien passe `cancelled` (« remplacé par … ») et son éventuel rapport tardif est refusé (409) : pas de publication en double.
- **Travaux physiques** (`start_print`, `send_to_printer`) : jamais acceptés par ce protocole (409 `physical_task_refused`), jamais ré-assignés (testé aussi sur une ligne forcée en base). Une seconde impression ne peut donc pas naître d'une perte d'agent.
- Un résultat n'est accepté avec des sorties que si chaque sortie a été **transférée et vérifiée** (409 `output_not_uploaded` sinon). L'artefact rapatrié reste un blob ; il ne devient une version publiée que par un geste explicite hors de ce jalon.

## 2. Import depuis Windows (dossier §15.4)

1. Config agent : dossiers autorisés (`bambu-agent folder add --label Modèles --path D:\3D`). Seuls ces dossiers sont lus.
2. Travail `inventory` (ou `bambu-agent inventory --label …`) : parcours **lecture seule** (ouverture en lecture, aucune écriture/renommage/suppression ; liens symboliques non suivis), STL/OBJ/3MF/STEP, sha256 de chaque fichier, détection d'un fichier modifié pendant la lecture. Envoi au serveur par lots.
3. Côté catalogue : `RegisterRemote` (nouveau fichier `internal/catalog/remote.go`) crée collection (étiquette + sous-dossiers), modèle, version v1 et fichier source **`windows_only`** (empreinte annoncée par l'agent, aucun contenu). Même contenu déjà connu → doublon sans rien ajouter ; même chemin d'origine avec un autre contenu → nouvelle version. `GET /api/agents/{id}/inventory` donne le résumé (fichiers, octets, par état, **octets encore uniquement sur Windows**).
4. `POST /api/agents/{id}/inventory/select` (tout, ou une liste de `rel_paths`) renvoie fichiers + octets estimés et crée un travail `upload_files`. L'agent **recalcule l'empreinte** de chaque fichier : modifié depuis l'inventaire → `skipped_changed`, jamais envoyé. Envoi avec reprise, un seul transfert par contenu.
5. À réception (sha256 vérifié, blob écrit atomiquement) le fichier est posé dans une zone de réception (`data/agent-inbox/<agent>/<étiquette>/…`, nom et mtime d'origine) puis importé par le chemin d'import normal du catalogue : `windows_only → linux` sans doublon, structure en collections, aperçu/analyse lancés. La zone est vidée ensuite (les blobs restent). États d'inventaire : `inventoried → requested → uploaded → imported | error`.
6. Originaux Windows : jamais modifiés (test : contenu + date comparés avant/après, aucun fichier ajouté/supprimé). Une copie sur le serveur n'est pas une sauvegarde (dossier : stratégie de sauvegarde séparée, non traitée ici).

## 3. Slicing Windows en renfort

Travail `slice` : entrée = artefact (modèle) téléchargé et vérifié, `internal/slicer` exécuté localement (mêmes presets/surcharges/validation que J5), artefact `.gcode.3mf` renvoyé par transfert vérifié ; le résultat porte l'exécuteur (`windows-agent`), la version de l'agent, la version du binaire Studio et la validation. Mesuré : modèle cube 20 mm sur P1S, **1,1 s** de bout en bout agent↔serveur (test réel `TestSliceReinforcementReal`, archive contenant `Metadata/plate_1.gcode`, validation OK). Les sorties Linux/Windows peuvent différer ; qualification sur corpus commun : non faite (aucun slicer Linux qualifié dans ce dépôt).

## 5. Agent Windows (`cmd/bambu-agent`)

```
bambu-agent pair --server http://192.168.1.20:7878 --token pair-… [--name PC-Atelier] [--dpapi-scope user|machine]
bambu-agent folder add --label Modèles --path D:\3D        # dossiers autorisés
bambu-agent run                                            # boucle de travaux (premier plan)
bambu-agent inventory --label Modèles
bambu-agent status | studio info | studio project | studio open F | studio probe --file F --close | studio close --pid N
bambu-agent service install|remove|run                      # service Windows (droits admin)
```
Jeton : sur le serveur, `curl -X POST http://127.0.0.1:7878/api/agents/pairing` (refusé hors boucle locale).

- **Secret** : `agent.json` (`%LOCALAPPDATA%\BambuAtelier`) ne contient que le blob **DPAPI** (`CryptProtectData`, sel applicatif, `CRYPTPROTECT_UI_FORBIDDEN`) en base64, jamais le secret en clair, jamais dans les logs. Portée `user` par défaut (même compte, même poste) ; `machine` pour un service sous un autre compte. Si le profil Windows change, le secret est illisible : réappairer.
- **Service** : implémenté (`golang.org/x/sys/windows/svc`, `mgr`), journal `agent.log` ; **non exécuté ici** (nécessite l'élévation). DPAPI « user » est lié au compte : appairer avec `--dpapi-scope machine` ou faire tourner le service sous le compte qui a appairé. Pas d'icône de zone de notification (l'option « simple » retenue : processus `run`, ou service).
- Coupures réseau : reconnexion avec attente croissante (1 → 30 s), résultat gardé au journal jusqu'à l'acquittement.

## 7. Limites et points ouverts

- Seconde ouverture avec une instance déjà lancée : non mesurée. Ligne de commande d'un vrai Studio : non rejouée après ajout.
- Crash dump à la fermeture de l'essai manuel (voir matrice) ; fichier laissé dans `%APPDATA%\BambuStudio\log`.
- `get_project_state` ne voit pas les modifications non enregistrées ni un projet jamais enregistré.
- Pas de passerelle C++ : aucune modification en direct de la session.
- Authentification du reste de l'API `/api/*` inchangée (J1 : écoute locale). Le protocole agent, lui, est authentifié, mais **non chiffré** (HTTP) : sur un LAN non fiable, mettre HTTPS/VPN devant (non traité). bambud écoute par défaut sur 127.0.0.1 : pour un agent distant, lancer avec `--addr` LAN en connaissance de cause.
- Espace disque libre du serveur non comparé aux octets à copier avant sélection (l'estimation d'octets est fournie).
- Pas de synchronisation retour (copies de travail vers Windows avec révision) au-delà de `open_in_studio` ; pas d'extraction d'archives.
- Qualification Linux/Windows des sorties de slicing : non faite.
- Migration numérotée 0080 ; `store_test` compare désormais le nombre de migrations à celles embarquées.
- Modifications hors périmètre strict, minimales : `core.go` (+`CapabilityHooks`), `contracts/capabilities.go` (+`Agents`), `httpapi.go` (+1 ligne), `mcpserver/server.go` (+1 ligne) et `server_test.go` (nombre d'outils 22), `store_test.go`, `go.mod` (`golang.org/x/sys` direct).
