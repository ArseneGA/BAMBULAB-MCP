# Sécurité — modèle de menace et mécanismes

Date : 2026-11-06. Complète `docs/DOSSIER.md` §1 et §10 (« aucun lancement sans accord humain explicite, lié, par impression ; un booléen fourni par l'agent ne suffit pas »). Mécanismes détaillés : J7b (chaîne d'impression), J8 (agent Windows).

## 1. Modèle de menace

| Acteur | Capacités | Traitement |
|---|---|---|
| **Le modèle (Claude)** | n'a que les **outils MCP** (et leurs sorties) | **Doit JAMAIS pouvoir produire seul l'accord de lancement ni d'arrêt** d'une impression, ni lire un secret (code d'accès LAN, jeton de confirmation, code d'enregistrement, jeton d'appairage). C'est la menace de référence. |
| Un site web / une page ouverte dans le navigateur de l'humain | requêtes cross-origin | refusées (garde Host, `http.CrossOriginProtection`, cookie `SameSite=Strict`, `Sec-Fetch-*`, nonce de formulaire) |
| Un appareil du LAN | requêtes réseau vers bambud (si l'écoute n'est pas en loopback) | l'API JSON et `/mcp` exigent le Bearer (`--api-token`, obligatoire hors loopback) ; les pages humaines exigent le cookie d'un navigateur enregistré |
| Un agent Windows appairé | protocole `/agent/v1` authentifié par secret | ne peut ni lancer ni arrêter (les travaux physiques lui sont refusés) ; formats et tailles contrôlés |
| **Un processus local qui a les droits de l'utilisateur (shell)** | lit la base, le coffre, peut lancer `bambud enroll` | **Hors périmètre** : il pourrait aussi bien lire le coffre des codes d'accès ou piloter l'imprimante directement. On rend l'abus **difficile** (code à usage unique, cookie haché, révocation) et **visible** (journal d'audit : création de code, session, révocation, épinglage de certificat, arrêt). |

Conséquence de conception : **l'accord humain ne passe que par des pages HTML servies par bambud, derrière le cookie d'un navigateur enregistré**. Aucun outil MCP et aucune route JSON n'approuve un lancement ou un arrêt.

## 2. Navigateurs enregistrés (`internal/humanauth`)

1. **Code d'enregistrement** : `bambud enroll` (terminal de l'humain) affiche un code de 8 caractères (alphabet sans `0 O 1 I`), **usage unique, 10 min**, stocké **haché** (SHA-256). Il n'existe ni outil MCP ni route JSON pour le créer ou le lire.
   - *Canal CLI → service* : la commande **écrit directement dans la base SQLite** partagée (WAL, verrou d'écriture court, aucun passage par le verrou d'instance), le service relit la table à chaque saisie. Choix retenu plutôt qu'une socket/un fichier de commande : aucune surface réseau ou fichier supplémentaire à protéger, aucun port, la protection est celle de la base (droits du compte). Justification : un attaquant qui peut écrire dans la base est déjà dans la catégorie « processus local avec les droits de l'utilisateur » (hors périmètre, §1).
2. **Saisie** : `GET/POST /enroll` (HTML serveur). Après un code valide : cookie `bambu_session` (jeton 256 bits, **stocké haché**), `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` si la requête est en TLS, si un proxy **de confiance** (`--trusted-proxies`, défaut loopback) envoie `X-Forwarded-Proto: https`, ou si l'URL publique dont l'hôte correspond au `Host` est en `https://` (`--public-url` accepte une liste), durée 30 jours. Anti-force brute : **par adresse client** (adresse TCP, ou entrée `X-Forwarded-For` la plus à droite qui n'est pas un proxy de confiance) — 6 échecs → verrou de 5 minutes, doublé à chaque récidive jusqu'à 1 h ; **plafond global** plus haut (60 échecs en 5 minutes, donc au moins 10 adresses distinctes) → suspension de tous les enrôlements 1 minute, doublée à chaque déclenchement jusqu'à 15 min. Un attaquant isolé ne peut pas bloquer l'enrôlement des autres. La soumission exige `Sec-Fetch-Site: same-origin` et `Sec-Fetch-Mode: navigate`.
3. **Gestion** : `bambud enroll --list`, `--revoke ID` (préfixe accepté si non ambigu), `--revoke-all` ; `POST /enroll/logout` (page) retire le navigateur courant.
4. **Pages protégées** (`humanauth.Require`) : `/confirm/{id}`, `/stop/{id}`, `/setup/printer/{id}`, `/setup/passkeys` (§ 13), `/agents/pair`.
   - `GET` sans cookie valide → 303 vers `/enroll?next=…` (chemin local uniquement).
   - `POST` : cookie valide **et** `Sec-Fetch-Site: same-origin` **et** `Sec-Fetch-Mode: navigate` (en-tête absent = refus) **et** nonce de formulaire à usage unique lié à la page.
4bis. **Pages humaines en http hors loopback** : refusées par une page « Cette page exige HTTPS : ouvrez <URL https de BAMBU_PUBLIC_URL> » (403), avant toute autre logique ; la protection cross-origin n'est jamais assouplie (`Origin: null` reste refusé). Seul localhost ou https (TLS, proxy de confiance ou URL publique https) sert ces pages. Test : `TestHumanPageHTTPSRequired`.
5. **`GET /api/session`** → `{enrolled, session?}` (sans secret, sans jeton d'API) pour la web app.
6. **Jeton d'API vs cookie** (interface web) : avec `--api-token`,
   - `/mcp` exige **toujours et seulement** le Bearer (le cookie n'y vaut rien : le modèle n'a pas de cookie, et ne doit pas en gagner un) ;
   - `/api/*` accepte le Bearer **ou** le cookie d'un navigateur enregistré. Par cookie, les lectures (`GET`/`HEAD`) passent ; les **écritures** exigent en plus l'en-tête personnalisé `X-Atelier-Request: 1` (envoyé par `web/src/api/client.ts`, impossible à poser depuis un autre site sans préliminaire CORS, que bambud ne donne jamais) **et** `Sec-Fetch-Site: same-origin` (à défaut d'en-têtes Sec-Fetch — les navigateurs n'en envoient pas en `http://` hors localhost —, un `Origin` identique au `Host`), sinon 403 `csrf` ; la protection cross-origin de Go s'applique en plus. Un Bearer valide n'a pas besoin de ces en-têtes ;
   - la SPA (`GET /`, `/assets/*`, routes client) est servie **sans authentification** : elle ne contient aucune donnée (tout passe par `/api/*`). Sans cookie, elle affiche « Enregistrer ce navigateur » (lien vers `/enroll`) ;
   - les pages HTML humaines (`/confirm`, `/stop`, `/setup`, `/agents/pair`) restent **inchangées** : cookie + navigation de même origine + nonce, ni Bearer ni appel de la SPA ne peuvent les remplacer. **Aucune route d'approbation de lancement ou d'arrêt n'existe sous `/api` ni dans `/mcp`** (test `TestCookieWritesNeedCSRFHeaderAndSameOrigin` : un appel « SPA » à `/stop/…` reste refusé) ;
   - l'URL d'aperçu signée (`/api/assets/<sha>.glb?exp&sig`, HMAC + expiration, vérifiée par le handler) reste lisible sans Bearer pour l'iframe d'un hôte MCP Apps.
   Le cookie vaut donc exactement les droits du Bearer sur `/api/*`, pas davantage : c'est l'humain devant son navigateur enregistré.
7. **URL publique** : `--public-url` (env `BAMBU_PUBLIC_URL`, une **liste** séparée par des virgules est possible) : la première fixe la base des liens remis au modèle (`/confirm`, `/stop`, `/setup`) ; tous les noms d'hôte sont autorisés d'office par le garde Host ; plus jamais `http://[::]:port` (hôte non spécifié → `127.0.0.1`).
8. **Jeton obligatoire** : refus de démarrer sans `--api-token` si l'écoute n'est pas loopback, avec `--require-token` / `BAMBU_REQUIRE_TOKEN`, si `--public-url` désigne un hôte non loopback ou si `--allowed-hosts` contient un nom non loopback. **Derrière un proxy (Funnel, `tailscale serve`, nginx), toujours un jeton.** `/mcp` derrière un proxy loopback fonctionne (le garde Host de bambud remplace le contrôle de loopback du SDK MCP).
9. **Proxys de confiance** : `--trusted-proxies` / `BAMBU_TRUSTED_PROXIES` (défaut : loopback ; `none` : aucun). `X-Forwarded-For` et `X-Forwarded-Proto` ne sont lus que sur une connexion TCP venant de ces adresses ; ailleurs ils sont ignorés (forgeables).
10. **Racines d'import** : refus de démarrer si `BAMBU_IMPORT_ROOTS` contient le dossier de données, ou s'y trouve (sinon import puis téléchargement de la base et de `secrets/`).

## 3. Lancement d'une impression (rappel, voir J7b §2)

`request_print_confirmation` → **l'humain** ouvre `/confirm/{id}` dans un navigateur enregistré, (ou saisit son code dans la vue), coche « plateau vide » et valide → **le serveur lance lui-même l'impression** (`internal/printing/autostart.go`, 2026-11-08) : même `StartPrint` que l'outil, clé d'idempotence propre à la confirmation, un seul envoi, jamais de renvoi (START_UNKNOWN réconcilié en lecture). Le modèle n'a aucun pouvoir de plus : seul un geste humain approuve, donc seul un geste humain démarre. `start_print` reste une reprise : il constate « déjà lancé » sans renvoyer ; si le démarrage automatique n'a rien envoyé (imprimante pas prête), l'accord reste valable 2 minutes. Tests : `TestEndToEndChainWithSimulator`, `TestConcurrentStartsSendOneCommand`, `TestLaunchCodeApprovesPrintFromAppTool`, `TestConfirmationViewChain`.

- La confirmation est liée (imprimante, empreinte, plateau, matières), à usage unique, expire (10 min) ; son jeton reste **en mémoire** du service.
- **L'accord humain ne vaut que 2 minutes après le clic** ; il est **invalidé après tout `not_sent`** (le jeton n'est pas brûlé, l'humain doit recliquer).
- Le jeton est consommé **juste avant la publication MQTT** (`printer.Start` : fichier distant vérifié → relecture d'état fraîche et contrôle « lançable » (IDLE, FINISH ou FAILED, sans HMS ni erreur en cours : § 12) → vérification/consommation de la preuve → publication).
- Si la confirmation est consommée mais que le passage en `START_REQUESTED` ne peut pas être enregistré : état terminal sûr **`START_ABORTED_BEFORE_SEND`** (rien n'a été envoyé).
- Plateau multi-pièces (`plan_plate`, `execute_plate_slice`) : ces outils ne font que planifier et découper ; **une impression = une plaque**, chacune avec sa propre confirmation liée à l'empreinte de SON archive (qui ne contient que cette plaque) et à son numéro de plaque.
- Aucun outil MCP n'approuve **sans le code de lancement personnel de l'humain** (§ 12) : `confirm_print_from_app` a été **supprimé** ; `get_print_confirmation_view` est en lecture seule (ni jeton ni nonce) ; les seuls outils d'approbation sont `approve_print_with_code` / `approve_stop_with_code` (app-only, mais appelables par un modèle : la sécurité est le code, haché, verrouillé après 3 échecs). Test : `TestNoMCPToolCanApproveAConfirmation` énumère tous les outils (schémas d'entrée sans champ d'approbation, appels forgés, la confirmation reste non approuvée).

## 4. Arrêt d'une impression

`cancel_print` sur une impression en cours **ne renvoie aucun identifiant exécutable** : il **crée une demande d'arrêt** (TTL 10 min, réutilisée tant qu'elle est valide) et renvoie `stop_url` (`/stop/{id}`). L'imprimante n'est arrêtée que lorsque l'humain valide cette page (navigateur enregistré + nonce), ou saisit son code de lancement dans la vue d'arrêt (§ 12). L'identifiant n'est qu'un localisateur : sans le cookie, il ne sert à rien. Les tables en mémoire `stops`, `pages` (nonces), `approv`, `consumedBy` ont un TTL et sont purgées (à l'émission et chaque minute).

## 5. Imprimantes : hôte, certificat, code d'accès

- `add_printer` n'accepte plus `insecure_reason`, `allow_start_from_finish` ni `pinned_sha256`. Il n'y a **aucun moyen de désactiver la vérification TLS** par MCP/API. `allow_start_from_finish` est un réglage de code de confiance (non validé sur le matériel).
- **Hôte** : adresse privée (RFC 1918), de lien local (169.254/16, fe80::/10), ULA (fc00::/7) ou nom en `.local`. Loopback et adresses publiques refusés (le serveur ne doit pas être détourné vers un tiers), sauf option serveur `--allow-any-printer-host`.
- **Épinglage du certificat** : sur `/setup/printer/{id}`, le **serveur** lit le certificat présenté par l'imprimante (`FetchCertInfo`, rien n'est envoyé), l'**affiche** (empreinte SHA-256, CN) avec le **numéro de série attendu** (avertissement si le CN ne correspond pas, ou si le certificat a changé depuis l'épinglage). L'humain confirme **en saisissant le code d'accès** : l'empreinte épinglée est exactement celle affichée (liée au nonce côté serveur ; un champ forgé dans le formulaire est ignoré). Tant que rien n'est épinglé, **aucune connexion** n'est tentée.
- **Changement d'hôte** (`UpdatePrinterHost`) : l'empreinte épinglée est effacée → ré-épinglage obligatoire.
- Le code d'accès n'est jamais une entrée MCP/JSON ; coffre chiffré (DPAPI + AES-256-GCM) ; jamais journalisé.

## 6. Agent Windows

- **Appairage** : le jeton d'appairage ne se crée plus par `POST /api/agents/pairing` (route supprimée, répond 410). Seulement par `bambud agent pair` (CLI humaine, affiché sur le terminal) ou par la page `/agents/pair` d'un navigateur enregistré. Usage unique, 15 min, haché.
- **Transport** : l'agent accepte `--server-fingerprint` (empreinte SHA-256 du certificat TLS du serveur, épinglage) ; avertissement explicite si le serveur est joint en `http://` hors loopback (secret et fichiers en clair). Client HTTP avec délais (connexion 10 s, TLS 10 s, en-têtes 2 min, JSON 60 s, morceau 10 min).
- **Transferts** : format contrôlé selon le type de travail (sorties `slice` : `.gcode.3mf`/`.3mf` ; import : STL, OBJ, 3MF, STEP — signature vérifiée avant publication dans le magasin), tailles maximales par type (STL/OBJ/STEP 512 Mio, 3MF 1 Gio), verrou par (agent, sha), `.part` complet finalisé à la reprise, `.part` abandonnés purgés (24 h) et supprimés à la fin du travail.
- Gardes d'état (`Complete`, `CancelTask`, `Requeue`) avec contrôle de `RowsAffected` ; `Registry.Run` démarré par `Core.Run`, imports en arrière-plan avec contexte d'arrêt, attendus (`Shutdown`) avant la fermeture de la base.

## 7. Autres durcissements

- **Idempotence** : clés composées `printJobID:kind:clé` (dépôt, lancement) ; rejeu avec d'autres paramètres refusé (`clé d'idempotence déjà utilisée avec d'autres paramètres`).
- **Réconciliation** : `not_started` seulement si l'imprimante est idle (ou finie sur un autre travail) dans un rapport **complet** postérieur à la publication + délai de stabilisation (10 s), sans commande acceptée depuis ; sinon `unknown`. Correspondance de fichier **exacte** (plus de `Contains`).
- `/api/previews/{sha}` ne sert que des blobs enregistrés comme aperçus PNG.
- `GET /api/files/{id}/download` et `POST /api/export` ne servent que des originaux du stockage par empreintes (fichiers copiés, modèle hors corbeille) : aucun chemin du disque n'est lisible par cette voie, les noms d'entrée de l'archive sont assainis, le sha256 est recalculé à l'écriture (une divergence laisse une archive invalide plutôt que fausse). Elles restent derrière le jeton d'API (ou le cookie d'un navigateur enregistré) et le garde Host / cross-origin comme tout `/api`.
- L'interface web n'ajoute aucune route d'approbation : lancement et arrêt passent toujours par `/confirm` et `/stop` (navigateur enregistré) ; la réconciliation d'un lancement incertain est en lecture seule et n'envoie jamais de commande de lancement.
- **Coût, journal, tableau de bord, post-traitement** (`internal/insights`, outils `estimate_cost`, `set_cost_settings`, `list_print_log`, `update_print_log`, `suggest_print_adjustments`, `get_usage_dashboard`, `get_project_costs`, `post_processing_advice` ; routes `/api/cost`, `/api/print-log`, `/api/usage`, `/api/post-processing`) : le paquet ne lit que `print_jobs`, `printers`, `models`, `print_results` et n'écrit que `insight_settings` et `print_logs` ; il n'appelle jamais la chaîne d'impression (ni lancement, ni arrêt, ni approbation : le test `TestInsightToolsRegisteredAndWorking` vérifie l'absence de champ d'approbation). Les réglages ne contiennent que des prix et des watts (aucun secret). Les photos de fiche : JPEG, PNG ou WebP seulement (signature vérifiée, SVG refusé), 12 Mio et 8 par fiche au plus, servies uniquement si le blob est une photo de la fiche demandée, avec `X-Content-Type-Options: nosniff` et `Content-Security-Policy: default-src 'none'; sandbox` ; l'envoi passe par `POST /api/print-log/{id}/photo` derrière le Bearer ou le cookie d'un navigateur enregistré avec l'en-tête CSRF. Les ajustements de réglages proposés ne sont jamais appliqués automatiquement.
- `EnsureModels` ne fige plus un échec (pas de `sync.Once`).
- `get_print_status` n'est plus annoncé en lecture seule (il met l'impression à jour).

## 8. Limites assumées

- Un processus local avec les droits de l'utilisateur est hors périmètre (§1).
- Ce n'est pas une preuve cryptographique de présence humaine : c'est une barrière qui sort la décision du canal que contrôle le modèle.
- Le cookie `Secure` n'existe qu'avec TLS direct, `X-Forwarded-Proto: https` d'un proxy de confiance ou une URL publique en `https://` correspondant au `Host` (bambud ne termine pas TLS lui-même : mettre un proxy).
- Navigateurs sans `Sec-Fetch-*` (très anciens) : les `POST` des pages humaines sont refusés.
- Un navigateur enregistré garde sa session 30 jours ; révoquer avec `bambud enroll --revoke`.
- Pas encore de rotation du jeton d'API, pas de TLS natif côté serveur.


## 10. OAuth 2.1 intégré (connecteur distant de Claude) — 2026-11-07

Détail et exigences de Claude : `docs/OAUTH.md`. Ce qui touche au modèle de menace :

- Le **Bearer statique reste valide** sur `/mcp` et `/api/*`, inchangé. S'y ajoute, **sur `/mcp` uniquement**, un jeton d'accès OAuth (`bat_…`, 1 h) émis par bambud pour la portée unique `mcp`. Il n'ouvre **ni `/api/*`, ni les pages humaines** ; sur `/mcp` il n'a pas plus de droits que le Bearer (aucun outil MCP n'approuve un lancement ou un arrêt, voir §3 et §4).
- **Le consentement est un geste humain** : `/oauth/consent/{id}` est une page humaine (`isHumanPath`, `humanauth.Require` : cookie de navigateur enregistré, `Sec-Fetch-*` de navigation, nonce à usage unique, demande à usage unique de 10 min). `/oauth/authorize` n'accorde rien : il valide la demande (client enregistré, `redirect_uri` exacte, PKCE S256, `resource`) et affiche une page « Continuer » (le cookie `SameSite=Strict` ne suit pas une navigation venue d'un autre site). Le modèle n'a ni cookie ni moyen de produire le consentement.
- **Consentement non hameçonnable** : la page « Continuer » (vue par le navigateur qui a ouvert `/oauth/authorize`) pose un cookie de liaison (`obind`, HttpOnly, SameSite=Strict, limité au chemin de la demande) dont l'empreinte est gardée avec la demande ; `/oauth/consent/{id}` (GET et POST) l'exige. Un lien de consentement transmis à un navigateur enregistré qui n'a pas ouvert la demande est refusé (403) : l'attaquant ne peut plus faire approuver SA demande par la victime. Conséquence assumée : il faut cliquer « Continuer » dans le navigateur enregistré qui a lancé la connexion. La page n'affiche plus le `client_name` comme fiable : « nom déclaré par le client (non vérifié) », avec l'hôte de redirection, l'adresse IP et l'heure de la demande. Tests : `TestOAuthConsentPhishingIsRefused`, `TestConsentIsBoundToTheInitiatingBrowser`.
- **Abus de l'enregistrement et de l'autorisation** : limites de débit par adresse (`opts.clientAddr` : proxys de confiance pris en compte, `X-Forwarded-For` jamais cru ailleurs) sur `POST /oauth/register` et `GET /oauth/authorize` (429), clients sans autorisation purgés après 15 min, au plus 30 clients récents par adresse.
- **Révocation en cascade** : révoquer un navigateur enregistré (`bambud enroll --revoke`, `--revoke-all`, déconnexion) révoque aussi les autorisations OAuth qu'il a accordées (`human_session_id`). Test : `TestRevokingABrowserRevokesItsOAuthGrants`. Les erreurs d'écriture de l'audit et de mise à jour sont journalisées, plus ignorées.
- Surface non authentifiée ajoutée : `POST /oauth/register` (clients publics, redirections en liste blanche : callbacks de Claude + boucle locale ; au plus 200 clients, purge des clients sans autorisation après 15 min, corps ≤ 16 Kio), `POST /oauth/token` (code à usage unique 60 s + PKCE ; refresh à rotation ; rejeu d'un code ou d'un refresh révoque l'autorisation ; corps ≤ 16 Kio), `GET /oauth/authorize`, `GET /.well-known/*` (métadonnées). Les autres chemins `/.well-known/` répondent 404 JSON.
- Jetons et refresh stockés **hachés** (SHA-256) ; jamais journalisés. Révocation : `bambud oauth --list|--revoke|--revoke-all` (effet immédiat) ; audit des événements `oauth.*`.
- Un jeton est lié à sa ressource (`<url publique>/mcp`, RFC 8707) : valable pour l'hôte public qui l'a émis seulement.
- `guard.go` : modifications minimales et testées (`isOAuthOpen`, préfixe `/oauth/consent/` dans `isHumanPath`, jeton d'accès accepté sur `/mcp` seulement, `WWW-Authenticate` avec `resource_metadata` sur le 401 de `/mcp`). Tests : `internal/httpapi/oauth_test.go` (PKCE, mauvais verifier, redirection non autorisée, jeton révoqué, refresh et rejeu, consentement sans cookie / cross-site / mauvais nonce, jeton hors `/mcp`, jeton lié à l'hôte) ; les tests existants (garde, cookie, CSRF, `TestNoMCPToolCanApproveAConfirmation`) restent verts.
- Limites : état en attente (demandes, codes) en mémoire ; pas de CIMD ni de `/oauth/revoke` ; non éprouvé contre un vrai claude.ai (aucune exposition faite).

## 9. Caméra, détection d'échec, notifications (chantier D)

- **Aucun arrêt ni lancement automatique.** La détection d'échec n'a aucun accès à une commande d'arrêt (l'interface `camera.Backend` n'en offre pas). Une alerte crée seulement une *demande* d'arrêt (`/stop/{id}`, validée par l'humain) et notifie avec photo. Test : l'imprimante reste RUNNING après l'alerte et après l'ouverture de la page `/stop`.
- **Caméra** : TLS vers le port 6000 avec l'empreinte épinglée (celle de MQTT, ou une empreinte propre validée par l'humain sur `/setup/camera/{id}`, liée à un nonce) ; aucune connexion tant que rien n'est épinglé ; tailles d'images bornées (4 Mio), JPEG vérifié. Le code d'accès vient du coffre, jamais loggé.
- **Photos** : servies par `/api/camera/photos/{sha}` seulement si enregistrées dans `camera_photos` (jamais un autre blob) ; derrière le jeton d'API ou le cookie d'un navigateur enregistré. Une image de caméra est une donnée, jamais une instruction. La photo de `/confirm` ne remplace pas l'attestation humaine « plateau vide ».
- **Notifications** : la DESTINATION d'un canal (hôte, port et utilisateur SMTP, destinataires, URL ntfy / webhook) et ses secrets (URL ntfy, URL/clé webhook, mot de passe SMTP) ne se règlent que sur `/setup/notifications` (navigateur enregistré + nonce), coffre chiffré ou variables ; l'outil MCP `configure_notifications` ne peut que lister (sans secret), activer ou désactiver un canal EXISTANT et choisir ses évènements (`Service.PatchChannel` : ni création, ni suppression, ni destination). Sans cela, le modèle aurait pu rediriger un canal e-mail vers un hôte à lui et récupérer le mot de passe SMTP (AUTH) et les photos. Le mot de passe SMTP est **lié à (hôte, port, utilisateur)** : un changement de l'un des trois l'invalide (effacé du coffre) et, même si la configuration était modifiée hors de la page, la liaison enregistrée refuse de servir le mot de passe à une autre destination. Jamais renvoyés (vue : `set`/`source` seulement), jamais journalisés ; redirections HTTP refusées ; webhook non signé refusé ; SMTP toujours en TLS (certificat vérifié).
- **Destinations non publiques refusées (SSRF)** : ntfy, webhook et SMTP ne peuvent viser ni la boucle locale, ni un réseau privé, ni une adresse de lien local (contrôle à la saisie sur les adresses littérales et noms évidents, ET à la connexion sur l'adresse réellement résolue, contre le rebond DNS) ; les ports SMTP hors {25, 465, 587, 2525} sont refusés. `BAMBU_NOTIFY_ALLOW_PRIVATE=1` (variable du serveur, jamais réglable par le modèle) lève cette garde pour un ntfy ou un SMTP local voulu. Aucune erreur renvoyée au modèle (`test_notification`, journal d'envoi) ne contient d'adresse, de port ou de nom d'hôte : « connexion impossible », « délai dépassé », « certificat non vérifié », « destination non publique refusée ». Tests : `internal/notify/guard_test.go`.
- **Caméra** : un instantané à la demande n'est jamais enregistré ; limite de débit par imprimante (instantanés et ouvertures de flux, spectateurs bornés) ; images refusées au-delà de 4096 x 4096 (`jpeg.DecodeConfig` avant tout décodage, y compris dans le moniteur) ; photos d'alerte purgées après `alert_photo_retention_days` (90 par défaut).
- Limite : le détecteur est heuristique (faux positifs possibles : personne devant la caméra plusieurs minutes ; faux négatifs : filaments dans la colonne de la pièce). Il aide, il ne garantit rien.
## 9. File d'attente, bobines et AMS (chantier E)

- **La file ne lance jamais.** `queue_print`, `list_print_queue`, `reorder_queue`, `remove_from_queue` et le service `internal/filament` préparent seulement : attente de la découpe, dépôt du fichier de l'élément de tête (clé d'idempotence `queue-<id>`), demande d'une confirmation (`request_print_confirmation`, qui n'approuve rien), notification. Le démarrage de chaque impression passe par `/confirm/{id}` (navigateur enregistré, nonce, case « plateau vide ») **pour chaque impression**, y compris la suivante après la fin d'une impression : une file n'enchaîne jamais seule.
- Garde-fous testés : `TestQueueNeverStartsAutomatically` (trois impressions en file, le simulateur ne reçoit qu'une commande `project_file` par clic humain, jamais davantage), `TestQueueNeverStartsOrApproves` (le code de `internal/filament` ne contient aucun appel de lancement, d'approbation, d'arrêt ni de consommation de jeton), `TestHTTPRoutes` (aucune route de lancement ou d'approbation sous `/api/print-queue` ni `/api/spools`) ; `TestNoMCPToolCanApproveAConfirmation` couvre aussi les nouveaux outils (aucun champ d'approbation dans leurs schémas).
- Le lien de confirmation affiché par la file expire comme les autres (10 minutes) ; « nouveau lien » redemande une confirmation, jamais un accord.
- **L'affectation matière est liée à l'accord** (`bindingSlot` = `f<n>><emplacement>`) : un changement d'affectation après le clic invalide la confirmation (`TestConfirmationBindsMaterialAssignment`).
- **L'alerte de manque est informative.** Elle s'ajoute au rapport de validation (`filament_short_<n>`) et à la page de confirmation, sans bloquer : un inventaire faux ne doit pas empêcher une impression légitime ; l'humain voit l'alerte avant de cliquer.
- **Saisie humaine protégée** : la lecture de l'AMS ne modifie que les données observées, l'étiquette RFID (si vide) et un restant qui n'a pas été saisi (`remaining_source` différent de `human`). Les champs saisis sont listés dans `human_fields`.
- Les points d'accroche `Printing.AddJobEndHook` et `SetFilamentCheck` n'ont aucun pouvoir sur le lancement : ils observent la fin d'une impression (décompte) ou ajoutent des alertes.

## 11. Contenu du G-code (surcharges, archive, confirmation) — 2026-11-07

Un modèle de langage manipulé pourrait chercher à faire confirmer à l'humain un fichier dangereux : une buse à 350 °C, un démarrage modifié, une commande qui touche au micrologiciel. Trois barrières, indépendantes de ce que dit le modèle, et dont la référence est toujours l'installation locale de Bambu Studio (jamais le fichier jugé).

**1. Liste blanche des surcharges** (`internal/slicer/allowlist.go`, appliquée à `modify_slicing_profile`, `apply_variant`, les expériences, la calibration et le tranchage lui-même : toutes passent par `applyOverrides`).
- Seules les clés listées (voir `docs/UTILISATION.md` § 13) sont surchargeables, avec leur type et leurs bornes. **Toute clé `*_gcode`** (`machine_start_gcode`, `machine_end_gcode`, `layer_change_gcode`, `before_layer_change_gcode`, `change_filament_gcode`, `time_lapse_gcode`, `template_custom_gcode`, `printing_by_object_gcode`, `filament_start_gcode`…), `post_process` (script exécuté sur le G-code) et `gcode_substitutions` sont refusées par un message explicite ; toute clé hors liste aussi.
- Bornes : température de buse dans `[nozzle_temperature_range_low ; min(nozzle_temperature_range_high, maximum du modèle)]` du profil filament ; plateau ≤ `bed_temperature_limit` (ou `bed_temp_range`) du modèle ; le maximum du modèle est lu dans `resources/printers/<id>.json` de Bambu Studio (`nozzle_temp_range`) : P1S 300/100 °C, A1 mini 300/80 °C, A1 300/100 °C, X1E 320/110 °C, H2 350 °C. Vitesses ≤ `machine_max_speed_x/y` du profil machine, accélérations ≤ `machine_max_acceleration_extruding` (déplacement : `…_travel`) ; les profils BBL dépassant eux-mêmes ce maximum en déplacement (travel_speed 700 sur A1/A1 mini, travel_acceleration 10000 > 9000), la borne est `max(maximum machine, valeur actuelle du profil officiel)`. Hauteur de couche ≤ diamètre de buse. Le reste : bornes statiques documentées.
- Les réglages par pièce et par plage de hauteur du plan multi-pièces passent par la même liste blanche et les mêmes bornes (`CheckObjectSettings`, avant l'écriture du 3MF) ; ils n'acceptent que des clés de process.

**2. Validation de l'archive** (`slicer.ValidateArchive`, appelée aussi par `validate_print_artifact`). Tout le G-code de chaque plaque est lu :
- `M104`/`M109` (buse), `M140`/`M190` (plateau), `M141`/`M191` (chambre) : maxima, consigne en vigueur à la 1re couche, minimum/maximum pendant l'impression. Au-delà du maximum du modèle, ou de la plage haute du filament pendant l'impression, ou consigne illisible (`S0x15E`, gabarit non évalué) : **refus `unsafe_gcode`** (contrôle bloquant : pas de dépôt sur l'imprimante). Le démarrage officiel du P1S chauffe à 250 °C pour vidanger : le plafond de la phase de démarrage est le maximum du modèle, celui de l'impression la plage du filament.
- Commandes : l'ensemble attendu (`slicer.ExpectedCommands`) est établi sur de vrais fichiers de Bambu Studio 02.08 (P1S PLA/PETG avec supports, bordure, repassage ; A1 mini) et les gabarits de G-code des profils P1/A1 : toute autre commande est un **avertissement** (`gcode_commands`, avec première ligne et exemple) ; les commandes qui modifient le micrologiciel (`M92`, `M112`, `M206`–`M208`, `M301`–`M304`, `M502`, `M906`–`M914`, `M997`, `M999`, écriture/suppression SD `M28`–`M30`, `M32`) sont un **refus**.
- **Empreinte du G-code de démarrage/fin** : tous les paramètres `*_gcode` de `project_settings.config` et le bloc de configuration du G-code sont comparés (fins de ligne normalisées) à ceux du profil machine officiel résolu, filament compris ; `post_process` doit être vide. Une différence : **refus** (`unsafe_gcode_profile`, avec la liste des clés). Profil inconnu de l'installation : avertissement « non vérifiable ». Pour que l'empreinte ait un sens, `profiles.Resolve` applique maintenant les gabarits `include` des machines BBL (voir (e) ci-dessous).

**3. Confirmation humaine** : `/confirm/{id}` et `get_print_confirmation_view` / `request_print_confirmation` affichent, lus dans le G-code et non dans une déclaration : températures de buse (démarrage, 1re couche, impression min–max) et de plateau, matières, et la ligne « G-code de démarrage : profil officiel ✓ ». Toute anomalie (analyse absente, profil différent, commande inattendue, filament non vérifiable) est en rouge. Le résumé vient de l'analyse de l'archive, jamais du modèle.

**Tests** : `internal/slicer/safety_test.go` (liste blanche, bornes, M104 S350/400 °C, commandes dangereuses, empreinte, post_process), `integration_safety_test.go` (vrais profils BBL, vrais fichiers P1S PLA/PETG et A1 mini acceptés, archives modifiées à la main refusées), `internal/printing/safety_unit_test.go`, `safety_e2e_test.go` (page et vue de confirmation, dépôt bloqué), `internal/goals/whitelist_test.go`.

**Limites** : (a) le G-code final ne se compare pas au gabarit après rendu (substitutions de variables) : un démarrage altéré par des déplacements sans commande interdite et sans température hors bornes n'est détecté que par l'empreinte des paramètres, que le faussaire contrôle aussi dans l'archive ; les commandes et températures, elles, sont lues dans le G-code exécutable. (b) Le maximum thermique est celui de la fiche du modèle, pas la sécurité du micrologiciel de l'imprimante réelle. (c) Une archive tranchée avec une autre version de Studio (G-code de démarrage daté différemment) est refusée : retrancher avec la version installée. (d) La liste des commandes attendues couvre la famille P1/A1 ; une X1/H2 produira des avertissements, pas des refus. (e) Défaut corrigé au passage : `profiles.Resolve` ignorait les `include` des profils machine BBL, donc le CLI de Studio recevait le G-code de démarrage **générique** du profil de base (`G28`, `M109 S205`, ligne de purge) au lieu de celui de la P1S/A1 mini (mise en chauffe du plateau puis de la buse à la température du filament, nettoyage, nivellement, vidange AMS). Les gabarits (uniquement des clés `*_gcode`) s'appliquent désormais comme dans Studio ; les fichiers tranchés avant ce correctif avaient une chauffe de buse incorrecte (mesuré sur Studio 02.08 : PLA Basic imprimé à 205 °C du début à la fin au lieu de 220 °C ; PETG attendu à 205 °C puis consigne 255 °C donnée sans attente) et doivent être retranchés.

## 12. Code de lancement personnel : approuver depuis la vue MCP App — 2026-11-07

**Besoin** : lancer et arrêter une impression sans quitter Claude (vue de confirmation dans la conversation). **Contrainte** : le serveur ne distingue pas un appel venu de la vue d'un appel fait par le modèle ; `visibility: ["app"]` n'est qu'un indice d'affichage (la faille `confirm_print_from_app` a déjà été corrigée une fois). Un simple bouton serait donc approuvable par Claude lui-même. **Conception** : l'accord repose sur un **secret que seul l'humain connaît**, pas sur la visibilité d'un outil. *On suppose qu'un modèle PEUT appeler les outils app-only.*

**Le code**
- 6 à 8 chiffres (ni identiques, ni en suite), défini **uniquement** sur `/setup/launch-code` (page humaine : `humanauth.Require` = navigateur enregistré + `Sec-Fetch-*` de navigation + nonce à usage unique, POST seulement, jamais dans une URL, jamais renvoyé dans la page) ou supprimé par `bambud launch-code --reset` (terminal de l'humain, même canal base de données que `bambud enroll`). Aucun outil MCP, aucune route `/api` ne le crée, le lit, le change ni le déverrouille.
- Stocké **haché** (argon2id, sel aléatoire de 16 octets, 32 Mio / 2 passes) dans la table `launch_code` (migration 0210). Jamais journalisé : l'audit enregistre « défini / révoqué / déverrouillé / échec n° k » avec l'identifiant de confirmation, jamais la valeur. Révocable et changeable sur la même page.

**Outils** (`internal/mcpserver/launch_tools.go`) : `approve_print_with_code(confirmation_id, code, plate_clear)` et `approve_stop_with_code(stop_id, code)`, tous deux `visibility: ["app"]` ; `get_launch_view_state` et `get_stop_view_state` (app-only, lecture seule, aucun secret : code défini ?, verrouillé ?, essais restants, photo réduite du plateau). `cancel_print` et `request_print_confirmation` sont liés à la vue (`_meta.ui.resourceUri`).

**Garanties** (chacune a un test) :
1. *Sans le bon code, aucun outil n'approuve* : absent, vide, mal formé, faux, `plate_clear` faux → rien. `TestNoMCPToolCanApproveAConfirmation` (énumère tous les outils : les deux seuls noms en `approve_` sont app-only et exigent `code` ; arguments forgés sur tous les autres outils) et `TestLaunchCode*`.
2. *Verrouillage global après 3 échecs consécutifs* (compteur durable en base, commun au lancement et à l'arrêt) : ensuite même le **bon code** est refusé. Seuls la page `/setup/launch-code` (bouton « Déverrouiller », navigateur enregistré) et `bambud launch-code --unlock|--reset` déverrouillent. Un essai bien formé est **compté avant** la comparaison (douze appels parallèles ne donnent que trois comparaisons : `TestLaunchCodeParallelGuessesAreCountedOnce`). Un essai mal formé (pas 6 à 8 chiffres) est refusé sans être compté (il ne permet aucune devinette).
3. *Délai minimal de 3 s entre deux essais* (refus sans comparaison ni décompte).
4. *Tentative liée à la confirmation précise* : l'essai n'est examiné que sur une confirmation vivante, non consommée, dont la liaison (imprimante, empreinte, plateau, matières) est inchangée ; une confirmation périmée, inconnue ou remplacée est refusée **sans consommer d'essai**. Pour l'arrêt : une demande `/stop/{id}` valide et une impression encore en cours. L'accord obtenu ne vaut que pour cet identifiant, **2 minutes à partir de l'approbation** (la confirmation vit 10 minutes depuis la demande ; les deux délais sont indépendants), et **déclenche aussitôt le démarrage côté serveur** (autostart.go) ; `start_print` n'est plus qu'une reprise : `ConsumeConfirmation` et la preuve consommée juste avant la publication MQTT sont **inchangés**. L'arrêt par code exécute `ExecuteStop` comme la page `/stop`.
5. *L'attestation « plateau vide » reste obligatoire* en plus du code (le code ne la remplace pas).
6. *Le code n'apparaît nulle part* : ni dans une sortie d'outil (les échecs sont des résultats structurés `problem: bad_code|locked|too_fast|not_set|format`), ni dans un message d'erreur (un intergiciel de réception du serveur MCP expurge toute reprise de l'argument `code`, y compris l'écho d'une validation de schéma sur un type erroné : le SDK écrit « type: 907351 has type integer »), ni dans les journaux (le serveur ne journalise aucun argument d'outil ; le SDK non plus), ni dans l'audit, ni dans un fichier de données. `TestLaunchCodeNeverLeaks` et la fin de `TestNoMCPToolCanApproveAConfirmation` capturent **tous les journaux au niveau Debug** (service, serveur MCP, API), **toutes les réponses d'outils**, l'audit et le dossier de données, et exigent l'absence du code (bon et mauvais).
7. *Descriptions d'outils pour le modèle* : « tu ne dois PAS appeler cet outil et tu ne dois JAMAIS demander ce code à l'utilisateur dans la conversation » (descriptions des deux outils, de `request_print_confirmation`, de `cancel_print`, instructions du serveur).
8. *Sans code défini, ou verrouillé* : la vue affiche le lien navigateur (comportement d'avant). **Le lien navigateur reste toujours disponible**, y compris sous verrou (test `TestLaunchCodeThreeWrongCodesLockEverything`).

**La vue** (`web/mcp-app/launch.tsx`, tests vitest) : le code n'est jamais gardé (champ vidé avant l'appel, jamais dans le DOM, aucun `updateModelContext` / `sendMessage`), mise en garde permanente « Ne tapez jamais ce code dans la conversation avec Claude ».

**Risques résiduels (assumés)**
- **Saisie du code dans la conversation.** Si Claude le demande malgré les consignes et que l'utilisateur l'écrit, le code est dans le contexte du modèle, qui peut alors appeler `approve_print_with_code` lui-même : le serveur **ne peut pas l'empêcher**. Atténuations : consignes dans quatre descriptions d'outils et les instructions du serveur, mise en garde visible dans la vue et sur la page de définition, « changez-le tout de suite » en cas d'erreur. Même exposition possible si l'hôte affiche ou relaie à Claude les arguments des appels d'outils faits par la vue (comportement de l'hôte, non vérifié ici). Dans les deux cas l'attestation « plateau vide » reste à la charge du modèle puisque `plate_clear` est un argument : **un code divulgué permet à un modèle d'approuver seul**. Les 2 minutes, l'usage unique de la confirmation et le lien à l'impression précise limitent la portée ; changer le code répare.
- **Déni de service par le modèle** : trois mauvais codes verrouillent l'approbation par code (le lien navigateur reste utilisable, l'humain déverrouille). C'est le prix de l'absence de devinette : avec 6 chiffres, trois essais ont 3 chances sur un million.
- **Force brute hors ligne** : l'empreinte argon2id d'un code à 6–8 chiffres se casse en quelques minutes pour qui lit la base ; ce lecteur est un processus local avec les droits de l'utilisateur, **hors périmètre** (§ 1).
- Pas de preuve de présence humaine : un code se saisit comme un mot de passe (hameçonnage par une page qui imiterait la vue : non traité). Le verrou est durable (base) mais le délai minimal et la sérialisation sont par processus.
- Photo du plateau : réduite à 480 px de large et ≤ 70 Ko avant envoi à la vue (limite d'environ 150 000 caractères par résultat d'outil) ; l'affichage d'une image `data:` dépend de la CSP de l'hôte (non vérifié sur un vrai Claude Desktop).
- Non éprouvé contre un vrai Claude Desktop ni une vraie imprimante.
- **Photo du plateau sur `/confirm` (défaut corrigé 2026-11-08)** : la photo était servie (200, JPEG, cookie d'enrôlement) mais **bloquée par la CSP de la page** (`default-src 'none'` sans `img-src`, `internal/humanauth/web.go`) : icône brisée. Seule la page `confirm` reçoit maintenant `img-src 'self'` (`PageHeadersWithImages`) : jamais `data:` ni origine tierce ; la route `/api/camera/photos/{sha}` reste derrière le Bearer ou le cookie d'un navigateur enregistré (aucune photo sans autorisation). Test : `TestCameraEndToEnd`.
- **Démarrage déclenché par l'approbation** : un code de lancement divulgué permettait déjà à un modèle d'approuver puis d'appeler `start_print` ; il le permet maintenant en un appel, sans changement de pouvoir. L'attestation « plateau vide » reste un argument fourni par l'appelant.
- **Mise à niveau du plateau dans la liaison approuvée (2026-11-08)** : `contracts.ConfirmationBinding.NoBedLeveling` (omitempty : l'empreinte des liaisons « activée » est inchangée) fait partie de l'empreinte consommée par `ConsumeConfirmation` ; changer `bed_leveling` exige une nouvelle confirmation, qui invalide l'ancienne. La commande lit la valeur de l'impression liée, jamais un paramètre de `start_print`. Tests : `TestBindingFingerprintCoversBedLeveling`, `TestStartSendsBedLevelingByDefault`, `TestBedLevelingOffIsBoundAndShown`.
- **Départ depuis FAILED et FINISH, imprimante lançable avant confirmation (2026-11-08)** : après une annulation la P1S reste en `gcode_state=FAILED` (print_error 50348044 = `0300_400C`) jusqu'au redémarrage ; Bambu Studio lance depuis FAILED ou FINISH. Le service aussi (`printer.StartPolicy`, `BambuConfig.StartFromTerminal`, posé par `internal/printing`), **sans rien relâcher d'autre** : (1) état **frais** relu juste avant l'envoi ; (2) **aucune alerte HMS active** ; (3) **aucun `print_error` en cours**, sauf le reliquat bénin d'annulation (`0300400C`, `0500400E`) et seulement en FAILED/FINISH (en IDLE ou ailleurs, toute erreur bloque) ; (4) plateau attesté vide par l'humain, confirmation à usage unique, `ConsumeConfirmation` atomique, une seule commande, jamais de renvoi — **inchangés**. L'ancien état final **ne compte jamais comme preuve de départ** : depuis FINISH/FAILED, seul PREPARE/RUNNING observé après la commande prouve le démarrage ; sinon `START_UNKNOWN` (réconcilié en lecture). Un FAILED d'avant la commande n'est pas pris pour un refus. Le contrôle (`printer.CheckLaunchable`) est le même à trois endroits : `request_print_confirmation` (refuse AVANT d'émettre la confirmation, avec une consigne précise : occupée, injoignable, « erreur HMS 0300_… ; acquittez-la sur l'écran ou redémarrez »), `StartPrint` et `printer.Bambu.Start`. `get_printer_status` rend `launchable` / `launch_blocker` et les erreurs décodées. Le défaut de l'adaptateur nu (`StartFromTerminal` faux) est inchangé ; le réglage par imprimante `allow_start_from_finish` reste lu mais n'est plus nécessaire. Tests : `TestCheckLaunchableRules`, `TestStartFromFailedResidualAfterCancel`, `TestStartFromFinish`, `TestStartRefusedFromFailedWithActiveHMS`, `TestStartFromFailedRefusedByDefault`, `TestStartFromFailedAfterCancelEndToEnd`, `TestConfirmationRefusedWhenHMSActive`, `TestConfirmationRefusedWhenPrinterBusy`. **À prouver sur la vraie P1S** : que la P1S accepte bien un `project_file` depuis FAILED, et que le reliquat y soit bien `0300400C`.
- **Options de démarrage dans la liaison approuvée (2026-11-08)** : `flow_cali`, `vibration_cali`, `timelapse` rejoignent `bed_leveling` dans `ConfirmationBinding` (`NoFlowCali`, `NoVibrationCali`, `Timelapse`, tous `omitempty`, exprimés par l'écart au défaut historique : l'empreinte des liaisons par défaut est **inchangée**, aucune migration). Elles sont affichées sur `/confirm` et dans le contenu structuré de la vue, lues sur l'impression liée (jamais sur un paramètre de `start_print`) et envoyées telles quelles ; en changer une exige une nouvelle confirmation. - **« Reprendre la photo » (2026-11-08)** : `POST /confirm/{id}/photo`, mêmes protections que `/confirm` (navigateur enregistré, nonce à usage unique lié à `photo:{id}`, garde cross-origin / `Sec-Fetch` de l'API) ; il ne fait que prendre une photo puis rediriger (303) : aucun effet sur l'approbation ni sur l'imprimante. Côté vue, `get_launch_view_state(fresh_photo)` reste en lecture seule.
- **Avertissement de décollement et annonce de capacité client (2026-11-08)** : informatifs. L'avertissement n'est jamais bloquant ni une condition d'approbation ; l'annonce `io.modelcontextprotocol/ui` du client sert à choisir le texte et à journaliser, jamais à autoriser ou refuser.

## 13. Passkeys (WebAuthn) : approuver sans code — 2026-11-08

**Besoin** : une approbation que ni un modèle, ni un code divulgué, ni un site tiers ne peut produire, sans rien taper. **Ajout, pas remplacement** : le bouton de `/confirm` et `/stop`, le code de lancement (§ 12) et le lien navigateur restent disponibles tant que l'humain n'a pas activé « exiger une passkey » (désactivé par défaut). Une installation sans passkey se comporte exactement comme avant (page, CSP et outils inchangés ; test `TestPasskeyDefaultsLeaveEverythingUnchanged`).

**Bibliothèque** : `github.com/go-webauthn/webauthn` v0.18.2 (maintenue ; vérifie signature, RP ID, origine, drapeaux UP/UV/BE/BS ; ES256, EdDSA, RS256…). **Licences** : go-webauthn et `go-webauthn/x` BSD-3-Clause ; dépendances transitives `fxamacker/cbor`, `golang-jwt/jwt`, `go-viper/mapstructure`, `tinylib/msgp`, `x448/float16`, `philhofer/fwd` MIT ; `google/go-tpm` Apache-2.0 : toutes **compatibles AGPL-3.0** (permissives ; Apache-2.0 est compatible avec la v3). Les formats d'attestation TPM, SafetyNet et Android de la bibliothèque ne servent pas : l'enregistrement demande `attestation: none`.

**Enregistrement** (`/setup/passkeys`, `internal/humanauth/passkey_web.go`) : page humaine comme `/setup/launch-code` : `humanauth.Require` (cookie d'un navigateur enregistré ; sans cookie, GET → 303 `/enroll`, POST → 403), `Sec-Fetch-Site: same-origin` + `Sec-Fetch-Mode: navigate`, nonce à usage unique lié à ce navigateur, HTTPS exigé comme les autres pages humaines (§ 2, 4bis). L'authentificateur doit **vérifier l'utilisateur** (UV) ; au plus 10 passkeys ; les passkeys existantes sont exclues (pas de doublon). Chaque enregistrement, révocation et changement de réglage est audité (`human.passkey_*`).

**Origines et RP ID** (`Passkeys.Env`) : dérivés de `BAMBU_PUBLIC_URL` (liste). Le RP ID est l'hôte de la première URL `https://` ; sont acceptées les URL `https://` dont l'hôte est ce RP ID ou un sous-domaine (plusieurs origines possibles, ports compris). **Refusé proprement** (message qui dit quoi faire) : `http` hors `localhost` (ex. le LAN `http://bambu.lan:7878`, listé ou non à côté d'un https), adresse IP (`127.0.0.1` compris : un RP ID est un nom), origine non déclarée, `localhost` quand un RP https est configuré. Sans URL publique https : RP ID = hôte de la requête (https derrière un proxy de confiance, ou `localhost`). Une passkey n'est proposée que sous le RP ID qui l'a créée.

**Script** : aucun JavaScript en ligne. Un script statique de même origine, `GET /setup/passkeys/passkey.js` (embarqué, une centaine de lignes, ne lit que `data-pk-options` et remplit deux champs cachés), est chargé par les seules pages qui portent une cérémonie ; leur CSP gagne **`script-src 'self'`** (rien d'autre : ni `unsafe-inline`, ni `connect-src`, ni origine tierce ; `default-src 'none'`, `form-action 'self'`, `frame-ancestors 'none'` inchangés). Le résultat revient par un **formulaire classique** (`form.submit()`, navigation de même origine) : les protections du § 2 s'appliquent sans exception (cookie, `Sec-Fetch-*`, nonce, garde Host / cross-origin). Aucune route `/api` ni outil MCP n'approuve par passkey (test `TestPasskeyPagesNeedAnEnrolledBrowser`).

**Approbation** (`Service.ApproveWithPasskey` / `StopWithPasskey`, `Passkeys.BeginApproval` / `FinishApproval`) :
1. À l'ouverture de `/confirm/{id}` ou `/stop/{id}`, le serveur émet un **challenge aléatoire de 256 bits** (consigne de la bibliothèque : jamais un challenge dérivé) et le garde **en mémoire** avec : l'objet approuvé (`print:{confirmation}` ou `stop:{demande}`), l'**empreinte de liaison** de la confirmation (imprimante, empreinte du fichier, plaque, matières, options : `BindingFingerprint`) ou l'identifiant du travail pour un arrêt, le **navigateur enregistré** (empreinte du cookie), le RP ID et l'origine. TTL 5 minutes, au plus 4 par objet et 256 au total.
2. À la soumission, le challenge est **consommé d'abord** (usage unique, même si la vérification échoue). Refus si : inconnu, périmé, déjà utilisé, émis pour un autre objet, une autre empreinte de liaison (la liaison a changé entre l'ouverture et la signature), un autre navigateur, une autre origine ou un autre RP ID.
3. Vérifications de la bibliothèque : signature sur `authData ‖ SHA-256(clientDataJSON)`, `type = webauthn.get`, challenge, origine exacte, hash du RP ID, **UP et UV obligatoires**, cohérence des drapeaux de sauvegarde. Le **compteur** doit progresser (`nouveau > ancien` dès qu'un des deux est non nul : les passkeys synchronisées qui envoient toujours 0 restent acceptées ; un clone ou un rejeu est refusé) et sa mise à jour est **comparée-et-échangée** en base (`WHERE sign_count = ancien`).
4. Seulement alors, **même chemin que l'existant** : `ApproveAndStart` (accord humain, `StartPrint`, `ConsumeConfirmation` atomique, **une seule commande**, jamais de renvoi) ; l'arrêt passe par `ExecuteStop`. L'attestation « plateau vide » reste obligatoire (case à cocher) en plus de la passkey. Audit : `print.passkey_accepted` / `print.passkey_refused` (raison, jamais de donnée du client).

**« Exiger une passkey »** (table `passkey_settings`, défaut 0) : activable sur `/setup/passkeys` ou par `bambud passkey --require=on` seulement si une passkey active existe ; la dernière passkey ne se révoque pas tant que c'est actif. Alors : `Approve` (point central) refuse tout canal autre que `passkey` ; `/confirm` et `/stop` n'affichent plus le bouton simple et leur POST sans passkey est refusé (403) ; `approve_print_with_code` / `approve_stop_with_code` répondent `problem: not_set` **avant** de toucher au compteur d'essais (le code n'est ni brûlé ni verrouillé) ; `get_launch_view_state` annonce `code_set: false` (la vue affiche le lien du navigateur, où se fait la passkey). Secours : `bambud passkey --require=off` (poste du service).

**Stockage** (migration additive `0270_passkeys.sql`, tables `passkeys` et `passkey_settings`) : identifiant public du credential, **clé publique** COSE, compteur, drapeaux, RP ID, dates, nom. **Aucun secret** : la clé privée ne quitte jamais l'authentificateur ; lire la base ne permet pas d'approuver.

**Ce que cela apporte** : contrairement au code (§ 12), il n'y a **rien à divulguer, taper ou deviner** ; le modèle n'a ni cookie, ni authentificateur, ni moyen de produire une signature ; une page tierce ne peut pas obtenir de signature valable (l'origine est dans la signature) : une page qui imiterait bambud sur un autre domaine n'obtient rien pour ce RP ID.

**Limites assumées / non prouvé**
- Éprouvé avec un **authentificateur virtuel** (clés ES256 et EdDSA de test, `internal/humanauth/passkeytest`), de l'enregistrement à l'approbation, sur les vraies pages et un simulateur d'imprimante. **Non éprouvé avec de vrais navigateurs** (Chrome, Safari, Firefox, Edge), de vrais authentificateurs (Touch ID, Windows Hello, clés FIDO2, gestionnaires de mots de passe) ni le script `passkey.js` dans un navigateur réel (pas de moteur JavaScript dans les tests Go).
- Pas de preuve de **présence physique** au-delà de ce que l'authentificateur garantit (UV). Une passkey **synchronisée** (iCloud, Google, 1Password) suit le compte de son fournisseur : plus pratique, pas aussi fort qu'une clé matérielle (la page l'indique « synchronisée »).
- Un processus local avec les droits de l'utilisateur reste hors périmètre (§ 1) : il lit la base (clés publiques seulement) mais ne peut pas signer.
- Les challenges en attente sont en mémoire : un redémarrage les invalide (recharger la page).
- La vue MCP App ne fait pas de passkey (le bac à sable de l'hôte n'est pas garanti) : elle renvoie vers la page du navigateur.
- Une passkey est liée à un RP ID : changer le nom du site (`BAMBU_PUBLIC_URL`) exige de les enregistrer à nouveau.

## 14. Agent local v2 (`/agent/v2`) : imprimante « via agent » — 2026-11-08

Détail du protocole et activation : `docs/AGENT-V2.md`. Brique de la cible SaaS (serveur cloud + agent local) ; **le transport direct reste le défaut et n'est pas modifié**.

**Ce qui change dans le modèle de menace (imprimante en `link=agent` seulement)**
- Le **code d'accès LAN n'existe que dans l'agent** (fichier `--access-code-file` lu au démarrage). Le serveur ne le reçoit, ne le stocke et ne le journalise jamais : en mode agent il n'y a ni saisie sur `/setup/printer/{id}`, ni certificat à épingler côté serveur (l'empreinte du certificat de l'imprimante est épinglée par l'agent, `--pin-sha256`, obligatoire). `TestAgentLinkEndToEndThroughBambud` cherche le code dans le dossier de données, les journaux, l'audit et les réponses d'outils après une impression complète.
- Toutes les connexions de l'agent sont **sortantes** (long-poll `GET /agent/v2/orders/next`, télémétrie, résultats, tirage des fichiers). Aucun port n'est ouvert chez l'utilisateur.
- **Un lancement ne part que sur une autorisation signée** : Ed25519, clé du serveur **épinglée par l'agent à l'appairage** (comparée hors bande avec `--server-key-id`), liée à **agent + imprimante + empreinte SHA-256 du fichier + plateau + affectation des matières + options de démarrage + « plateau vide » attesté**, **valable 2 minutes** (une fenêtre déclarée plus longue que 2 min 30 est refusée même signée), **nonce à usage unique** de 128 bits. Le serveur ne signe qu'après la même chaîne qu'en direct (preuve de confirmation vérifiée, état frais et lançable, confirmation humaine consommée) ; la signature n'est que le transport de cette décision, pas une décision nouvelle.
- **L'agent ne fait pas confiance au serveur pour la suite** et revérifie tout : signature, fraîcheur (tolérance d'horloge 30 s), cible (agent et imprimante), nonce **inscrit sur disque avant la commande** (survit à un redémarrage : un rejeu est impossible), fichier **déposé par cet agent lui-même** (registre des dépôts), et **empreinte SHA-256 du fichier présent sur l'imprimante relue en FTPS** juste avant l'envoi. Puis les garde-fous de l'adaptateur (état frais, pas d'alerte HMS ni d'erreur en cours, une seule commande) s'appliquent à l'identique.
- **Jamais de renvoi** : l'agent envoie la commande **une seule fois** ; le serveur ne rejoue jamais un ordre de lancement remis. Si l'issue est indéterminée (délai, perte de l'agent), `START_UNKNOWN` et seule une **réconciliation par lecture d'état** (ordre `reconcile`, qui n'émet jamais de lancement) peut conclure. Un ordre jamais remis à l'agent est retiré et signalé comme **non envoyé** (rien n'a pu partir).
- **Kill-switch local** : l'agent peut être mis en **lecture seule** (`--read-only`, ou fichier `READ_ONLY` dans son dossier d'état, relu à chaque ordre : `touch` / `rm`, sans redémarrage). Il refuse alors tout lancement, tout dépôt de fichier et toute reprise ; l'arrêt et la pause restent permis (gestes de sécurité). Aucun ordre du serveur ne peut le lever ; l'agent annonce son mode en télémétrie et le serveur refuse **avant** de consommer la confirmation.
- Clé de signature du serveur : `data/secrets/agent-v2-ed25519.key` (0600, créée au premier usage, jamais avant). Elle ne quitte pas le serveur ; seule la clé publique est remise aux agents.
- Appairage : **le mécanisme existant** (jeton à usage unique `bambud agent pair` ou `/agents/pair`, secret d'agent haché côté serveur, comparaison en temps constant, révocation). Le journal `agent_v2_authz` (migration 0260) garde une ligne par autorisation émise et son résultat ; l'audit enregistre chaque émission.

**Tests** (`internal/agentv2/e2e_test.go`, `internal/printing/agentlink_e2e_test.go`, contre le simulateur d'imprimante) : lancement signé accepté une fois ; rejeu refusé (même nonce, après fin d'impression) ; autorisation périmée et fenêtre trop longue refusées ; empreinte différente (fichier altéré sur l'imprimante, empreinte jamais déposée) refusée ; signature d'une autre clé, charge utile modifiée, autre imprimante, autre agent, plateau non attesté refusés ; mode lecture seule refuse lancement, dépôt et reprise ; `START_UNKNOWN` sans renvoi ; ordre non remis retiré ; chaîne complète bambud (MCP, confirmation humaine, registre réel) ↔ agent ↔ simulateur ; défaut direct sans clé ni dossier créés.

**Risques résiduels (assumés)**
- **Serveur compromis** : il peut signer des autorisations valides. Ce qui le borne : l'agent n'exécute que des fichiers **qu'il a déposés** (mais le serveur en choisit le contenu), pour des plateaux et matières que le serveur choisit aussi ; l'attestation « plateau vide » est portée par la signature mais **non vérifiable par l'agent** (comme en direct). Le kill-switch local est le recours. **La signature protège contre un canal détourné ou un agent mal adressé, pas contre un serveur malveillant.** À durcir pour le SaaS multi-clients : confirmation humaine signée de bout en bout (clé de l'humain, pas du serveur).
- **Pas de rotation de clé de serveur** ni de liste de révocation : changer la clé exige de réappairer les agents.
- **Horloge** : l'agent compare l'autorisation à SA propre horloge (tolérance 30 s) ; un agent à l'heure fausse refuse (sûr) ou, s'il est en avance, raccourcit la fenêtre. Pas de NTP imposé.
- **Secret d'agent** stocké en clair dans `link.json` (droits 0600, pas de DPAPI côté `printer-link`) ; HTTP clair signalé comme en v1 ; épinglage TLS du serveur par `--server-fingerprint`.
- **Caméra** : instantanés seulement (le flux vidéo continu n'est pas relayé) ; surveillance périodique en mode agent non traitée.
- **Route `PUT /api/printers/{id}/link`** : sous la garde HTTP de l'API (jeton d'API, hôte autorisé) comme `POST /api/printers`, mais **sans passage par un navigateur enregistré**. Elle ne lance rien : elle redirige seulement les ordres de cette imprimante vers un agent appairé (révocable) ; un lancement exige toujours la confirmation humaine.
- Non éprouvé sur un Raspberry Pi ni une vraie imprimante (simulateur seulement).
## 15. Reprise après incident : réconciliation, arrêt vérifié, reprise, chargement, nettoyage — 2026-11-08

Retours d'une soirée réelle sur P1S. **Aucun pouvoir nouveau pour le modèle** : lancer, arrêter, reprendre, charger la bobine externe et supprimer des fichiers exigent tous la validation d'un **humain** (page enregistrée ou code de lancement dans la vue), une seule commande, jamais de renvoi automatique.

- **Réconciliation à chaque rapport (`internal/printing/watch.go`).** Une impression `PRINTING` passe seule en `FAILED` (cause décodée, événement horodaté) quand l'imprimante revient en `IDLE` après avoir été active (délai de grâce 8 s, aucun délai après une coupure de liaison : redémarrage), ne désigne plus ce fichier (30 s), rapporte `FAILED`, ou `FINISH` (-> `COMPLETED`). Aucune commande n'est envoyée : seul l'état **serveur** est corrigé. Une imprimante injoignable plus de 3 min ne change pas l'état (elle peut continuer) mais déclenche une alerte. Défaut corrigé : l'ancien suivi ne concluait que sur FINISH/FAILED du même fichier.
- **Alertes sans changement d'état** (`get_print_status.alert`, événements `attention` / `stalled` / `printer_unreachable`, notification `print_attention`, abonnement `OnAlert`) : pause sur erreur (« attend une action à l'écran : <HMS décodé> »), progression figée (couche, % et temps restant inchangés 5 min), consignes incohérentes (plateau à 0 °C en pleine impression, hors fin d'impression). Un détecteur d'incohérence peut se tromper (une matière sans chauffe du plateau) : c'est une **alerte**, jamais une action.
- **Arrêt validé tracé et vérifié (`stop.go`).** Événements `stop_requested`, `stop_approved` (avec le canal), `stop_sent`, `stop_acked`, `stop_verified` / `stop_not_applied`, puis `cancel`. Si l'imprimante acquitte mais garde `gcode_state=RUNNING` : l'effet est vérifié (consignes buse et plateau à 0, plus aucun mouvement) ; constaté -> `CANCELLED` + consigne de redémarrage (alerte `stop_not_applied`) ; non constaté -> l'impression reste `PRINTING`, l'arrêt est dit **non appliqué** (rien n'est renvoyé, l'humain peut revalider).
- **`reprint_uploaded`** : crée une **nouvelle** impression (l'échec reste dans l'historique) et sa confirmation pour un fichier **déjà déposé**, après avoir relu la carte par FTPS (présence, taille et **sha256 recalculé**, `quick` : présence et taille). Refus précis si le fichier a disparu ou changé, ou si l'imprimante n'est pas lançable (HMS actif, occupée). L'approbation humaine habituelle (`/confirm`, plateau vide) reste requise. Une impression restée `PRINTING` alors que l'imprimante est arrêtée est d'abord réconciliée.
- **`resume_print`, `load_filament`, `cleanup_printer_files`** : l'outil crée une demande (`action_id`, `action_url` = `/action/{id}`, 10 min, usage unique, **consommée avant l'envoi**) ; l'humain valide sur la page (cookie de navigateur enregistré, nonce, garde cross-origin comme `/stop`) **ou** avec son code de lancement via l'outil réservé à la vue `validate_action_with_code` (mêmes garanties que § 12 : verrou global après 3 échecs, code masqué des erreurs). Il n'y a **pas encore de carte dans la conversation** pour ces actions : Claude donne le lien. Tests : `TestPauseOnFilamentErrorLoadAndResume` (le modèle n'envoie rien ; mauvais code refusé ; demande non rejouable), `TestListAndCleanupPrinterFiles`.
- **Nettoyage de la carte SD.** `list_printer_files` (lecture seule). Seuls les fichiers au nom `<radical>-<sha12>.(gcode.)3mf` (déposés par bambud) peuvent être supprimés, jamais un fichier lié à une impression en cours ou en attente de lancement (revérifié au moment de supprimer), jamais la version la plus récente d'un modèle ; la page d'action montre la **liste exacte**, le résultat dit ce qui a été supprimé ; l'audit garde la liste (`printer.cleanup_requested` / `printer.cleanup_done`). Les NOUVEAUX dépôts ont un nom parlant (`porte_guitare_supports_v3-<sha12>.gcode.3mf`) ; les existants ne sont pas renommés.
- **`diagnose_connection`** : lecture seule ; ne sonde que l'hôte enregistré de l'imprimante (DNS, TCP sur 8883, 990, 6000, entrée ARP) ; n'envoie rien, ne lit aucun secret. La reconnexion MQTT est à délai croissant (2 s à 60 s) avec reprise dès qu'un port répond ; aucune commande n'est rejouée à la reconnexion.
- **Codes HMS** (`internal/printer/hms.go`) : table **écrite sans pouvoir la relire sur le wiki** (HTTP 402 depuis l'environnement de développement) ; chaque entrée est marquée `unverified` avec sa `source` (terrain ou mémoire). Le format du lien `https://wiki.bambulab.com/en/x1/troubleshooting/hmscode/<code>` n'est **pas vérifié**. Un code absent n'est jamais deviné.

- **Passkeys (§ 13).** `/action/{id}` propose le même parcours que `/stop/{id}` : formulaire passkey lié à la demande précise (sujet `action`), bouton simple et code de lancement **refusés** quand « exiger une passkey » est actif (le code est refusé avant tout essai : aucune tentative brûlée, `validate_action_with_code` répond `not_set`). Test : `TestPasskeyRequiredAppliesToActions`.
- **Agent local v2 (§ 14).** Reprise, arrêt, état et lancement passent par l'adaptateur commun et fonctionnent en mode agent (leur fiabilité sur l'agent n'est pas prouvée ici : l'agent peut ne pas rendre `ErrStateNotObserved`, alors l'arrêt est journalisé mais non vérifié par les chauffes). `list_printer_files`, `cleanup_printer_files`, `load_filament`, `reprint_uploaded` (vérification du fichier) et `diagnose_connection` **refusent avec un message clair** en mode agent : le serveur n'a ni accès au réseau de l'imprimante ni son code d'accès. Test : `TestRecoveryFunctionsRefuseCleanlyInAgentMode`.

**Limites / à prouver sur la vraie P1S** : la commande `ams_change_filament` (cible 254) du chargement de la bobine externe et sa réponse ; le comportement exact de `gcode_state` après `stop` ; qu'une P1S abandonnant en préparation repasse bien en `IDLE` sans `FAILED` ; le texte exact des codes HMS ; la durée de relecture FTPS d'un gros fichier (sha256).

## 16. Mises à jour automatiques du serveur : risque « supply-chain » — 2026-11-09

Mécanisme et exploitation : `docs/DEPLOY-LINUX.md` § 11. **Désactivé par défaut**. Ce paragraphe dit ce qu'il ajoute à la surface d'attaque et ce qu'il faut faire côté GitHub.

**Ce qui change dans le modèle de menace.** Activer l'automatique revient à dire : *tout commit de `main` dont la CI est verte sera exécuté sur le serveur, avec l'accès aux données, aux secrets d'imprimante et à l'imprimante.* La confiance est donc déplacée du serveur vers **le dépôt GitHub et son compte propriétaire** : qui peut pousser sur `main` (ou modifier le workflow de CI pour qu'il passe au vert) peut exécuter du code sur le serveur. Le modèle (Claude) n'est pas concerné : aucun outil MCP n'est ajouté ni modifié, aucune approbation de lancement ou d'arrêt n'est touchée, et un commit installé ne peut toujours pas lancer ou arrêter une impression sans la validation humaine (c'est le code **de ce dépôt** qui garantit cela : un commit malveillant le supprimerait).

**Ce que fait le mécanisme pour limiter le risque**
- **Le serveur tire, rien n'entre.** Aucun port, aucun webhook, aucune clé de déploiement, aucun accès SSH donné à GitHub. Compatible Tailscale sans IP publique.
- **Seuls les commits de `origin/main` avec CI verte.** Tous les contrôles du commit (check-runs et statuts) doivent être terminés et réussis ; rouge, annulé, en cours ou inconnu (réseau, limite de débit) : rien n'est installé. Option `ATELIER_UPDATE_REQUIRED_CHECKS` pour exiger des jobs précis par leur nom.
- **Historique non réécrit.** Le commit visé doit prolonger la version installée (`git merge-base --is-ancestor`). Un force-push sur `main` est **refusé et notifié** ; une version épinglée doit appartenir à `origin/main`.
- **Le code téléchargé ne s'exécute jamais avec les droits du service ni de root.** `git`, `npm ci` (scripts d'installation compris), `go build`, `go test`, le validateur : utilisateur système dédié `atelier-update`, environnement **vidé** (aucun `BAMBU_*`, aucun jeton), **sans accès** à `/var/lib/atelier` (0750 `atelier`) ni à `/etc/atelier` (0750 `root:atelier`). L'orchestrateur root n'exécute que l'outil installé **par l'administrateur** (`/opt/atelier/updater/bambud`, jamais remplacé automatiquement par la version construite) et des commandes système (`systemctl`, `chown`, bascule d'un lien) ; le test de fumée, qui est un script du dépôt, s'exécute sous `atelier`, pas en root ; les processus de `atelier-update` sont tués avant publication ; les binaires construits sont publiés `root:root` non modifiables. Limite honnête : une fois la nouvelle version *démarrée*, elle tourne en `atelier` avec ses accès normaux ; la construction isolée protège le serveur d'un `postinstall` npm, pas d'un commit malveillant du dépôt lui-même.
- **Jeton GitHub facultatif, en lecture seule** : aucun par défaut (API publique). S'il existe (limite de débit), fichier `/etc/atelier/github-token` en **0600** (refusé sinon), envoyé **uniquement** à l'API GitHub, jamais journalisé, jamais transmis aux commandes de construction. Il n'a besoin d'aucun droit d'écriture ni d'accès aux dépôts privés (le dépôt est public) : ne jamais y mettre un jeton à portée d'écriture.
- **Une version testée avant de toucher au service** (tests `-short`, validateur MCP), **sauvegarde vérifiée** avant la bascule, **retour arrière automatique** (avec restauration si le schéma a changé), **notification** de chaque installation, échec ou report. Un commit qui échoue n'est pas retenté en boucle.
- **Surface ajoutée dans bambud** : `GET /api/system/busy`, lecture seule, **réservée au serveur lui-même** (connexion TCP loopback directe **sans** en-tête de proxy : un client distant passant par `tailscale serve` ou un reverse proxy local est refusé) **et** protégée par le jeton d'API ; **absente de `/health`** (public) pour ne pas révéler l'activité d'impression. Sous-commandes `upgrade`, `upgrade-probe` (lecture seule de la base, sans migration), `upgrade-notify` (ouvre la base **sans migration**) : exécutées en local, non exposées par HTTP ni MCP.
- **Interrupteur immédiat** : `/etc/atelier/auto-update.disabled` ; **épingle** : `atelier-update --pin current`.

**À FAIRE sur GitHub (recommandé fortement, hors du code)** : *Settings → Branches → Branch protection rule (ou Ruleset) sur `main`* :
1. **Require a pull request before merging** avec au moins une approbation (relecture) ;
2. **Require status checks to pass** : exiger les jobs de `.github/workflows/ci.yml` (`Go (vet + tests)`, `Worker géométrie (pytest + CadQuery)`, `Web (build + vitest)`, `Conformité MCP (validateur du SDK TypeScript)`, `Image Docker (sans pousser)`, `Scripts de déploiement (harnais Linux)`) et « Require branches to be up to date » ;
3. **Block force pushes** et **Restrict deletions** (le mécanisme refuse déjà un historique réécrit, mais la règle l'empêche à la source) ;
4. **Do not allow bypassing the above settings** (y compris pour les administrateurs) ;
5. **Un `CODEOWNERS` sur `.github/workflows/` et `deploy/`** exigeant la revue du propriétaire : sinon un commit qui affaiblit la CI s'auto-valide ;
6. 2FA (clé de sécurité / passkey) sur le compte propriétaire, *Require signed commits* si vous signez vos commits (le mécanisme ne vérifie pas encore les signatures) ;
7. Dans *Settings → Actions → General* : n'exiger l'approbation que des workflows de contributeurs externes (« Require approval for all outside collaborators ») ; la CI actuelle ne demande que `contents: read`.

**Risques résiduels (assumés)**
- **Compromission du compte GitHub propriétaire** (ou d'un contributeur avec droit d'écriture sur `main` sans protection de branche) : exécution de code sur le serveur dès le prochain passage, CI verte comprise (le workflow vit dans le dépôt). Sans protection de branche ni relecture obligatoire, l'automatique n'ajoute **aucune** barrière contre un compte compromis. Recours : `sudo touch /etc/atelier/auto-update.disabled`, ou n'activer l'automatique que sur une branche protégée, ou épingler (`--pin`).
- **Dépendances** (`go.sum`, `package-lock.json`) : verrouillées et reconstruites à l'identique (`npm ci`, modules Go vérifiés par `go.sum`), mais un paquet compromis déjà dans un commit vert serait installé ; le build isolé protège les secrets, pas l'intégrité du binaire produit.
- **Worker CAO** : la mise à jour exécute `uv sync` / `uv run` sous l'utilisateur du service avec l'environnement `UV_*` lu dans la configuration du service (aucun secret transmis : seules les variables `UV_*` sont reprises) ; sa version est contrôlée par l'empreinte du code (§ docs/DEPLOY-LINUX.md 11.11). Les commandes lancées sous un autre utilisateur partent de `/`.
- **Pas de vérification de signature** des commits ni d'attestation de build.
- **Mise à jour pendant une impression (autorisée par défaut, 2026-11-09)** : `ATELIER_UPDATE_ALLOW_DURING_PRINT=1` laisse passer une impression en cours (`print_running`) et une imprimante au travail (`printer_active`) : redémarrer `bambud` n'interrompt pas l'impression (fichier sur la carte SD) et **aucune commande** n'est envoyée à l'imprimante au redémarrage (`Recover` ne fait que reprendre le suivi, test `TestRestartDuringPrintKeepsTrackingWithoutCommands`). Restent bloquants : dépôt FTPS / découpe, confirmation, arrêt ou action en attente de l'humain (10 min au plus), lancement en cours d'accusé (`START_REQUESTED`, `START_UNKNOWN`), travail lourd. Désactivable (`=0`). Surface inchangée : l'outil de mise à jour n'a aucun pouvoir sur le lancement ni l'arrêt ; le seul risque ajouté est une perte de suivi de quelques secondes pendant le redémarrage.
- **Fenêtre de redémarrage** : une impression lancée entre la dernière vérification d'occupation et le redémarrage n'est pas retenue ; `START_UNKNOWN` bloque l'installation tant que l'humain n'a pas tranché (voir DEPLOY-LINUX § 11.10).
- **Dépôt public** : la CI est lisible par tous ; l'API GitHub non authentifiée est limitée en débit (le mécanisme attend alors, il n'installe jamais « par défaut »).

## 17. Surface publique restreinte (`--public-listen`) — 2026-11-09

Détail et procédure : `docs/OAUTH.md` § 3 bis. Spécification : `docs/specs/G1-connecteur-distant.md` F1, F2.

- **Second écouteur, liste blanche exacte** : `/mcp`, métadonnées OAuth, `/oauth/register|authorize|token|consent/{id}`, `/health` réduit, `/about`, `/privacy`, `/icon.svg`, `/robots.txt`. Tout le reste (`/confirm`, `/stop`, `/action`, `/setup/*`, `/enroll`, `/agents`, `/api/*`, `/agent/v1|v2`, SPA) répond **404**, avec ou sans Bearer ; le filtre précède le garde. Le Funnel ou le reverse proxy ne doit pointer que sur cet écouteur. L'écouteur principal est inchangé ; sans `--public-listen`, rien ne change.
- **Jeton obligatoire** dès que `--public-listen` est défini (`ValidateServe`). Mêmes gardes que l'écouteur principal (Host, Origin, jeton, `TrustedProxies`). Le jeton OAuth reste limité à `/mcp` ; un jeton émis pour l'adresse publique ne vaut pas sur l'adresse privée (liaison à la ressource, RFC 8707).
- **Consentement** : le cookie du navigateur enregistré (hôte, pas de port) posé via l'écouteur principal est accepté par l'écouteur public ; un navigateur non enregistré reçoit une page d'explication (403), pas de redirection vers `/enroll`. Les liens remis au modèle (`/confirm`, `/stop`, `/action`) restent sur l'adresse privée.
- **Limites de débit** par adresse sur l'écouteur public : enregistrement (heure), jeton (minute), `/mcp` sans jeton valide (minute) ; 429 + `Retry-After` ; en plus des limites existantes de `internal/oauth`. Si le proxy ne transmet pas l'adresse réelle du client, les plafonds sont partagés (déni de service possible des échanges de jetons : relever les limites).
- **Diagnostic** : `bambud doctor connector` (jamais le jeton en sortie ; pas de suivi des redirections ; http refusé hors boucle locale).
- Tests : `internal/httpapi/public_test.go`, `cmd/bambud/doctor_test.go`, `cmd/bambud/publiclisten_test.go`.
