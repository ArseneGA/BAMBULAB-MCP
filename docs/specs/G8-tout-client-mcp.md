# G8 — Compatible tout client MCP et interface web autonome

Spec pour un agent de code. Lire d'abord `docs/specs/README.md` § 2 (règles communes), `docs/research/mcp-apps.md` (en entier), `docs/OAUTH.md`, `docs/UTILISATION.md` § 7 (l'interface web), `docs/strategie/ETUDE-MARCHE.md` § 9 risques n°4 et 7. Module Go `github.com/ArseneGA/BAMBULAB-MCP`, Go ≥ 1.26, SQLite pur Go, `CGO_ENABLED=0`.

## 1. Objectif et valeur

Réduire la **dépendance à Claude** (risque n°4 de l'étude de marché) et élargir le marché : Printalk doit fonctionner avec **n'importe quel client MCP** (ChatGPT, Gemini et ses outils en ligne de commande, clients open source, MCP Inspector) et offrir une **interface web autonome** qui couvre les parcours essentiels **sans aucun assistant** (importer, analyser, préparer, découper, comparer, déposer, confirmer, suivre, chiffrer). Le produit ne paie aucun modèle de langage : l'utilisateur apporte le sien, ou aucun.
Segment : tous (utilisateurs d'autres assistants IA, utilisateurs qui préfèrent l'écran, institutions qui refusent un assistant donné).

## 2. Périmètre / hors périmètre

Dans le périmètre : audit et **tests automatisés de compatibilité** avec le client officiel MCP (TypeScript et Go) et l'inspecteur officiel ; contrôle de la **compatibilité des schémas d'outils** avec les contraintes connues de plusieurs clients (liste à **vérifier** pour chaque client) ; **profils d'outils** (`full` par défaut, `core` réduit) pour les clients limités en nombre d'outils ; **textes de résultat** utilisables sans vue ni image ; redirections OAuth documentées pour d'autres clients (configurables, jamais ajoutées par défaut) ; **matrice de compatibilité** honnête (testé / non testé) ; **couverture web des parcours essentiels** et son test de bout en bout ; documentation `docs/CLIENTS-MCP.md`.
Hors périmètre : héberger ou payer un modèle de langage ; assistant conversationnel intégré à l'interface web (décision séparée, voir § 10) ; widgets propres à un autre éditeur (cartes d'approbation dans ChatGPT, `openai/outputTemplate`, etc. : **non retenus** car l'approbation doit rester humaine hors de la conversation) ; changement des outils, de leurs noms ou de leurs comportements ; test sur des abonnements payants de tiers sans accord de l'utilisateur (l'agent de code ne crée aucun compte, voir règles d'accès).

## 3. État actuel dans le code

- **Serveur MCP** : `internal/mcpserver` (une centaine d'outils enregistrés par `addTool` dans les fichiers `*_tools.go` + vues ; l'agent doit **compter précisément** via `tools/list`), SDK officiel `github.com/modelcontextprotocol/go-sdk v1.8.0`, transports **Streamable HTTP** sur `/mcp` (`internal/httpapi/httpapi.go`) et **stdio** via le pont `cmd/bambu-mcp` (relais vers `bambud`, `--api-token-file`).
- **Conformité** : `internal/mcpserver/spec_conformance_test.go` (noms `^[a-zA-Z0-9_-]{1,64}$`, `inputSchema.type == "object"`, `outputSchema.type == "object"`, descriptions non vides, `structuredContent` objet). `scripts/mcp-sdk-validate/validate.mjs` valide `tools/list` avec `ListToolsResultSchema` du **SDK TypeScript officiel** contre un `bambud` lancé (usage documenté en tête du fichier) : c'est le contrôle qui protège Claude Desktop.
- **Détection du client** : `internal/mcpserver/clientcaps.go` (`clientViewSupport` : lit `capabilities.extensions["io.modelcontextprotocol/ui"]` et le nom du client dans `initialize` ; adapte seulement le **texte** des résultats, jamais la sécurité) ; `get_capabilities` / `GET /api/capabilities` (`internal/contracts/capabilities.go`).
- **Sans vue** : les résultats portent déjà du texte, des images (PNG/GIF) et du `structuredContent` ; les vues MCP App sont un bonus (`docs/research/mcp-apps.md` § 9 : « tout fonctionne SANS vue »). Les liens de confirmation/arrêt (`/confirm`, `/stop`) sont des pages web humaines, indépendantes du client.
- **Authentification** : Bearer statique (`BAMBU_API_TOKEN`), OAuth 2.1 intégré avec DCR (`internal/oauth`, `internal/httpapi/oauth.go`) ; redirections acceptées = callbacks de Claude + boucle locale + `--oauth-redirects` / `BAMBU_OAUTH_REDIRECTS` (`cmd/bambud/main.go`, `httpapi.Options.OAuthRedirects`) ; limites connues (`docs/OAUTH.md` § 4) : les clients navigateur (MCP Inspector) envoient `Origin` et sont refusés sur `POST /oauth/*` sauf `TrustedOrigins`.
- **Interface web** : `web/src` (React/Vite, embarquée), pages `Library.tsx`, `Model.tsx`, `Prepare.tsx` (+ `PrepareParts.tsx`, `PrepareNav.tsx`, `PlatePanel.tsx`), `Compare.tsx`, `Print.tsx`, `Printers.tsx`, `Filament.tsx`, `Insights*.tsx`, `Gabarits.tsx`, `Materials.tsx`, `Settings.tsx`, `Trash.tsx`, `UploadLauncher.tsx`, `ImportDialog.tsx`, `ExportDialog.tsx`, `CameraPanel.tsx`, `RecordResult.tsx`, `Agents.tsx`, `Design.tsx` ; routes `web/src/main.tsx`, menu `web/src/Shell.tsx` ; client API `web/src/api/*` ; style vert Printalk (`web/src/design/tokens.css`, `web/src/components/ui.tsx`).
- **Tests de parcours existants** : `web/scripts/e2e.mjs` (Playwright, vrai `bambud` : import → opérations avec aperçu → corbeille → restauration), `web/scripts/e2e-plates.mjs`, tests Go `internal/httpapi/webscreens_test.go`, `webfeatures_test.go`, `webauth_test.go`, `internal/printing/e2e_test.go`, `smoke.ps1`/`scripts/smoke-linux.sh` (bout en bout avec simulateur).
- **Routes HTTP** de toutes les fonctions (`internal/httpapi/*.go` : `/api/models…`, `/api/print-jobs…`, `/api/cost/…`, `/api/printers…`, etc.) : l'interface web ne passe **pas** par MCP.

Ce qui manque : preuve de compatibilité avec d'autres clients ; contrôle de schémas par client ; profil d'outils réduit ; matrice documentée ; inventaire **parcours web ↔ fonctions MCP** avec trous comblés ; test de bout en bout **sans MCP**.

## 4. Exigences fonctionnelles

**F1 — Banc de compatibilité client (automatisé, local).** Un script `scripts/client-compat/run.mjs` (Node, comme `scripts/mcp-sdk-validate`) et un test Go `internal/mcpserver/clients_compat_test.go` qui, contre un `bambud` éphémère (service de test + imprimante simulée), exécutent pour **chaque client disponible** : `initialize`, `tools/list` (validation de schéma), `tools/call` sur un petit jeu d'outils de lecture (`get_capabilities`, `list_printers`, `search_models` sur `seed-demo`, `estimate_cost` en plan saisi), `resources/list` et `resources/read` d'une vue, et — pour la sécurité — la tentative d'un appel qui **doit** être refusé (`start_print` sans confirmation). Clients couverts : (a) **SDK TypeScript officiel** (existant : `scripts/mcp-sdk-validate`, à intégrer), (b) **SDK Go officiel** (client du `go-sdk`, déjà utilisé par `connectClient` des tests), (c) **MCP Inspector officiel** en mode CLI (`npx @modelcontextprotocol/inspector --cli …`, version fixée, **à vérifier** pour les options exactes), (d) **client Python officiel `mcp`** (facultatif), (e) un client **OpenAI** *si* l'utilisateur fournit une clé d'API pour l'essai : le script ne la lit que depuis une variable d'environnement, ne la journalise jamais, ne tourne **pas** en CI et n'est **jamais** requis ; sans clé, la ligne de la matrice est « non testé ». Les dépendances Node vivent dans `scripts/client-compat/package.json` (comme `scripts/mcp-sdk-validate`), pas dans `web/`.
**F2 — Lint des schémas d'outils par profil de client.** Test Go `TestToolSchemasAreClientPortable` : pour chaque outil, examine `inputSchema`/`outputSchema` (tels qu'ils passent sur le fil) et signale, avec leur nom, les constructions connues pour poser problème à certains clients (liste **à vérifier** pour chacun avant de bloquer ; l'agent la complète depuis la documentation officielle de chaque client et cite URL + date dans `docs/CLIENTS-MCP.md`) : tableaux de types (`"type":["object","null"]`), absence de `type`, `$ref`/`$defs` récursifs, `oneOf/anyOf` imbriqués, `additionalProperties` non booléen, profondeur d'objet > 5, `enum` mixtes, description d'outil ou de paramètre > N caractères, noms de paramètres hors `[a-zA-Z0-9_.-]`, tableaux sans `items`. Chaque constat est classé **bloquant** (casse un client majeur documenté, déjà couvert par `spec_conformance_test.go` pour `type`) ou **avertissement** (listé dans la doc). Les **corrections** ne changent **ni noms ni comportements** : on aplatit un schéma seulement si la sémantique reste identique, avec test d'équivalence (mêmes entrées valides acceptées/refusées). Tout ce qui ne peut pas être corrigé sans changer le contrat est documenté comme limite connue.
**F3 — Profils d'outils (`full` par défaut, `core` optionnel).** Certains clients limitent le nombre d'outils ou paient au jeton la description de chaque outil (limites **à vérifier** : l'agent mesure le poids réel de `tools/list` en octets et en jetons approximatifs et le consigne). Ajouter un paramètre de connexion `?profile=core` sur l'URL `/mcp` (et l'indicateur `--tool-profile` / `BAMBU_TOOL_PROFILE` pour fixer le défaut du serveur, valeur par défaut **`full`** = comportement actuel). Le profil `core` n'expose qu'un sous-ensemble **explicite et testé** (≈ 30 à 40 outils : recherche/détails de modèle, import/upload, analyse, réparation, modification de géométrie, découpe, comparaison, coût, état d'imprimante, file de travaux, demande de confirmation et suivi d'impression, journal) défini dans un fichier de classification (`internal/mcpserver/profiles.go`, comme la politique de rôles de G6) ; **un test échoue si un outil n'est classé ni `core` ni `full-only`** (tout nouvel outil doit être classé). Le profil est choisi à l'`initialize` et ne change pas en cours de session ; appeler par son nom un outil hors profil renvoie une erreur claire (« outil hors du profil core : utiliser le profil full »). **Aucune règle de sécurité ne dépend du profil** : `start_print`/`approve_*` restent soumis aux mêmes contrôles. Ordre d'application avec G6 : **le filtrage par rôle d'abord, le profil ensuite**.
**F4 — Résultats utilisables partout.** Pour chaque outil qui renvoie une image ou une vue, le **texte** doit se suffire à lui-même (il le fait déjà pour la plupart : `docs/research/mcp-apps.md` § 9) ; ajouter un test qui, pour chaque outil à vue ou image du banc F1, vérifie que le `content[0].text` n'est pas vide et contient les informations clés (lien `/confirm` pour une confirmation, pourcentage pour une progression, dimensions pour un modèle). Quand `clientcaps` ne détecte **aucune** annonce de vue, le texte donne le lien web équivalent (comportement existant : le préserver et le tester pour un client « nu »). Aucun texte ne dépend d'un nom de client ; la détection de client (`client` dans `clientViewSupport`) ne sert qu'à la **journalisation** (`client MCP initialisé …`) et à adapter le texte quand la vue manque, jamais au contrôle d'accès.
**F5 — Authentification pour d'autres clients.** Documenter et tester : (a) Bearer statique (valable pour tout client qui sait envoyer un en-tête `Authorization`, y compris Claude Code, les SDK, l'inspecteur en CLI) ; (b) OAuth/DCR pour les clients qui le gèrent. **Redirections** d'autres éditeurs (par exemple celles de ChatGPT : adresses **à vérifier** sur la documentation d'OpenAI) : **non ajoutées par défaut** ; `docs/CLIENTS-MCP.md` explique comment les ajouter explicitement via `BAMBU_OAUTH_REDIRECTS` (liste blanche exacte), avec l'avertissement que l'URL doit être **publique en https** (voir G1). Test : une redirection ajoutée par configuration est acceptée, une non listée est refusée (comportement existant, test d'extension). Pour les clients **navigateur** (Inspector web), documenter `TrustedOrigins` (existant) ; ne pas relâcher la protection d'origine par défaut.
**F6 — Interface web : inventaire des parcours et comblement des trous.** Livrer `docs/PARCOURS-WEB.md` : tableau « parcours essentiel × écran web × route d'API × outil MCP équivalent × état (complet/partiel/absent) » pour au moins ces parcours : (1) **importer** des fichiers (glisser-déposer, dossier, lien) ; (2) **ranger et retrouver** (collections, étiquettes, recherche, corbeille) ; (3) **analyser et réparer** un maillage (rapport de fabricabilité, réparation) ; (4) **préparer** (imprimante, matière, objectifs, variantes, plusieurs pièces sur un plateau) ; (5) **découper et comparer** ; (6) **valider et déposer** le fichier ; (7) **confirmer et lancer** (page `/confirm`) et **arrêter** (`/stop`) ; (8) **suivre** (état, caméra, progression, notifications) ; (9) **bobines/AMS/file** ; (10) **coût et journal** ; (11) **imprimantes** (ajout, état) ; (12) **export** de projet ; (13) **réglages** (prix, notifications). Pour chaque trou **partiel ou absent**, soit le combler dans ce chantier si la route d'API existe déjà (écran manquant) et que c'est petit (≤ 1 jour), soit le lister dans la section « reste à faire » avec taille. **Ne pas** inventer de route : si la fonction n'existe qu'en outil MCP, créer d'abord la route HTTP équivalente **en réutilisant le même service** (aucune logique dupliquée) avec ses tests ; l'agent liste précisément ce qui a été ajouté.
**F7 — Aide intégrée à l'interface sans assistant.** Sur chaque écran du parcours, un court texte « Que faire ensuite ? » (états vides et état courant → prochaine action, avec lien) pour que l'utilisateur sans assistant sache avancer ; la page d'accueil (`Home.tsx`) affiche l'état de préparation (« 3 modèles, 1 impression prête à confirmer ») et un guide des parcours. Textes en français, vert Printalk, composants `ui.tsx`. **Aucun** texte ne suppose Claude.
**F8 — Test de bout en bout SANS MCP.** (a) Go : `internal/httpapi/journey_nomcp_test.go` exécute **uniquement via HTTP** (`/api/*` et pages humaines) le parcours : import d'un STL de démonstration → analyse → préparation d'une impression pour l'imprimante simulée → découpe (slicer factice) → validation → dépôt dans le simulateur → création de la confirmation → **approbation par la page `/confirm` avec un cookie de navigateur enregistré** → suivi jusqu'à la fin dans le simulateur → fiche de journal et coût. Aucun appel MCP. (b) Web : étendre `web/scripts/e2e.mjs` ou ajouter `web/scripts/e2e-journey.mjs` (Playwright déjà en dépendance de développement) pour dérouler le même parcours **dans l'interface**, contre un vrai `bambud` + `printer-sim` ; non requis en CI par défaut (comme `e2e.mjs` aujourd'hui), exécutable par `scripts/smoke.ps1`/`smoke-linux.sh` en option. (c) Vitest : tests de composants pour chaque nouvel écran/état.
**F9 — Documentation `docs/CLIENTS-MCP.md`.** Pour chaque client : comment connecter (URL, en-tête, OAuth), profil recommandé, ce qui marche, ce qui ne marche pas (vues, images), version testée et date, **et un champ « statut » honnête** (`testé <date> avec <version>` | `non testé`). Matrice « client × fonctions » : connexion, `tools/list`, appels de lecture, appels d'écriture, images, vues, OAuth, suivi long (`wait_for_job`), confirmation d'impression (lien web). Clients nommés dans le dossier (statut initial **non testé** sauf ceux couverts par F1) : ChatGPT (connecteurs/mode développeur), API Responses d'OpenAI avec outil MCP distant, Gemini (CLI et SDK), Claude (Desktop, claude.ai, mobile, Code), clients open source. Chaque ligne **« non testé »** est une **question honnête**, pas une promesse. Les exigences particulières d'un client (par exemple des outils nommés `search`/`fetch` pour certains connecteurs de recherche, **à vérifier**) sont listées comme **non implémentées** tant que non vérifiées ; ne pas ajouter d'outil pour s'y conformer sans décision de l'utilisateur.
**F10 — Pas de dépendance cachée à Claude.** Audit du dépôt : aucune fonction ne **requiert** un client Claude ; les textes d'outils ne s'adressent pas à « Claude » nommément (rechercher « Claude » dans `internal/mcpserver/*.go` hors commentaires et tests ; reformuler « Claude » en « l'assistant » dans les **textes rendus** quand ce n'est pas une instruction de sécurité spécifique, **sans changer** les phrases de sécurité testées par `TestNoMCPToolCanApproveAConfirmation` et les tests d'instructions ; chaque reformulation passe par les tests existants de texte). Les instructions du serveur (`mcpserver.New` → `Instructions`) restent identiques sur le fond.

Outils MCP : **aucun nouvel outil, aucun renommage**. Seule nouveauté de surface : paramètre d'URL `profile` et indicateur serveur (F3). Routes HTTP : seulement celles ajoutées pour combler un trou de F6 (à lister par l'agent).

## 5. Modèle de données

Aucune table ni migration. (Le profil d'outils est un paramètre de session ; la matrice de compatibilité est un fichier de documentation.) Si F6 oblige à une nouvelle route, elle s'appuie sur les tables existantes ; une migration éventuelle serait additive, numérotée à **dernier + 10** au moment du codage.

## 6. Sécurité et règles non négociables

- **Aucun assouplissement de l'approbation** pour un autre client : pas de carte d'approbation, pas de widget propriétaire, pas d'outil d'approbation ; l'approbation reste la page `/confirm` (ou la vue avec code de lancement) déclenchée par l'humain ; `TestNoMCPToolCanApproveAConfirmation` reste vert, **avec chaque client du banc** (le client tente l'approbation et échoue).
- **Secrets** : jetons et clés d'API (dont une éventuelle clé OpenAI de test) **uniquement** par variables d'environnement, jamais journalisés, jamais écrits dans les rapports ni la doc, jamais passés en argument de ligne de commande visible ; le script les masque.
- **Profil `core`** : ne change aucun contrôle d'accès ; un outil dangereux n'est jamais « sauvé » par son absence d'un profil (la sécurité est dans le service).
- **Redirections OAuth** : liste blanche exacte uniquement ; aucune redirection d'un autre éditeur par défaut ; pas de `*`.
- **Origine** : ne pas affaiblir la protection `Origin` pour accommoder l'Inspector web ; documenter `TrustedOrigins`.
- **Entrées** : les nouveaux contrôles de schéma ne modifient pas la validation des entrées des outils.
- Les tests ne contactent **aucun service tiers payant** ; les essais avec un client d'éditeur sont manuels/optionnels.
- Mesuré/calculé/estimé : la matrice distingue `testé` (preuve : version + date + sortie) de `non testé` ; jamais de « compatible » sans preuve.

## 7. Compatibilité production

- Sans paramètre, **tout est identique** : profil `full`, mêmes outils, mêmes noms, mêmes schémas (sauf aplatissements de F2, **testés équivalents**), mêmes textes (sauf reformulations de F10 passant les tests). Claude Desktop via `mcp-remote`, le pont `bambu-mcp`, Claude Code, l'OAuth de Claude : inchangés.
- `tools/list` conforme (`spec_conformance_test.go`, `scripts/mcp-sdk-validate`) avec les **deux profils**.
- Aucune migration ; aucun changement de défaut ; aucune dépendance Go ajoutée (les dépendances Node du banc sont isolées dans `scripts/client-compat`, hors binaire).
- Le paramètre `?profile=` inconnu est **ignoré avec un avertissement** dans le journal (ne casse pas une connexion) et retombe sur `full`.
- La SPA existante reste servie ; les routes ajoutées sont additives.

## 8. Critères d'acceptation (CA)

Tests : Go `internal/mcpserver/clients_compat_test.go`, `schema_portability_test.go`, `profiles_test.go`, `internal/httpapi/journey_nomcp_test.go`, `internal/mcpserver/no_claude_text_test.go` ; Node `scripts/client-compat/run.mjs` ; web `web/src/pages/*.test.tsx` des écrans touchés, `web/scripts/e2e-journey.mjs` (manuel/optionnel). **Simulateur d'imprimante** (`internal/printer/sim`, `cmd/printer-sim`) pour tout scénario d'impression ; slicer factice quand Bambu Studio est absent.
- **CA1** Étant donné un `bambud` de test, quand `scripts/client-compat/run.mjs` tourne avec le SDK TypeScript officiel et l'Inspector CLI, alors les deux obtiennent la même liste d'outils que le client Go (mêmes noms), valident le schéma sans erreur, exécutent les 4 appels de lecture avec succès, lisent une ressource de vue (`ui://bambu/print-confirm.html`, type `text/html;profile=mcp-app`) et **échouent** sur `start_print` sans confirmation (refus explicite). Le script sort en code ≠ 0 au moindre écart et affiche un tableau.
- **CA2** `TestToolSchemasAreClientPortable` passe sur la liste réelle ; un outil de test avec `"type":["object","null"]` ou sans `items` fait échouer le test (test négatif) ; chaque aplatissement de schéma réalisé est couvert par un test d'équivalence (entrées valides/invalides identiques avant/après).
- **CA3** Profils : sans paramètre, `tools/list` est **identique octet pour octet** (après tri) à la liste obtenue avant ce chantier (fichier de référence versionné dans `testdata`) ; avec `?profile=core`, la liste est exactement l'ensemble déclaré dans `profiles.go` et plus petite ; un appel par nom à un outil hors `core` renvoie l'erreur claire ; un nouvel outil non classé fait échouer le test de classification (test négatif).
- **CA4** Sécurité par profil : en `core` comme en `full`, `request_print_confirmation` renvoie le lien `/confirm` et **aucun** outil ne peut approuver (`TestNoMCPToolCanApproveAConfirmation` exécuté dans les deux profils).
- **CA5** Texte autosuffisant : pour 8 outils à image/vue (`request_print_confirmation`, `capture_preview`, `get_model_details`, `search_models`, `show_layers`, `get_job_status`, `get_print_status`, `show_atelier`), `content[0].text` est non vide et contient l'information clé listée ; avec un client **sans** annonce de vue, le lien web équivalent est présent.
- **CA6** OAuth : une redirection fournie par `BAMBU_OAUTH_REDIRECTS` est acceptée à l'enregistrement/autorisation, une redirection non listée est refusée, et **aucune** redirection d'autre éditeur n'est acceptée par défaut (test de la liste par défaut).
- **CA7** Parcours sans MCP : le test Go `journey_nomcp_test.go` déroule le parcours F8(a) uniquement par HTTP, jusqu'à la fiche de journal et au coût, avec **un seul** `project_file` reçu par le simulateur, **après** l'approbation par la page `/confirm` (cookie de navigateur enregistré) ; avant l'approbation, le compteur de commandes du simulateur est à zéro ; le test échoue si un appel `/mcp` est émis (intergiciel de comptage).
- **CA8** `docs/PARCOURS-WEB.md` contient les 13 parcours, chacun avec une cellule d'état renseignée (`complet/partiel/absent`) et, pour chaque `partiel/absent`, soit une référence au commit qui le comble, soit une ligne « reste à faire » avec taille ; un test de lien vérifie que chaque route d'API citée existe réellement dans le routeur (extraction des motifs de `internal/httpapi`).
- **CA9** Web (vitest) : les états vides des écrans du parcours affichent « Que faire ensuite ? » avec un lien valide ; la page d'accueil montre l'état de préparation ; aucun texte ne contient « Claude » dans les écrans concernés (test de recherche).
- **CA10** `docs/CLIENTS-MCP.md` : chaque ligne de client a un statut ∈ {`testé <date> <version>`, `non testé`} ; un test de doc vérifie qu'aucune ligne ne dit « compatible » sans statut `testé` ; les clients de F1 couverts automatiquement sont `testé` avec la version réelle (`npx` fixe la version).
- **CA11** Reformulations de F10 : `go test ./internal/mcpserver/...` passe avec **les mêmes** tests de textes de sécurité ; aucun test existant n'a été modifié pour passer (la différence de tests existants est vide, hors ajouts).
- **CA12** `go test -short ./... -count=1` vert, `go vet ./...` propre, compilation croisée sans cgo, `cd web && npm ci && npm run build && npx vitest run` verts.
