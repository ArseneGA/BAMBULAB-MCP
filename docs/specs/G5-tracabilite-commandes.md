# G5 — Traçabilité par commande pour les fermes

Spec pour un agent de code. Lire d'abord `docs/specs/README.md` § 2 (règles communes), `docs/UTILISATION.md` §§ 4, 8, 10, 11 (lancement, caméra, file d'attente, journal), `docs/SECURITY.md` §§ 3, 4, 12. Module Go `github.com/ArseneGA/BAMBULAB-MCP`, Go ≥ 1.26, SQLite pur Go, `CGO_ENABLED=0`.

## 1. Objectif et valeur

Une ferme d'impression sait répondre, pour **chaque commande client**, à : *quelles pièces, quelles impressions, sur quelle machine, avec quelle bobine, quels réglages réels, qui a donné l'accord de lancement, à quelle heure, avec quelle photo avant/après, quel contrôle qualité, et pour quel coût réel*. Printalk relie **commande → lignes (pièces) → impressions → preuves** et produit un **dossier de traçabilité** exportable. Il se différencie des gestionnaires de flotte (gratuits ailleurs) en **vendant la preuve et la qualité**, pas le nombre d'imprimantes, avec un humain qui garde la main sur chaque lancement.
Segment : petites fermes (3 à 15 imprimantes), vendeurs avec commandes multiples.

## 2. Périmètre / hors périmètre

Dans le périmètre : entités commande et lignes ; liaison lignes ↔ impressions (une impression peut servir plusieurs commandes, une ligne peut demander plusieurs impressions) ; état et priorité/échéance ; file d'attente triable par priorité et échéance (sans jamais lancer seule) ; contrôle qualité par ligne avec photos et défauts ; trace complète par impression (réglages réels, bobine, machine, accord humain, photos) ; coût réel par commande ; dossier de traçabilité (zip + JSON + CSV, PDF facultatif) ; outils MCP, routes HTTP, écrans web.
Hors périmètre : import automatique de commandes depuis Etsy/MakerWorld/Shopify (API ou CSV) ; facturation et paiement ; expédition (transporteurs, étiquettes) ; gestion des stocks de pièces finies ; planification automatique de la production (l'humain décide de l'ordre ; l'outil **propose**) ; multi-utilisateurs avec rôles (c'est **G6**) ; données personnelles clients au-delà d'une étiquette (pas d'adresse, pas de téléphone).
Frontière avec G2 : G2 possède les **devis** (`quotes`, prix, PDF). Une commande peut être créée **à partir d'un devis accepté** (liaison facultative, détectée à l'exécution) ; le coût réel d'une commande est la somme des coûts réels des impressions liées, calculée par les fonctions de `internal/insights` existantes.
Frontière avec G6 : G5 ne modifie **ni** `internal/humanauth` **ni** la sémantique d'approbation ; il **lit** la trace d'audit.

## 4. Exigences fonctionnelles

**F1 — Commande.** Une commande a : `reference` (numéro lisible, ex. `C-2026-0007`, généré, modifiable tant qu'unique), `customer_label` (étiquette libre : prénom/organisme ou pseudo ; **aucune adresse**), `channel` (`etsy | makerworld | direct | autre`), `external_ref` (numéro côté plateforme, texte libre), `status` (`nouvelle | planifiee | en_production | en_pause | prete | expediee | annulee`), `priority` (1 = urgente … 5 = basse, défaut 3), `due_at` (échéance facultative), `notes`, `quote_id` (facultatif, liaison G2), dates de création/mise à jour. Une commande a **≥ 1 ligne** ; une ligne a : `model_id` + `version_id` **figée** (la version au moment de la commande ; l'avertir si une version plus récente existe), `description`, `quantity` (≥ 1), `material`/`color` demandés, `variant_id` ou `profile_revision` facultatifs (réglages convenus), `unit_price` facultatif (information, pas de calcul de marge ici).
**F2 — Liaison impressions.** Table de liens ligne ↔ impression : `print_job_id`, `plate`, `parts` (nombre d'exemplaires de cette ligne **produits par cette impression**), création **manuelle** (`link_print_to_order`) ou à la mise en file (`queue_print` accepte `order_id`/`order_line_id` optionnels). Une impression multi-pièces (plateau composé par `plan_plate`) peut être liée à plusieurs lignes/commandes. Délier est possible tant que l'impression n'est pas terminée ; après, la liaison est **figée** (la corriger exige une note et crée une entrée d'audit).
**F3 — Progression dérivée (jamais saisie).** Pour chaque ligne : `qty_ordered`, `qty_planned` (somme `parts` des impressions non terminées), `qty_printed` (impressions `COMPLETED` × `parts`), `qty_ok` (somme des contrôles qualité `pass`), `qty_failed`, `qty_rework`. Pour la commande : `progress_pct = Σ qty_ok / Σ qty_ordered`, `late` (échéance dépassée et statut ni `prete` ni `expediee` ni `annulee`), `next_actions[]` calculées (ex. « Ligne 2 : aucune impression liée », « 1 impression en attente de l'accord humain : ouvrir /confirm/… », « Ligne 1 : contrôle qualité à faire »). Le statut `status` reste **posé par l'humain** (ou par un outil appelé par le modèle sur demande explicite) ; le système ne le change jamais seul, il **suggère** (`suggested_status`).
**F4 — File par priorité et échéance (sans lancement automatique).** `queue_print` accepte en plus `priority`, `due_at`, `order_id`, `order_line_id` (champs JSON additifs du `doc` de la file, pas de migration) ; `list_print_queue` accepte `sort` ∈ {`position` (défaut, comportement actuel), `priority_due`} et, dans ce second cas, renvoie l'ordre **proposé** (priorité croissante, puis échéance la plus proche, puis ancienneté) avec la **raison** de chaque rang. Aucun réordonnancement n'est appliqué sans appel explicite à `reorder_queue` (existant). La file **ne lance jamais** : un élément « prêt » attend l'accord humain sur `/confirm` comme aujourd'hui ; un test vérifie qu'aucun chemin de la file n'appelle `Approve` ni `Start`.
**F5 — Trace d'une impression (« fiche de preuve »).** `orders.TraceOf(printJobID)` assemble, **sans rien inventer** : machine (`printer_id`, modèle, numéro de série si connu), fichier découpé (`artifact_sha256`, nom, révision de profil, empreinte du fichier source du modèle), **réglages réels** (`LogEntry.Settings` : température, remplissage, hauteur de couche… tels que lus dans l'archive), matières et **bobines** (`spool_usage` : bobine, grammes consommés, prix au kg figé, **lot** si renseigné), horaires (début/fin, durée réelle), issue (`Outcome`), **accord humain** (entrée d'audit `print.confirmation_approved` : instant, valeur de `via` affichée comme chaîne — tolérer qu'elle soit enrichie plus tard —, `plate_clear`, options de lancement approuvées : mise à niveau, calibrations, timelapse), **photos** (photo de la page de confirmation `kind=confirm`, photo de fin `kind=final`, photos du journal, alertes caméra), défauts déclarés, coût réel (`ActualCost`). Chaque champ porte son **niveau** : *mesuré* (lu de l'archive, de l'imprimante, du journal), *calculé* (coût), *estimé* (valeurs estimées/prorata d'une impression interrompue : `spool_usage.estimated=1` doit apparaître), *déclaré* (saisie humaine : défauts, notes, lot). Un champ absent est affiché « non disponible » avec la raison (ex. « pas de caméra sur cette imprimante »).
**F6 — Contrôle qualité (QC).** `record_order_qc` enregistre pour une ligne : `result` (`pass | fail | rework`), `qty`, `defects[]` (vocabulaire existant `insights.validDefect` ; autre texte libre refusé ou rangé en `note`), `note`, `operator` (étiquette libre facultative), `photos[]` (références `sha256` de blobs déjà déposés ou `camera_photo_id` ; **dépôt de photo par l'interface web** uniquement, comme `POST /api/print-log/{id}/photo`), `print_job_id` concerné. Les contrôles sont **ajoutés** (journal), jamais écrasés ; une correction est un nouveau contrôle qui référence le précédent. Une ligne `fail` ouvre une suggestion « réimprimer » (non exécutée).
**F7 — Coût réel d'une commande.** `orders.CostOf(orderID)` = somme des `ActualCost.Total` des impressions liées, **au prorata de `parts`** quand une impression sert plusieurs lignes/commandes (règle : part de la masse totale des pièces concernées, à défaut au nombre de pièces ; la règle utilisée est **écrite dans le résultat**), + les impressions échouées liées (coût du gâchis affiché **séparément**). Si une impression n'a pas de coût réel (pas de durée observée), le coût est **estimé** et marqué ainsi. Comparaison avec le devis lié s'il existe (écart en montant et %).
**F8 — Dossier de traçabilité.** `export_order_dossier` (travail asynchrone, comme `export_project`) produit une archive zip : `trace.json` (toutes les fiches F5 + QC + coût), `trace.csv` (une ligne par impression, colonnes stables, séparateur `;`, UTF-8 avec BOM, dates ISO), `README.txt` (français : contenu, empreintes, niveaux de preuve, avis), `photos/` (confirmation, fin, QC), `manifest.json` (sha256 de chaque fichier, version de Printalk, date). Si `internal/pdfdoc` (G2) est disponible, un `dossier.pdf` de synthèse est ajouté (sinon omis sans erreur et le README le dit). **Aucun secret, aucun chemin du serveur, aucune donnée client hors l'étiquette.** URL signée de 10 minutes, conservation 24 h, taille bornée (réutiliser `internal/export` : constructeur, bornes, nettoyage).
**F9 — Outils MCP (nouveaux ; texte en français).** `create_order`, `get_order` (avec progression, `next_actions`, impressions liées, coût), `list_orders` (filtres `status`, `late`, `channel`, `due_before`, tri `priority_due`), `update_order` (statut, priorité, échéance, notes, ajout/suppression de lignes **tant qu'aucune impression terminée n'est liée à la ligne**), `link_print_to_order`, `record_order_qc`, `get_order_trace` (fiche de preuve complète ou d'une impression), `export_order_dossier` (+ `get_order_dossier` pour l'URL signée, ou réutilisation de `get_project_export` si le mécanisme l'accepte). Les outils `queue_print` et `list_print_queue` reçoivent les paramètres additifs de F4 (tous facultatifs). **Aucun outil de lancement/arrêt n'est ajouté ni modifié.** Exemple de texte rendu : « Commande C-2026-0007 (Etsy, échéance 2026-11-20, priorité 2) : 12/20 pièces conformes (60 %). Ligne 2 : aucune impression liée. 1 impression prête : l'accord se donne sur <lien>. Coût réel à ce jour : 31,40 € (dont 4,10 € de gâchis). ».
**F10 — Routes HTTP.** `GET|POST /api/orders` ; `GET|PATCH /api/orders/{id}` ; `POST /api/orders/{id}/lines` ; `POST /api/orders/{id}/links` ; `POST /api/orders/{id}/qc` ; `POST /api/orders/{id}/photos` (multipart, image ≤ 5 Mio, signature d'image vérifiée comme `checkImageBlob`) ; `GET /api/orders/{id}/trace` ; `POST /api/orders/{id}/dossier` ; `GET /api/orders/{id}/photos/{sha}` (protégée). Les téléchargements du dossier passent par l'URL signée (mécanisme des exports ; **`isSignedAsset` de `guard.go` étendu aussi étroitement que pour `/api/exports/*.zip`**).
**F11 — Écrans web (vert Printalk).** Menu « Commandes » (`Shell.tsx`) : liste (référence, client, canal, statut, priorité, échéance avec badge « en retard », barre de progression, coût réel), détail (lignes avec progression, **chronologie** des impressions liées avec pastilles de niveau Mesuré/Calculé/Estimé/Déclaré, photos avant/après côte à côte, bouton « Contrôle qualité » avec dépôt de photo et choix de défauts, bloc coût, bouton « Exporter le dossier »), et sur la page « File » (`Filament.tsx`) : colonnes Priorité/Échéance modifiables et bouton « Proposer l'ordre ». Un lien « Ouvrir la confirmation » renvoie à `/confirm/…` (jamais d'approbation depuis ces écrans). États vides, erreurs et chargements explicites.
**F12 — Documentation.** `docs/COMMANDES.md` : flux type d'une commande, définitions des statuts, niveaux de preuve, contenu du dossier, limites (pas de facturation ni d'import), exemple de `trace.csv`.

## 5. Modèle de données

Migration **additive** `<N>_orders.sql` (N = dernier existant + 10 au moment du codage) :
- `orders(id TEXT PK, reference TEXT NOT NULL UNIQUE, customer_label TEXT NOT NULL DEFAULT '', channel TEXT NOT NULL DEFAULT 'direct', external_ref TEXT NOT NULL DEFAULT '', status TEXT NOT NULL, priority INTEGER NOT NULL DEFAULT 3, due_at TEXT, quote_id TEXT NOT NULL DEFAULT '', notes TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL, updated_at TEXT NOT NULL)` ; index `(status, due_at)`, `(priority, due_at)`.

- `order_print_links(id TEXT PK, order_line_id TEXT NOT NULL REFERENCES order_lines(id), print_job_id TEXT NOT NULL, plate INTEGER NOT NULL DEFAULT 0, parts INTEGER NOT NULL CHECK (parts >= 1), frozen INTEGER NOT NULL DEFAULT 0, note TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL, UNIQUE(order_line_id, print_job_id, plate))` ; index `(print_job_id)`.
- `order_qc(id TEXT PK, order_line_id TEXT NOT NULL REFERENCES order_lines(id), print_job_id TEXT NOT NULL DEFAULT '', result TEXT NOT NULL, qty INTEGER NOT NULL CHECK (qty >= 1), defects TEXT NOT NULL DEFAULT '[]', note TEXT NOT NULL DEFAULT '', operator TEXT NOT NULL DEFAULT '', photos TEXT NOT NULL DEFAULT '[]', corrects TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL)` ; **trigger** interdisant `UPDATE`/`DELETE` (journal en ajout seul, sur le modèle de `slicing_profiles_no_update`) ; index `(order_line_id)`.

- Photos de contrôle : blobs existants adressés par sha256 ; rattachement dans `order_qc.photos` (liste de sha256) ; le contenu est vérifié comme une image (JPEG/PNG) avant enregistrement.
- Audit : `order.created`, `order.status_changed`, `order.linked`, `order.qc_recorded`, `order.dossier_exported`.
- Aucune colonne existante n'est modifiée ; les champs de file (F4) vivent dans le JSON `doc` de `print_queue`.

## 6. Sécurité et règles non négociables

- **Approbation humaine intacte** : ni la file, ni la commande, ni aucun nouvel outil ne peut approuver, lancer ou arrêter une impression ; la priorité et l'échéance **n'accélèrent jamais** un lancement ; chaque impression garde son accord humain individuel lié à (imprimante, empreinte du fichier, plateau, matières). Tests : `TestNoMCPToolCanApproveAConfirmation` étendu aux nouveaux outils ; un test statique interdit l'import de `Approve`/`Start` dans `internal/orders`.
- **Données personnelles minimales** : étiquette client seulement ; jamais dans les journaux applicatifs ; suppression d'une commande = suppression de ses lignes/liens/QC et des références de photos (les blobs orphelins sont nettoyés par le ramasse-miettes existant, à vérifier).
- **Journal QC en ajout seul** (triggers) ; liaisons figées après impression terminée ; toute correction est tracée.
- **Distinguer mesuré/calculé/estimé/déclaré** dans la trace, le dossier et l'interface ; champ inconnu = « non disponible » + raison.
- **Secrets** : aucun code d'accès d'imprimante, jeton ni chemin serveur dans la trace ni dans le dossier (test de recherche de motifs sur l'archive produite).
- **Originaux immuables** : les lignes pointent une **version figée** ; la trace ne modifie aucun fichier ni profil.
- Validation des entrées (bornes de quantité, longueurs de texte, énumérations), protection contre les références croisées (une ligne ne peut lier qu'une impression existante).

## 7. Compatibilité production

- Les outils `queue_print`/`list_print_queue` gardent leurs entrées/sorties actuelles : les ajouts sont **facultatifs**, `sort` vaut `position` par défaut ⇒ ordre identique à aujourd'hui.
- Aucun outil renommé ni supprimé ; `tools/list` conforme (`spec_conformance_test.go`) avec les 9 outils ajoutés.
- Migration additive uniquement (4 tables + 1 compteur) ; aucune donnée existante migrée ; une installation qui n'utilise jamais les commandes n'a aucun changement visible (menu « Commandes » vide avec état vide explicite).
- Le journal d'impression, la caméra, les bobines, la file et l'approbation fonctionnent à l'identique ; le serveur Linux, la P1S en direct et `mcp-remote` ne demandent aucune action.
- Si G7 est fusionné (impressions « déclarées » sans lancement), la trace gère le niveau *déclaré* ; sans G7, il n'apparaît pas.
