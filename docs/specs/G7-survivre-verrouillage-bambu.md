# G7 — Survivre au verrouillage Bambu : tout fonctionne sans lancement

Spec pour un agent de code. Lire d'abord `docs/specs/README.md` § 2 (règles communes), `docs/research/bambu-lan-protocol.md` §§ 1 et 3 (Authorization Control, mode Développeur), `docs/SECURITY.md` §§ 3-5, `docs/strategie/ETUDE-MARCHE.md` §§ 5.3, 9 (risque n°1), `docs/BRANCHEMENT.md`. Module Go `github.com/ArseneGA/BAMBULAB-MCP`, Go ≥ 1.26, SQLite pur Go, `CGO_ENABLED=0`.

## 1. Objectif et valeur

Le **risque n°1** du produit est que Bambu Lab durcisse ou retire le mode Développeur/LAN (l'« Authorization Control » de 2025 a déjà réduit le contrôle tiers ; `ETUDE-MARCHE.md` § 5.3). Ce chantier garantit que **100 % de la valeur hors lancement survit** : bibliothèque, CAO paramétrique, réparation, découpe, comparaison, coût, devis, rapports, journal, commandes. Quand l'imprimante n'accepte plus qu'on la pilote, Printalk **prépare et livre** : il produit le fichier `.gcode.3mf` validé et une **feuille de lancement** qui reprend tout ce que la page de confirmation montrait (matières, températures, avertissements), l'humain lance **lui-même** (carte SD, Bambu Studio/Handy, Bambu Connect), puis déclare ou fait observer le résultat pour que le journal, les bobines et les coûts restent justes. Le mode est choisi **par imprimante**, sans toucher au mode actuel.
Segment : tous (assurance de la valeur du produit).

## 2. Périmètre / hors périmètre

Dans le périmètre : réglage `launch_mode` par imprimante (+ commutateur global) ; application stricte côté serveur (aucune écriture réseau vers une imprimante en mode livraison) ; **paquet de livraison** (`.gcode.3mf` + feuille de lancement + variante « carte SD ») téléchargeable par URL signée ; commande de livraison à l'**agent Windows** pour ouvrir Bambu Connect (si vérifié) ; **déclaration humaine** du lancement et du résultat (niveau « déclaré ») ; observation en lecture seule quand elle reste possible ; détection d'un rejet de lancement qui **propose** de passer en mode livraison ; simulateur capable de reproduire un verrouillage ; documentation honnête des voies Bambu (« à vérifier ») ; écrans web.
Hors périmètre : contournement de l'Authorization Control, signature ou usurpation d'identité de logiciel autorisé, utilisation de l'API/cloud non officiels de Bambu (risque de conditions d'utilisation), automatisation de l'écran de l'imprimante, **tout lancement automatique** ; écriture sur carte SD par le serveur (le serveur n'a pas accès au support physique : l'humain copie) ; intégration d'une API officielle de Bambu **qui n'existe pas encore** (le chantier prévoit seulement la couture d'abstraction, voir F9).

## 4. Exigences fonctionnelles

**F1 — Mode de lancement par imprimante.** Champ `launch_mode` ∈ {`direct` (comportement **actuel**, défaut), `delivery` (préparer et livrer ; aucune écriture réseau vers la machine)} et `observe` ∈ {`auto` (défaut : lecture MQTT best-effort si la connexion fonctionne), `off`}, stockés dans le document JSON de l'imprimante (`printers.doc`, champs additifs `omitempty`, **sans migration**). Lecture seule dans `list_printers`, `get_printer_status`, `get_capabilities` (texte : « Mode : livraison (le lancement se fait sur la machine) »). **Changement de mode** : uniquement par la CLI `bambud printer mode <id> direct|delivery` et une action sur une page humaine (`/setup/printer-mode/{id}`, cookie de navigateur enregistré) ; **aucun outil MCP ne change le mode** (le modèle ne peut ni activer ni désactiver le lancement). Commutateur global d'urgence : `BAMBU_LAUNCH_MODE=delivery` (ou `--launch-mode delivery`) force `delivery` pour **toutes** les imprimantes, prioritaire sur le réglage par imprimante ; la valeur effective est affichée.
**F2 — Application stricte en mode livraison.** `printing.Service` refuse, pour une imprimante en `delivery`, toute opération qui **écrit** vers la machine : `Upload`, `Start`, `Pause`, `Resume`, `Stop`, calibrations, commandes G-code ; erreur typée `ErrDeliveryMode` avec le texte « Cette imprimante est en mode livraison : le fichier est préparé pour un lancement manuel. Utilise prepare_delivery. ». Le contrôle est **dans la couche service** (pas seulement dans les outils), donc valable pour MCP, HTTP, file d'attente (`queue_print` ne dépose plus et marque l'élément « livraison »), agent. `request_print_confirmation`, `start_print`, `upload_print_artifact`, `cancel_print` renvoient ce refus clair. La **lecture** (`Status`, `Subscribe`) reste permise si `observe=auto`. La machine d'états n'est **pas** modifiée (pas de nouvel état) : la livraison est un jalon porté par le `Job` (F3).
**F3 — Paquet de livraison.** Nouvel outil `prepare_delivery` (écriture, travail court ou long selon la taille) : entrée `print_job_id` (impression **VALIDATED** ou plus avancée, découpée et validée) ; sortie : `delivery_id`, nom de fichier, taille, sha256, URL signée de 10 minutes du `.gcode.3mf` et du **zip « carte SD »**, et le texte de la feuille de lancement. Le `.gcode.3mf` livré est **l'artefact exact validé** (mêmes octets, même sha256 ; jamais re-généré). Nom de fichier assaini et stable : `<stem>-<sha12>.gcode.3mf` (même règle que `remoteName`). Le **zip** contient : le `.gcode.3mf` à la racine (organisation exacte attendue par les imprimantes Bambu sur carte SD : **à vérifier** ; ne pas inventer de sous-dossier), `LISEZ-MOI.txt` (feuille de lancement en texte) et `feuille-de-lancement.html` (autonome, imprimable, sans script ni ressource externe), `SHA256SUMS`. **Feuille de lancement** (reprend tout ce que montre `/confirm`) : imprimante, plaque, nom du fichier, empreinte abrégée, durée et masses **mesurées par le slicer** (niveau « mesuré (slicer) »), matières et **affectation AMS/bobines** attendues (couleur, matière, emplacement), **températures** (buse, plateau) lues dans le G-code (`gcodeexcerpt.go`), options attendues (mise à niveau, calibrations, timelapse), **avertissements** (risque d'adhérence `Job.Adhesion`, fabricabilité), case « plateau vide et propre », et les **marches à suivre** de F5 (une par voie), avec la phrase fixe « Printalk ne lance rien : c'est vous qui démarrez l'impression sur la machine. ». Génération côté serveur en Go (`html/template` ; pas de bibliothèque PDF requise ; si `internal/pdfdoc` de G2 est présent, une version PDF peut être ajoutée, sinon omise). Route HTTP : `POST /api/print-jobs/{id}/delivery` et `GET /api/print-jobs/{id}/delivery/{sha}.zip|.gcode.3mf?exp&sig` (URL signée HMAC comme les exports ; **`isSignedAsset` étendu aussi étroitement que pour `/api/exports/*.zip`**). Le fichier ne sort **que** par URL signée.
**F4 — Déclaration humaine et observation.** (a) `declare_manual_print` (écriture ; réservé aux imprimantes en `delivery`) : `print_job_id`, `started_at` (défaut maintenant), `outcome` (`started | completed | failed | cancelled`), `ended_at`, `grams_used` (facultatif, sinon la masse du slicer, **marquée estimée**), `note`. Effets : ajoute des jalons au `Job.Delivery` (document JSON additif : `route`, `prepared_at`, `declared[]`), crée/complète la **fiche de journal** (`insights.LogEntry`, champ additif `source` : `printer` (défaut) | `declared` | `observed`), décompte les **bobines** (`spool_usage.estimated = 1`, note « déclaré »), alimente les coûts réels et le tableau de bord. **Le niveau de preuve est « déclaré par l'humain »**, distinct de « mesuré » : l'interface et les outils l'affichent partout (journal, coûts, rapports, dossiers G5). (b) Page web : boutons « J'ai lancé l'impression » et « Terminée / Échouée » sur la fiche d'impression livrée. (c) **Observation** : si `observe=auto` et que la lecture MQTT fonctionne, un observateur (abonné en lecture à `Status`, comme `internal/camera` et `internal/notify` : abonnement aux transitions, sans pouvoir les provoquer) associe une impression en cours à une livraison quand `GcodeFile`/`SubtaskName` correspond au nom livré ; il passe la déclaration en `observed` (début, progression, fin `FINISH`/`FAILED`) et déclenche les mêmes effets (journal, bobines) avec niveau « observé (lecture seule) ». Si l'imprimante est injoignable, la déclaration humaine reste possible. Rien de ceci ne lance, ne dépose ni ne commande.
**F5 — Voies de livraison (documentées et, quand c'est sûr, assistées).** Documentation et feuille couvrent, **chacune avec « à vérifier »** tant que non testée sur le matériel réel : (1) **Carte SD** : copier le fichier du zip sur la carte, l'insérer, lancer depuis l'écran de l'imprimante ; (2) **Bambu Studio** : ouvrir le `.gcode.3mf`/`.3mf` et utiliser « Envoyer » (réseau local ou cloud selon le mode de l'imprimante) ; (3) **Bambu Handy** : envoi depuis Studio via le cloud (nécessite le mode cloud de l'imprimante, donc **incompatible avec le mode Développeur/LAN seul**, à vérifier) ; (4) **Bambu Connect** : application relais officielle de Bambu pour logiciels tiers (disponibilité par système d'exploitation et schéma d'URL d'import **à vérifier** sur la documentation Bambu/communauté ; la communauté mentionne un schéma de type `bambu-connect://import-file?path=…&name=…&version=…`, **non vérifié ici**). Aucune de ces voies n'est présentée comme garantie. **Assistance via l'agent Windows** (seulement si le schéma d'URL est vérifié par l'agent de code sur une source citée) : nouveau type de travail d'agent `open_in_connect` (ouvre Bambu Connect avec le fichier ; **l'humain clique ensuite sur Imprimer dans l'application de Bambu**) ; il n'est **pas** un travail physique (le serveur ne commande rien à la machine) mais est documenté comme tel ; `PhysicalKinds` reste **inchangé** et un test le garantit ; le fichier est transmis à l'agent par le mécanisme de blobs vérifiés par sha256 existant (`GET blobs/{sha}`). Si la vérification échoue, la voie reste « téléchargement manuel » et la doc dit pourquoi.
**F6 — Détection d'un verrouillage et proposition (sans changer de mode seul).** Quand, en mode `direct`, un lancement est **rejeté** par l'imprimante (réponse `result:fail` à `project_file`, `FaultRejectStart` du simulateur, codes d'erreur de `internal/printer/errcodes.go` correspondant à une autorisation refusée — **codes à relever dans la doc de recherche, à vérifier**) ou que la connexion MQTT/FTPS est systématiquement refusée alors que l'imprimante répond au réseau, le texte rendu au modèle ajoute : « L'imprimante refuse les commandes de lancement : cela peut venir d'un verrouillage du fabricant (Authorization Control) ou du mode Développeur désactivé. Printalk peut continuer en mode livraison : demandez à l'humain d'exécuter `bambud printer mode <id> delivery` ou d'utiliser la page /setup/printer-mode/<id>. ». Aucun changement de mode automatique ; la détection est consignée dans le journal d'audit (`printer.launch_rejected`) et affichée sur la page Imprimantes (bandeau « Lancement refusé par la machine — passer en mode livraison ? »).
**F7 — Simulateur verrouillé.** Ajouter une panne `lock_dev_mode` à `internal/printer/sim` (et à l'indicateur `--faults` de `cmd/printer-sim`) qui reproduit un verrouillage : refus de `project_file` (`result:fail` avec un code d'erreur dédié), FTPS refusé après authentification (530) ; la **lecture d'état MQTT** reste permise par défaut, avec une seconde panne `lock_status` qui la refuse aussi (pour tester `observe`). Les pannes existantes ne changent pas.
**F8 — Écrans web (vert Printalk).** Page **Imprimantes** (`web/src/pages/Printers.tsx`) : badge de mode (« Direct » / « Livraison »), bandeau de détection F6, lien vers la page humaine de changement de mode (aucun bouton qui bascule en `direct` depuis la SPA : la bascule passe par la page humaine). Page **Impressions** (`Print.tsx`) pour un job de machine en livraison : à la place du bouton de confirmation, bloc **« Livraison »** : bouton « Préparer la livraison », liens de téléchargement (fichier, zip SD), feuille de lancement affichée, boutons de déclaration/observation (F4), pastille de niveau « Déclaré »/« Observé ». Texte d'aide « Pourquoi ce mode ? » avec le résumé du risque n°1 en deux phrases et un lien `docs/LIVRAISON.md`.
**F9 — Couture d'abstraction « voie officielle ».** Sans implémenter d'API inexistante : introduire dans `internal/printer` une interface facultative `Deliverer` (`Deliver(ctx, artefact, name, sha256) (DeliveryRef, error)`) que `delivery` implémente par « paquet local » aujourd'hui ; un test d'interface vérifie que `Bambu` (mode direct) et le mode livraison respectent le même contrat de non-lancement ; la doc `docs/LIVRAISON.md` décrit où brancher une éventuelle API officielle (à vérifier si Bambu en ouvre une).
**F10 — Documentation.** `docs/LIVRAISON.md` : pourquoi (risque n°1), choix du mode (CLI, page), voies de livraison avec leurs états « à vérifier », ce qui marche / ne marche pas sans lancement (tableau : bibliothèque, CAO, découpe, comparaison, coût, devis, journal = tout ; lancement, caméra, AMS en direct, arrêt = non), exemple de feuille de lancement, commande d'urgence `BAMBU_LAUNCH_MODE=delivery`, procédure de test sur la vraie P1S (**à faire par l'humain**, avec points d'arrêt, à la manière de `docs/BRANCHEMENT.md`).
Outils MCP **nouveaux** : `prepare_delivery`, `declare_manual_print` (+ lecture : `get_delivery` ; ou champ `delivery` ajouté à `get_print_status`/`get_job_status` de façon additive). Outils existants : aucun renommage ; en mode livraison leur refus est explicite.

## 5. Modèle de données

- **Pas de migration obligatoire** : `launch_mode`/`observe` dans `printers.doc` ; `Job.Delivery` dans `print_jobs.doc` ; `source` dans le document de `print_logs.doc`.
- Migration **facultative additive** `<N>_delivery.sql` (N = dernier existant + 10 au moment du codage) : `deliveries(id TEXT PK, print_job_id TEXT NOT NULL, printer_id TEXT NOT NULL, route TEXT NOT NULL DEFAULT '', artifact_sha256 TEXT NOT NULL, zip_sha256 TEXT NOT NULL DEFAULT '', sheet_sha256 TEXT NOT NULL DEFAULT '', state TEXT NOT NULL, declared TEXT NOT NULL DEFAULT '[]', created_at TEXT NOT NULL, updated_at TEXT NOT NULL)` + index `(print_job_id)`, `(printer_id, created_at)` — utile pour lister les livraisons et leur état sans parcourir les `Job` ; à décider par l'agent (sinon JSON dans le `Job`).
- Les zip de livraison et feuilles sont des fichiers temporaires (`<données>/deliveries/<id>.zip`, **supprimés à l'expiration**, comme `project_exports`) ou des blobs ; jamais de secret dedans.
- Audit : `printer.mode_changed`, `printer.launch_rejected`, `delivery.prepared`, `delivery.declared`.

## 6. Sécurité et règles non négociables

- **Aucun lancement automatique, aucune écriture vers la machine en mode livraison**, vérifié dans la couche service et par un test exhaustif (toutes les routes et tous les outils ; compteur d'écritures du simulateur à zéro).
- **L'humain lance** : le serveur ne commande rien ; `PhysicalKinds` (`start_print`, `send_to_printer`) reste interdit à l'agent ; le nouveau travail `open_in_connect` (si implémenté) ne commande pas la machine.
- **Le modèle ne change pas le mode** : seul le terminal de l'humain ou une page humaine (navigateur enregistré) le fait ; le passage `delivery → direct` redonne un pouvoir, donc il est humain-seulement ; un test vérifie qu'aucun outil MCP ne modifie `launch_mode`.
- **Secrets** : le code d'accès de l'imprimante n'est jamais dans la feuille, le zip, les journaux ni les réponses ; aucune adresse IP interne n'est écrite dans la feuille (nom de l'imprimante seulement) ; chemins de serveur absents.
- **Original immuable** : le `.gcode.3mf` livré a le sha256 exact de l'artefact validé ; le zip reprend ces octets sans les modifier ; `SHA256SUMS` permet la vérification.
- **Mesuré / déclaré / observé distingués** : une déclaration humaine n'est jamais présentée comme une mesure ; les masses estimées sont marquées ; l'observation est en lecture seule.
- **Sécurité du fichier livré** : mêmes contrôles qu'avant le dépôt (`ValidateArtifact`, scan thermique/sécurité du G-code `internal/slicer/gcodesafety.go`) ; une livraison est **refusée** si la validation a des contrôles bloquants.
- Téléchargement uniquement par URL signée (HMAC, 10 min) ; pas de chemin de fichier côté client.
- Ne pas contourner les protections du fabricant ; ne pas encourager le retour de version de firmware dans l'interface (seulement mentionné comme information externe « à vérifier » dans la doc).

## 7. Compatibilité production

- **Défaut `direct` = comportement actuel à l'identique** : P1S en direct (LAN + Développeur), dépôt FTPS, lancement par accord humain, caméra, AMS, arrêt, file d'attente, journal. Aucune configuration à changer ; les imprimantes existantes n'ont pas de champ `launch_mode` (lu comme `direct`).
- Serveur Linux, `mcp-remote`, pont `bambu-mcp`, Claude Desktop : inchangés.
- Aucun outil renommé ou supprimé ; deux outils ajoutés (+ un champ additif de statut) ; `tools/list` conforme (`spec_conformance_test.go`) ; **en mode `direct`, les textes des outils existants ne changent pas** (le texte « mode livraison » n'apparaît qu'en mode livraison).
- `internal/contracts/print.go` (machine d'états) **non modifié** : aucun nouvel état ; les tests de la machine d'états restent verts sans changement.
- Migration éventuelle additive ; sans elle, aucune base n'est modifiée.
- Variable d'environnement `BAMBU_LAUNCH_MODE` absente ⇒ aucun effet.
