# G6 — Mode classe et fablab : l'élève prépare, l'encadrant lance

Spec pour un agent de code. Lire d'abord `docs/specs/README.md` § 2 (règles communes), `docs/SECURITY.md` en entier (§§ 1 à 4, 10, 12 surtout), `docs/OAUTH.md` § 2, `docs/UTILISATION.md` § 4 bis. Module Go `github.com/ArseneGA/BAMBULAB-MCP`, Go ≥ 1.26, SQLite pur Go, `CGO_ENABLED=0`.

## 1. Objectif et valeur

Permettre à une école, un lycée, un fablab ou un makerspace d'utiliser Printalk avec des élèves **sans créer de comptes élèves** : les postes (ou groupes) **préparent** (importer, concevoir, découper, chiffrer, demander un lancement) ; **seul un encadrant** valide, depuis son navigateur, ce qui part sur les machines. Tout reste **sur site** (aucun service cloud nécessaire), et chaque demande, décision et résultat est consigné dans un **journal auditable** sans donnée nominative. C'est exactement ce que le produit a déjà (approbation humaine, données chez soi), qu'une institution exige.
Segment : écoles, fablabs, makerspaces (licence auto-hébergée, `docs/strategie/ETUDE-MARCHE.md` § 3.3, § 6).

## 2. Périmètre / hors périmètre

Dans le périmètre : **mode classe** activable/désactivable ; deux rôles (**préparateur**, **encadrant**) ; jetons de **poste** et inscription de navigateurs avec rôle ; séances (créneaux) ; règles et quotas ; file des **demandes de lancement** à valider ; refus motivé ; journal auditable à chaînage d'empreintes ; export CSV et purge ; restriction des outils MCP selon le rôle (liste blanche stricte) ; pages web ; sous-commande `bambud class …` ; documentation de déploiement sur site.
Hors périmètre : comptes nominatifs d'élèves, annuaire (LDAP/SSO/ENT), notation, import de listes d'élèves ; gestion de classes à l'année ; chiffrement de disque ; hébergement cloud (SaaS) ; toute **approbation par un préparateur ou par un outil** ; approbation depuis une vue de conversation (carte avec code) dans le mode classe (désactivée par défaut, voir F7).

## 4. Exigences fonctionnelles

**F1 — Mode classe (interrupteur).** Réglage `class_mode` (table de réglages dédiée, défaut **désactivé**). Activation par `bambud class enable` (terminal de l'humain) ou page humaine `/setup/class` (encadrant). Mode désactivé : **comportement strictement actuel** (les rôles sont ignorés, toute session et tout jeton valent « encadrant »). Mode activé : F2 à F9 s'appliquent. Un indicateur `class_mode` figure dans `get_capabilities` (lecture seule) et `GET /health` n'en dit rien (pas de fuite).
**F2 — Rôles.** Deux rôles : `encadrant` (tous les pouvoirs actuels : approbation, réglages, imprimantes, règles de classe) et `preparateur` (préparer et demander ; **jamais approuver**). **Défaut de tout l'existant = `encadrant`** : les sessions, jetons et autorisations OAuth déjà enregistrés gardent leurs pouvoirs (colonnes ajoutées avec défaut `encadrant`). Le Bearer statique `BAMBU_API_TOKEN` = `encadrant`. Le rôle `preparateur` ne peut être obtenu que par : (a) un **code d'enregistrement de navigateur** émis avec `bambud enroll --role preparateur` ou depuis `/setup/class` ; (b) un **jeton de poste** (F3) ; (c) une autorisation OAuth accordée **depuis une session préparateur** (le rôle de la session qui consent est copié dans `oauth_grants.role` ; un préparateur ne peut jamais consentir un rôle supérieur). Aucun outil MCP, aucune route `/api/*` ne permet de changer un rôle ni d'émettre un jeton/code.
**F3 — Jetons de poste.** `bambud class station add --label "Poste 3" [--session <séance>] [--ttl 8h]` affiche **une seule fois** un jeton (≥ 32 octets aléatoires, préfixe `pst_`), stocké **haché** (SHA-256) avec libellé, rôle `preparateur`, expiration (défaut : fin de la séance, sinon 8 h, maximum 30 jours), révocation (`bambud class station revoke|list`). Utilisable comme Bearer sur `/mcp` et `/api/*` (pont `bambu-mcp --api-token-file`, `mcp-remote --header`, Claude Code). Le jeton n'apparaît ni dans une réponse MCP, ni dans un journal, ni dans l'audit (seulement son identifiant `st_…` et son libellé). Limitation de débit des essais invalides comme pour le jeton d'API. Pas de jeton de poste sur la surface publique de G1 sauf configuration explicite.
**F4 — Séances.** Une **séance** = nom libre (« 4e B – techno »), début, fin, postes autorisés (facultatif). `bambud class session open --name "…" --until 12:00` ou `/classe` → « Ouvrir une séance ». En mode classe, les jetons de poste ne valent que **pendant une séance ouverte** (sinon 401 explicite « aucune séance ouverte : demander à l'encadrant »), les demandes et décisions portent l'identifiant de séance. Fermeture manuelle ou automatique à l'heure de fin. Les navigateurs enregistrés avec rôle suivent la même règle pour le rôle `preparateur`.
**F5 — Outils MCP autorisés pour un préparateur (liste blanche, refus par défaut).** Un module `internal/classroom/policy.go` classe **chaque outil existant** dans `allow` ou `deny` pour le rôle `preparateur`, avec la raison. Un test **échoue si un outil du `tools/list` n'est pas classé** (tout nouvel outil de n'importe quel chantier est donc refusé tant qu'on ne l'a pas classé). Classement initial **proposé** (à relire, voir § 10) : *autorisés* — lecture (`search_models`, `get_model_details`, `list_*` sauf imprimantes sensibles, `get_*_status`, `analyze_geometry`, `compare_variants`, `capture_preview`, `show_*`, `estimate_cost`, coûts en lecture, calibration en lecture), préparation (`import_model`, `upload_file`, `import_from_url`, `create_parametric_model`, `create_from_template`, `modify_geometry`, `repair_mesh`, `tag_models`, `apply_file_operations` limité à renommer/étiqueter/déplacer, `create_experiment`, `execute_headless_slice`, `plan_plate`, `execute_plate_slice`, `check_filament_for_print`, `validate_print_artifact`, `generate_calibration_set`), demande (`request_print_confirmation`, `queue_print`) ; *refusés* — `add_printer`, `set_cost_settings`, `set_filament_margin`, `configure_notifications`, `configure_failure_detection`, `test_notification`, `scan_folder`, `import_files` (chemins **du serveur**), `manage_print_history`, `restore_from_trash`, `update_spool`, `reorder_queue`/`remove_from_queue` des autres postes, `upload_print_artifact` (dépôt sur la machine : réservé à l'encadrant **ou** déclenché par l'approbation, voir F7), `start_print`, `cancel_print`, `cancel_job` d'un travail d'un autre poste, `reconcile_print`, `set_manufacturing_goals`, `record_*` d'étalonnage de la machine, `get_camera_snapshot` selon réglage, `export_project` (réglage), `open_in_studio` (agent Windows), et `approve_*_with_code`. **Mécanisme conseillé** : un serveur MCP par rôle (`mcpserver.NewForRole(c, role)` qui n'enregistre que les outils autorisés) choisi dans la fonction passée à `mcp.NewStreamableHTTPHandler` (`httpapi.go`) d'après le rôle du jeton ; **à vérifier dans le SDK `go-sdk v1.8.0`** quand cette fonction est appelée et que le rôle d'une session ne peut pas changer en cours de session (sinon : intergiciel de réception `AddReceivingMiddleware` refusant `tools/call` et filtrant `tools/list`). Dans les deux cas, **refus au niveau de l'appel** (pas seulement du listage) et message en français : « Ce poste est préparateur : cette action est réservée à l'encadrant. ».
**F6 — Routes `/api/*` et pages selon le rôle.** Un intergiciel de rôle (`internal/classroom/gate.go`) applique en mode classe la même politique aux routes `/api/*` (liste blanche par méthode + préfixe ; tout ce qui n'est pas classé → refus 403 pour un préparateur) et **rend les pages humaines d'approbation inaccessibles** aux sessions préparateur : `/confirm/*`, `/stop/*`, `/setup/*` (dont `/setup/passkeys*` et `/setup/printer/{id}` ; sauf pages en lecture seule explicitement classées), `/agents/pair`, `/oauth/consent/*` (consentement permis au préparateur **uniquement** pour un rôle préparateur, F2c), `/enroll` inchangé. Un préparateur qui ouvre `/confirm/…` voit une page « Demandez à l'encadrant de valider cette impression » avec le **résumé de la demande** (sans bouton d'approbation, sans formulaire). `humanauth.Require` reste la première barrière (cookie de navigateur enregistré) ; le contrôle de rôle s'y **ajoute**, il ne la remplace pas.
**F7 — Demandes de lancement et validation par l'encadrant.** Quand un préparateur appelle `request_print_confirmation`, la confirmation est créée **comme aujourd'hui** (liaison imprimante + empreinte + plateau + matières) **et** une **demande de classe** est enregistrée : séance, poste (libellé du jeton/de la session), groupe (étiquette libre facultative donnée dans le champ `note`/`requested_by`, avec **avertissement** si elle ressemble à une adresse e-mail ou un numéro de téléphone), impression, modèle, imprimante, matières, masse et durée estimées, avertissements d'adhérence, photo du plateau si disponible, état `en_attente`. **Règles vérifiées à la demande** (F8) ; en cas de dépassement → refus immédiat avec message clair. Page encadrant `/classe` (« À valider ») : liste en direct (rafraîchissement périodique), détail, lien **« Ouvrir la confirmation »** vers `/confirm/{id}` (l'approbation reste **exactement** le geste existant : navigateur enregistré **encadrant**, nonce, case « plateau vide », options de lancement), et bouton **« Refuser »** (motif obligatoire ≤ 200 car.) qui invalide la confirmation (réutiliser le mécanisme d'invalidation existant de `internal/printing/confirm.go` ; s'il manque, ajouter `RejectConfirmation` additif) et marque la demande `refusee`. Un élève voit l'état par l'outil **`get_launch_request`** (lecture) et par `get_job_status` : « En attente de l'encadrant », « Refusée : <motif> », « Approuvée, lancée à 10:42 », « Expirée ». **Le dépôt du fichier sur l'imprimante** (`upload_print_artifact`), aujourd'hui étape préalable à la demande, reste autorisé **seulement** dans le flux normal de la demande si la politique l'accepte ; sinon (réglage `deposit_requires_approval`, défaut vrai en mode classe) le dépôt est déclenché **après** l'approbation par l'encadrant. L'approbation par carte avec code de lancement (`approve_*_with_code`) est **désactivée en mode classe** (réglage `allow_card_approval`, défaut faux), car la carte s'afficherait dans la conversation d'un élève.
**F8 — Règles et quotas (réglables par l'encadrant).** `max_grams_per_request` (défaut vide = sans limite), `max_print_hours`, `allowed_materials[]`, `allowed_printers[]`, `max_pending_per_station` (défaut 3), `max_requests_per_session_per_station`, `allowed_hours` (créneaux où les **demandes** sont acceptées), `retention_days` (journal, défaut 365). Chaque refus de règle explique la règle. Les règles s'appliquent à la **demande** ; l'approbation reste un acte humain libre.
**F9 — Journal de classe auditable.** Table en **ajout seul** (triggers) où chaque évènement est enchaîné : `prev_hash` + `row_hash = sha256(prev_hash ‖ contenu canonique)`. Évènements : `session.opened/closed`, `station.created/revoked`, `request.created`, `request.rejected_by_rule`, `request.refused`, `request.approved` (avec `approver` = libellé de la session encadrant, **valeur de `via`**), `print.finished` (issue), `role.enroll`, `class_mode.changed`, `rules.changed`. **Aucune donnée nominative requise** : étiquettes libres uniquement. Page `/classe/journal` (filtres date/séance/poste/décision), export CSV (`;`, UTF-8 BOM) par `bambud class export --since … --until …` et bouton web, vérification `bambud class verify-journal` (recalcule la chaîne, signale la première rupture), purge `bambud class purge --before …` qui **conserve une ligne de ré-ancrage** (hash de la dernière ligne supprimée) pour garder la chaîne vérifiable, et purge automatique selon `retention_days`.
**F10 — Enrichissement de l'approbation.** `Approve(ctx, confID, plateClear, via)` : la valeur `via` passée en mode classe devient `encadrant:<libellé de session>` (chaîne d'affichage) ; hors mode classe : **valeur actuelle inchangée**. G5 traite `via` comme une chaîne libre.
**F11 — Écrans web (vert Printalk).** Pour un **encadrant** : menu « Classe » (`/classe`) avec onglets *À valider*, *Séances*, *Postes*, *Règles*, *Journal* ; boutons d'ouverture/fermeture de séance, création d'un jeton de poste (affiché une fois, avec bouton copier et rappel « ne le collez pas dans une conversation »), création d'un code d'enregistrement préparateur, règles. Pour un **préparateur** (rôle lu via `GET /api/session`, champ additif `role`) : bandeau « Mode classe — poste Poste 3 — séance 4e B », menu réduit (Bibliothèque, Préparer, Impressions en lecture, Coûts en lecture), bouton **« Demander le lancement »** (qui appelle la même route que l'outil) à la place de tout lien d'approbation, état de ses demandes. Aucun écran ne montre un jeton déjà émis.
**F12 — Sous-commandes CLI.** `bambud class enable|disable|status`, `class session open|close|list`, `class station add|list|revoke`, `class rules show|set`, `class export`, `class verify-journal`, `class purge`, `enroll --role preparateur`. Toutes opèrent sur la base locale comme `bambud enroll` (aucun accès réseau).
**F13 — Documentation.** `docs/CLASSE.md` : déploiement sur site (un PC ou Raspberry Pi serveur + postes + imprimantes sur le réseau local ; sans Internet sauf mises à jour), scénario type d'une séance, ce que voient élèves et encadrant, ce qui est journalisé (et **ce qui ne l'est pas** : aucune donnée nominative), limites, check-list RGPD **à faire valider par l'établissement** (pas une conformité affirmée), licence (AGPL-3.0 ; la licence commerciale est une décision de l'utilisateur).
Outils MCP **nouveaux** : `get_launch_request` (lecture, pour le préparateur et l'encadrant) ; **aucun outil d'approbation, de refus, de création de jeton ou de changement de rôle**. Les refus/approbations passent **uniquement** par les pages humaines.

## 6. Sécurité et règles non négociables

- **L'élève prépare, l'encadrant lance** : un préparateur **ne peut jamais** approuver ni arrêter une impression : ni par un outil MCP, ni par `/api/*`, ni par une page humaine, ni par la carte avec code (désactivée en mode classe). Tests négatifs obligatoires pour **chaque** chemin (`internal/classroom/noapprove_test.go`, extension de `TestNoMCPToolCanApproveAConfirmation`).
- L'approbation reste liée à (imprimante, empreinte du fichier, plateau, matières), à usage unique, expirante ; le mode classe **n'affaiblit aucune** de ces propriétés ; la file ne lance jamais seule.
- **Refus par défaut** : outil ou route non classé ⇒ refusé pour le préparateur ; escalade de rôle impossible (aucun chemin pour devenir encadrant depuis un jeton de poste, un code préparateur ou un consentement OAuth d'un préparateur).
- **Jetons de poste** : hachés, affichés une fois, expirants, révocables, jamais journalisés ; comparaison en temps constant ; limitation des essais ; pas d'envoi par MCP.
- **Secrets** (code d'accès imprimante, code de lancement) : inaccessibles aux préparateurs (aucune route ne les lit).
- **Données nominatives** : non requises, non collectées ; avertissement si une étiquette ressemble à un e-mail/téléphone ; journal sans photo d'élève (les photos de caméra montrent le plateau ; l'encadrant décide du réglage caméra en classe, voir § 10).
- **Journal auditable** : ajout seul + chaîne d'empreintes ; limites assumées dites dans la doc (quelqu'un ayant l'accès administrateur au fichier de base peut tout réécrire ; la chaîne détecte une modification partielle, pas une réécriture complète ; un export régulier hors machine renforce la preuve).
- **Surface publique (G1)** : le mode classe est conçu **sur site** ; ne pas exposer `/classe`, `/setup/*` ni les jetons de poste sur Internet.
- Mode désactivé ⇒ aucun contrôle supplémentaire, aucun changement de comportement.

## 7. Compatibilité production

- Installation actuelle : mode classe **désactivé** par défaut ; toutes les sessions et autorisations existantes gardent le rôle `encadrant` ; le Bearer statique, `mcp-remote`, `bambu-mcp`, Claude Code, l'OAuth de Claude et le lancement par code ou par page `/confirm` fonctionnent **sans action**.
- `tools/list` : un seul outil ajouté (`get_launch_request`), aucun renommé ; en mode désactivé, l'ensemble des outils visibles est identique à aujourd'hui ; `TestToolsListConformsToMCPSpec` vert pour **chaque rôle**.
- Migration additive (`ADD COLUMN` avec défaut + tables nouvelles) ; aucun redémarrage de session requis.
- `Approve(..., via)` : valeur inchangée hors mode classe.
- Les pages `/confirm`, `/stop`, `/setup/launch-code` sont inchangées pour un encadrant.

- **CA2** Mode activé, jeton de poste valide pendant une séance ouverte : `tools/list` ne contient que les outils classés `allow` ; un appel à un outil `deny` (`add_printer`, `scan_folder`, `set_cost_settings`) renvoie le refus en français **même si l'outil est appelé par son nom** (appel direct d'un client qui connaît le nom).
- **CA3** Test de **classification exhaustive** : pour chaque outil de `tools/list` (rôle encadrant), la table de politique contient une entrée ; ajouter un outil factice sans entrée fait échouer le test (preuve du refus par défaut) ; la politique est vérifiée par `go test` à chaque évolution du dépôt.
- **CA4** Sans séance ouverte, le jeton de poste est refusé (401 explicite) ; à la fermeture de la séance, une session MCP déjà ouverte est refusée dès l'appel suivant ; un jeton expiré ou révoqué est refusé ; 10 essais invalides rapprochés déclenchent la limitation.
- **CA5** Étant donné un préparateur qui appelle `request_print_confirmation` (imprimante simulée), alors une demande `en_attente` existe avec poste, séance, masse et durée estimées ; **aucun** ordre n'a été envoyé à l'imprimante simulée (compteur de commandes à zéro) ; `get_launch_request` rend « En attente de l'encadrant ».
- **CA6** Étant donné une session **préparateur** (cookie) qui ouvre `/confirm/{id}` : la page n'a **ni formulaire ni bouton d'approbation** ; un `POST` d'approbation avec ce cookie renvoie 403 et aucune approbation n'est enregistrée ; avec une session **encadrant**, le `POST` approuve, le simulateur reçoit exactement un `project_file`, et l'audit/journal de classe contient `request.approved` avec `via = encadrant:<libellé>`.
- **CA7** Un préparateur ne peut pas obtenir le rôle encadrant : un consentement OAuth depuis une session préparateur produit un grant `role = preparateur` ; l'enrôlement avec un code `--role preparateur` produit une session préparateur ; aucune route ne modifie `role` (tests de table de routes, y compris `PATCH`/`PUT` fantaisistes).
- **CA8** `approve_print_with_code` et `approve_stop_with_code` renvoient le refus « mode classe » quel que soit l'appelant ; `TestNoMCPToolCanApproveAConfirmation` reste vert pour les deux rôles et dans les deux modes.
- **CA9** Quotas : une demande de 500 g avec `max_grams_per_request = 300` est refusée avec la règle citée et journalisée `request.rejected_by_rule` ; un 4e élément en attente pour le même poste (limite 3) est refusé ; une matière hors `allowed_materials` est refusée.
- **CA10** Refus : l'encadrant refuse avec motif ⇒ la confirmation devient inutilisable (un `Approve` ultérieur échoue), la demande passe `refusee`, `get_launch_request` rend « Refusée : <motif> » ; un refus sans motif est rejeté.
- **CA11** Journal : 50 évènements ⇒ `verify-journal` OK ; la modification d'une ligne (via SQL direct en test) est détectée à la ligne exacte ; `UPDATE`/`DELETE` sont bloqués par les triggers hors chemin de purge ; la purge conserve l'ancre et la chaîne reste vérifiable ; l'export CSV a un en-tête stable, un BOM et **aucun** champ de jeton, de code d'accès ou d'adresse e-mail (recherche de motifs).
- **CA12** Dépôt : avec `deposit_requires_approval` vrai, `upload_print_artifact` par un préparateur est refusé ; après l'approbation par l'encadrant, le dépôt et le lancement s'enchaînent selon le comportement actuel (démarrage automatique à l'approbation) et le simulateur voit un seul `project_file`.
- **CA13** Étiquette de groupe ressemblant à une adresse e-mail : acceptée avec avertissement dans la réponse ; une étiquette de plus de 60 caractères est refusée.
- **CA14** Web (vitest, API simulée) : un préparateur voit le bandeau et **aucun** lien/bouton d'approbation ou de réglages ; un encadrant voit l'onglet *À valider*, ouvre une séance, crée un jeton (affiché une seule fois, puis masqué) ; les états vides et les erreurs sont rendus.
